From mocks to real integration tests

This lesson tests a bookstore checkout, not an instrument controller. It demonstrates why each testing library is useful and when it is unnecessary. The browser experiment is a JavaScript model, not a .NET test runner. The companion source contains actual xUnit tests.

1. Start with the real problem

A customer buys two $19.99 books. The application checks stock, requests a $39.98 payment authorization, stores the order, and sends a confirmation. The obvious test is “did checkout return success?” That question alone misses many expensive failures.

2. xUnit: the test runner and assertion vocabulary

xUnit discovers [Fact] and [Theory] methods, runs them and reports failures. Its assertions define expected outcomes. It is not a mock library, database or HTTP server.

[Fact]
public async Task Invalid_cart_does_not_charge()
{
    var result = await service.PlaceAsync(new("", 0, "token"));
    Assert.False(result.Success);
}

Run dotnet test to execute the C# suite. Fast unit tests should describe behavior, not just mirror implementation details.

3. NSubstitute: control and observe collaborator calls

Inventory stock and email dispatch are separate concerns. A substitute lets the test set stock to available without needing the actual warehouse service, and verify a notification happened once.

var inventory = Substitute.For<IInventory>();
inventory.InStockAsync("BOOK-1", 2, Arg.Any<CancellationToken>())
         .Returns(Task.FromResult(true));
await inventory.Received(1).InStockAsync(
    "BOOK-1", 2, Arg.Any<CancellationToken>());

For order-sensitive synchronous interactions, Received.InOrder(() => { ... }) can describe the expected invocation sequence. It observes invocation ordering, not completion ordering across independent asynchronous operations. A mock asserting a call happened is not proof that a production notification was delivered.

4. WireMock.Net: test your actual HTTP client

A substituted IPaymentGateway cannot detect incorrect JSON property names, endpoint paths or content types. WireMock.Net starts a local HTTP endpoint. Your real HttpClient sends the request and a stubbed response exercises serialization and response handling.

using var server = WireMockServer.Start();
server.Given(Request.Create()
    .WithPath("/authorize").UsingPost()
    .WithBody(new JsonMatcher(new { amountCents = 3998, token = "valid" })))
    .RespondWith(Response.Create().WithStatusCode(200)
       .WithHeader("Content-Type", "application/json")
       .WithBody("{\"approved\":true}"));

A local fake does not ensure the real remote provider uses the same protocol; keep official API contracts and provider sandbox tests.

5. Testcontainers: run real PostgreSQL in Docker

An in-memory list cannot detect PostgreSQL syntax errors, schemas, SQL types or transaction behavior. Testcontainers starts a disposable PostgreSQL container for the test, provides a connection string, and cleans up afterward.

await using var db = new PostgreSqlBuilder().WithImage("postgres:16-alpine")
    .WithDatabase("checkout_tests")
    .WithUsername("postgres")
    .WithPassword("postgres").Build();
await db.StartAsync();
var store = new PgOrderStore(db.GetConnectionString());
await store.InitializeAsync();

Docker or a compatible container engine must be installed and running. CI runners need container support. The image tag in this teaching snapshot is not digest-pinned.

6. All four working together

BoundaryImplementation in combined test
Test orchestrationReal xUnit test
Checkout orchestrationReal CheckoutService
Stock and notificationNSubstitute
Payment APIReal HttpClient + WireMock.Net
DatabaseReal Npgsql + PostgreSQL container

The success test should assert HTTP request count, the stored row's SKU/quantity/amount and notification count. The decline test should assert zero rows and zero notifications. The database-failure test should assert that authorization occurred but insert failed and no notification went out.

7. Why the failure case matters

It reveals a distributed consistency hole: a payment can be approved even though the order cannot be saved. Neither mocks nor a green unit suite resolves that problem. A real system should consider authorize-then-capture, idempotency keys, a persistent state machine, and an explicit reconciliation/compensation process. A test exposing this is a useful failing architecture requirement, not evidence of production readiness.

8. Reproduce locally

./setup.sh
./task.sh doctor
./task.sh test
./task.sh preview
# On Windows: .\setup.ps1 ; .\task.ps1 test

Preview serves static HTML only. A separate integration-test command requires an explicit running Docker engine. The setup scripts do not install or start Docker without permission.

9. When to use which tool?

Use xUnit for all ordinary C# tests. Use NSubstitute when a controlled collaborator or invocation contract matters. Use WireMock.Net when correctness depends on the HTTP wire contract. Use Testcontainers when correctness depends on the behavior of a real dependency. Resist adding a container to a pure calculation or mocking your own domain objects. Mock external edges and keep business logic real.

10. What has not been proved?

The static browser example never runs .NET, WireMock.Net or PostgreSQL. A local test run does not validate provider uptime, production credentials, payment idempotency, production migrations, or full distributed failure recovery. See the lesson README for provenance and verification notes.
