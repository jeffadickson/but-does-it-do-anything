What breaks in the straightforward solution?

A pure unit test can stub every collaborator and obtain a green result, even when the payment client's JSON field names are wrong or the SQL insert fails. Move those critical boundaries into integration tests: use an HTTP fake with actual requests, and a real database in a disposable container. Keep lightweight substitutes for inventory and notifications.

Important design flaw: authorizing a payment and subsequently saving an order is not atomic. If PostgreSQL fails after approval, a customer might be charged without an order. A passing test that detects this gap does not fix it. Consider payment authorization/capture separation, idempotency keys and reconciliation or a saga.
