01 / THE PROBLEM · CIRCA 2004

Three instruments. Six seconds. Almost no CPU work.

You have a digital multimeter, a current meter, and a frequency counter. Each takes roughly two seconds to integrate a signal and return a reading. A straightforward program asks one question at a time:

double voltage = meter.MeasureVoltage();
double current = currentMeter.MeasureCurrent();
double frequency = counter.MeasureFrequency();

The second call starts only after the first returns. The third starts after the second. Elapsed time is about 2 + 2 + 2 = 6 seconds, plus communication overhead. The computer is not necessarily doing six seconds of arithmetic. Most of that time can be spent waiting for electronics, an integration interval, or bytes.

A blocking call prevents the calling thread from progressing until the call returns. A thread is an execution context with a stack and scheduling state. While a blocked thread normally consumes little CPU, it still occupies resources and, in a bounded pool, one of the available workers. A thread pool reuses workers to avoid constantly creating threads; it does not turn blocking I/O into nonblocking I/O.

Concurrency

Several operations are in progress during overlapping time intervals. One CPU can coordinate three instruments that work independently.

Parallelism

Several computations execute at the same instant, typically on different cores. It helps CPU work; it is not required to overlap device waiting.

If the instruments are genuinely independent, initiate all three measurements before collecting their results. Their waiting intervals overlap, and total time approaches the longest interval: about two seconds. A two-worker pool running three blocking calls needs two waves, so it takes about four seconds. Shared buses, a common trigger, session locking, and instrument limits can change the result.

02 / JAVA 5 · 2004

A handle to work that has not finished yet.

Future<T> made it practical to separate submission from result retrieval using the standard concurrency library. A Callable<T> produces a result and may throw; an ExecutorService schedules it; the returned Future lets the caller observe its outcome. This standardized an important pattern rather than inventing the general idea of futures.

  1. Submit a callable.
  2. Receive its Future without waiting for the measurement result.
  3. The executor schedules the callable, possibly after a queue delay.
  4. The caller does other work.
  5. The Future reaches a terminal result, failure, or cancellation state.
  6. get() waits if necessary, then returns or throws.
ExecutorService executor = Executors.newFixedThreadPool(2);
try {
    Future<Double> future = executor.submit(() -> measureVoltage());
    System.out.println("Doing other work");
    double voltage = future.get();
} finally {
    executor.shutdown();
}

The lambda above requires Java 8. The complete FutureLab.java below uses a Java 5-style anonymous Callable and adds timeout handling and executor termination. Submission may still throw, for example if the executor rejects work; “immediate” means it does not wait for the operation’s result, not that submission is guaranteed to succeed or have zero cost.

03 / JAVA 8 · 2014
Describe what happens next.
CompletableFuture combines a Future with completion-stage composition. Instead of waiting for each intermediate value, construct a graph whose edges describe dependencies. Only the steps with dependencies must run sequentially.
APIUse in our laboratory
supplyAsyncSchedule a supplier. Without an explicit executor, normally uses the common ForkJoinPool. Blocking hardware calls often deserve a dedicated executor.
thenApplyTransform a completed voltage into calibrated volts: T → U.
thenComposeStart a dependent asynchronous read: T → CompletableFuture<U>, flattening the nested future.
thenCombineCombine two independent eventual results, such as volts × amps.
allOfA completion barrier returning CompletableFuture<Void>; collect typed results from the original futures afterward.
anyOfThe first terminal outcome, successful or exceptional, as CompletableFuture<Object>. Losers continue.
A non-Async continuation may run on a completing thread or an attaching caller if already completed. thenApplyAsync schedules through its executor. Neither spelling guarantees a particular thread identity for your whole chain.
CompletableFuture<Double> volts = supplyAsync(() -> readVoltage(), io);
CompletableFuture<Double> amps  = supplyAsync(() -> readCurrent(), io);
CompletableFuture<Double> watts = volts.thenCombine(amps, (v, i) -> v * i);
// No get() between submissions. Both reads can now progress.
exceptionally supplies a recovery value; handle transforms either success or failure; whenComplete observes an outcome, but can itself introduce a failure. join() blocks and exposes exceptional completion through CompletionException; get() uses checked ExecutionException. A recovery value should not disguise a failed safety measurement.
CompletableFuture.cancel(true) marks exceptional completion with CancellationException; its interrupt flag does not control the underlying computation. It is not a general upstream or sibling cancellation mechanism. Design the operation’s cancellation separately.

04 / A DIFFERENT ROUTE TO SCALABILITY
Keep the blocking style. Make the waiting thread cheaper.
Java virtual threads became final in Java 21. A platform thread is tied to an OS thread. A virtual thread is scheduled by the JVM onto carrier threads and can unmount during supported blocking operations, freeing its carrier for other work. This scales large numbers of waiting operations; it does not make an FFT run faster or remove device bandwidth limits. Native calls and runtime-specific pinning behavior require care.
Java virtual thread
Preserves a thread-oriented, blocking-style call stack. The runtime can suspend that virtual thread while supported I/O waits.
C# asynchronous I/O
An async method suspends via a compiler-generated state machine. The pending operation is represented by a Task; no dedicated blocked thread is inherently required.
Complete Java 21 program · VirtualLab.java{{JAVA_VIRTUAL}}
Structured concurrency is about ownership
Related work belongs to a scope: start children, join their outcomes, and finish their lifetimes before leaving. A scope’s policy can propagate failure and request cancellation of siblings. Cancellation still relies on cooperation. Merely using a virtual-thread executor does not choose a fail-fast policy.
Version check: 14 October 2026. Oracle’s Java 27 documentation identifies StructuredTaskScope as Structured Concurrency, Seventh Preview (JEP 533). It is not a final API. Java 26 used the sixth preview. Examples written for older previews may not compile against a newer one. This lesson’s runnable Java programs deliberately use stable APIs; preview concepts are explained without claiming stable source compatibility.

05 / .NET’S EVENTUAL OUTCOME
A Task is an operation, not a thread.
The Task Parallel Library arrived with .NET 4; C# 5 added async/await. Task<T> represents one eventual typed result, fault, or cancellation. A non-generic Task represents completion without a result value. Tasks can represent CPU work, network I/O, a timer, or an externally completed promise.
Task<double> measurement = MeasureVoltageAsync();
DoOtherWork();
double voltage = await measurement;
Calling an ordinary async method starts executing its body synchronously until it reaches an incomplete await. The returned task is usually already in progress; awaiting it observes and composes its outcome. There are exceptions to “tasks start automatically”: explicitly constructing new Task(...) creates an unstarted task. Prefer normal async APIs or Task.Run rather than that constructor.

06 / THE CENTRAL IDEA
Save the method’s place. Give the thread back.
Consider a user clicking “Measure.” The method begins on the UI thread, sends a command, and receives a task representing the pending reply. At await, the generated code checks whether the awaiter is already complete. If it is, execution continues inline. If not, it records the method’s state and arranges a continuation, then returns control to the caller.
The compiler transforms locals and control flow into a state machine. On completion, the continuation resumes at the next state, retrieves the result or throws the operation’s exception, and executes the next source statement. The continuation is not a second invocation of the entire method.
Experiment 4 · Follow one await
An actual asynchronous socket or OS I/O implementation can arrange completion notification without reserving a worker to wait. An API named Async can also wrap blocking native calls on a worker; inspect the implementation and driver contract. The keyword alone cannot guarantee nonblocking I/O.
Where does the continuation run?
By default, Task await can capture a suitable SynchronizationContext (for example, a desktop UI context), or a non-default TaskScheduler. The UI context posts the continuation back to its UI thread. In a console application or typical ASP.NET Core request, there usually is no such context; continuation placement is then governed by task completion and scheduling, often on the thread pool. It is not a guarantee of a new thread, or even a different thread.
Reusable library code that does not need a caller’s context often uses await operation.ConfigureAwait(false). This avoids requesting that context for that await. It does not force a thread switch, suppress all ExecutionContext flow, or make blocking safe everywhere. UI code that updates controls normally needs its UI context.
// I/O: use the asynchronous operation directly.
string text = await httpClient.GetStringAsync(uri, token);
// CPU: optionally offload substantial work to keep a UI responsive.
Spectrum result = await Task.Run(() => ComputeFft(samples), token);
Task.Run queues work to the thread pool. Its token can prevent work that has not started; the calculation itself must check cancellation to stop after it starts. Wrapping every async I/O call in Task.Run adds scheduling overhead without solving an I/O problem. Wrapping a blocking legacy driver is sometimes a containment strategy, but the worker remains occupied and cancellation needs driver support.
The classic deadlock
A UI handler calls ReadAsync().Result. ReadAsync awaits incomplete I/O and captures the UI context. The handler blocks the UI thread waiting for the result. I/O completes, but its continuation needs that same UI thread. Neither can proceed. Use await through the caller chain. On a server without that context, blocking can still exhaust workers even without this exact deadlock.
Async changes how a method waits. It neither guarantees concurrency nor creates a thread.

07 / START TOGETHER, OBSERVE TOGETHER
WhenAll joins work. It does not start it.
Task<double> volts = dmm.MeasureAsync(token);
Task<double> hz = counter.MeasureAsync(token);
Task<double> rms = scope.MeasureAsync(token);
Task<double[]> all = Task.WhenAll(volts, hz, rms);
try {
    double[] readings = await all; // Same order as the input tasks.
} catch {
    if (all.Exception is { } failures)
        foreach (Exception failure in failures.Flatten().InnerExceptions)
            Console.Error.WriteLine(failure);
    throw;
}
await A(); await B(); is normally sequential because B is not called until A completes. Instead call A and B first, retain their tasks, then await both. This assumes the calls return promptly and refer to independently usable resources.

WhenAll reaches a terminal state only after all inputs are terminal. If any fault, the aggregate task is faulted. Otherwise, if any cancel, it is cancelled. Otherwise it succeeds. An empty input completes successfully. One failure does not automatically cancel siblings, and WhenAll does not fail early while others are still running.
Awaiting a faulted WhenAll propagates one of its stored exceptions, rather than automatically throwing an AggregateException containing every failure. Do not depend on which one is selected. The aggregate task’s Exception property retains the collected faults; use Flatten when nested aggregates need flattening. A child that itself throws AggregateException can still make await throw that exception type.
First completion is not first success
Task<double> winner = await Task.WhenAny(volts, hz);
double first = await winner; // This await can throw or be cancelled.
// The other task still needs an owner: await it, or cancel and drain it.
Task.Delay supplies a timer-backed task, unlike Thread.Sleep, which blocks a thread. It is useful for settling intervals and retries, but a fixed delay is not proof that hardware is ready.

08 / STOP WAITING ≠ STOP THE OPERATION
Give every operation an owner and an exit policy.
A CancellationTokenSource owns a cancellation request. Its token is passed down to cooperative methods, which check it or supply it to cancellable I/O. Cancellation is not arbitrary thread interruption. A correctly propagated cancelled operation typically surfaces OperationCanceledException when awaited; TaskCanceledException is a subclass.
using var timeout = CancellationTokenSource.CreateLinkedTokenSource(userToken);
timeout.CancelAfter(TimeSpan.FromSeconds(3));
try {
    return await meter.MeasureAsync(timeout.Token);
} catch (OperationCanceledException)
    when (!userToken.IsCancellationRequested && timeout.IsCancellationRequested) {
    throw new TimeoutException("Measurement exceeded its budget");
}
This asks the operation to stop. It cannot enforce a hard deadline on a driver that ignores the token. If user cancellation and timeout race, the filter above gives user cancellation priority when it is observed.
Task<double> pending = meter.MeasureAsync(operationToken);
double voltage = await pending.WaitAsync(TimeSpan.FromSeconds(3), userToken);
WaitAsync bounds the wait: timeout throws TimeoutException; cancellation of its wait token cancels the wait. Neither automatically cancels pending. Request cancellation separately, observe its eventual outcome, and do not close or reuse its session while the old operation still owns it. The complete Patterns example drains the operation; that drain can outlive the nominal timeout. A hung native driver may require process isolation and a defined recovery procedure.
A timeout is a duration for one wait. A deadline is an absolute end budget for a whole procedure. Repeatedly assigning a fresh three-second timeout to ten steps can accidentally allow thirty seconds. Compute remaining time from a monotonic clock and carry the budget through the workflow.

C# 8 introduced asynchronous streams. An async iterator can await a measurement then yield it. Mark its cancellation parameter with [EnumeratorCancellation] when it should incorporate a consumer’s WithCancellation token. Passing a token has no effect unless the implementation observes it.
A simple pull iterator need not buffer readings: the next acquisition starts when the consumer requests it. A real instrument may independently sample into onboard memory; the pull API does not automatically stop that producer. A bounded Channel with BoundedChannelFullMode.Wait makes a cooperative writer await capacity, providing backpressure. Drop modes intentionally lose data; unbounded queues can exhaust memory. Choose policies from the measurement requirements.

10 / THE HARDWARE BOUNDARY
Make the interface simple. Make its contract precise.
public interface IDigitalMultimeter {
    Task ConfigureAsync(MeasurementConfiguration config,
        CancellationToken token = default);
    Task<double> MeasureAsync(CancellationToken token = default);
    IAsyncEnumerable<double> StreamAsync(CancellationToken token = default);
}
When hardware needs two seconds, the host should ideally send an acquisition command, await readiness or a response, and parse the result without monopolizing a worker. SCPI defines instrument commands and responses; VISA supplies an access/session layer whose asynchronous capabilities depend on its implementation. An async wrapper cannot create capabilities the installed driver lacks.
The interface must document units, range selection, whether Measure initiates a new acquisition or fetches an existing one, thread-safety, and state after cancellation. A scalar double is enough for teaching; production results often need timestamps, units, range, quality flags, and calibration identity.
Boundary conditionRequired design decision
One session, two callersSerialize complete command/response transactions, not individual writes. A SemaphoreSlim can prevent one query consuming another query’s reply.
Timeout / lost networkClassify timeout, transport failure, parse failure, and device error. After a partial reply, drain/resynchronize or discard the session according to the driver contract.
Triggered acquisitionSeparate configure, arm, trigger, and fetch when synchronization matters. Concurrent host tasks do not guarantee simultaneous sampling; a shared hardware trigger may.
CancellationDefine whether you stop waiting, cancel driver I/O, issue device abort, or all three. Clear stale responses before reuse.
Output safetyAttempt disable in finally using an independent bounded token. Record cleanup failure; a lost connection means “off” is unconfirmed. Interlocks remain a hardware responsibility.
MockingReturn controlled Tasks, including failures and cancellation. Test incomplete tasks as well as Task.FromResult, which can hide ordering bugs.
Task<double> reference = referenceMeter.MeasureAsync(token);
Task<double> output = outputMeter.MeasureAsync(token);
double[] readings = await Task.WhenAll(reference, output);
double difference = readings[0] - readings[1];
A single session protected by a semaphore will serialize these calls even if the host starts them together. That can be correct. Concurrency is valuable only where the hardware and protocol support it.


11 / BEYOND AN EXACT INTERACTION LIST
Verify what must happen before what.
An EasyMock-style strict global expectation list can encode too much. If generator configuration and DMM configuration are independent, either may be invoked first and either may complete first. Rejecting the other valid order is a test bug, not a product failure.
Use a partial order: both configurations must complete before enabling the output; enabling must complete before acquisition; acquisition must finish or fail before disable begins. If configuration or enable fails, cleanup still attempts disable. These constraints accept many schedules while rejecting unsafe ones.

12 / FROM INDIVIDUAL CALLS TO A PROCEDURE
A frequency-response run has a lifetime.
The lifecycle is Created → Startup → Running → Cleanup → Completed, Failed, or Cancelled. Startup or running failure routes through Cleanup. Cleanup failure produces Failed even if acquisition succeeded; preserve both the original error and the cleanup error.
The runnable C# program configures independent sessions concurrently, enables a simulated generator, sweeps frequencies, allows settling, awaits an acquisition, computes gain in dB, records structured points, and always attempts output disable. It returns partial results on cancellation or failure. Its simulated DMM returns a constant amplitude, so the sample is an orchestration example, not a physical frequency-response model.
The runner emits JSON events and creates an ActivitySource activity. JSON output alone is not an OpenTelemetry exporter. Without an activity listener, StartActivity may return null. A host can attach OpenTelemetry instrumentation/exporters and correlate run, instrument, and step identifiers without putting that dependency into the reusable measurement interface.

Why this is different from a notebook
A notebook is excellent for trying a measurement, plotting data, and investigating a hypothesis. A reusable runner owns an execution contract: validated configuration, bounded work, task ownership, cancellation, durable results, and cleanup. An editor or notebook can call that runner; it should not be the only place the contract exists.
Modern reactive notebooks such as marimo track data dependencies and refresh dependent calculations; Quarto/Observable can present reactive explanations and plots. Those ideas are useful for the lesson and result analysis. For a hardware procedure, rerunning a dependent cell must not silently re-enable an output. Separate editable definitions from explicitly authorized execution, with immutable run records, step state, redlines, and sign-off rules where required.

Practical failure rules
  • Task-returning async methods normally store body failures in their returned task. Non-async wrappers can throw before returning a task, so partial-start failures also need ownership handling.
  • Use async Task for composable operations. Reserve async void for event handlers that require it; callers cannot await or normally catch its asynchronous failures.
  • Never infer success from IsCompleted alone; terminal includes cancelled and faulted.
  • A completed task can be awaited more than once. A source-backed ValueTask generally cannot.
  • Use an explicit result type when “failed measurement” is a normal domain outcome; do not silently substitute zero volts.

Glossary
Asynchronous
A caller can continue before an operation completes; it does not imply another thread.
Awaiter
The protocol that reports completion, registers a continuation, and retrieves an outcome for await.
Backpressure
A mechanism making producers slow down when downstream capacity is exhausted.
Blocking
Preventing the calling thread from proceeding until a condition is satisfied.
Cancellation
A request to stop work, with semantics chosen by the operation; not rollback.
Concurrency
Overlapping lifetimes of operations.
Continuation
Code scheduled or invoked when an earlier operation completes.
Deadline
An end-of-budget point for an operation or procedure.
Faulted task
A task that completed with an exception rather than a successful result.
Future / promise
A representation of an eventual outcome; “promise” often emphasizes the producer’s ability to complete it.
I/O-bound
Limited primarily by external transfers or device waiting rather than CPU execution.
Parallelism
Simultaneous execution of computations.
Partial order
Required before/after relationships that leave independent events unordered.
Race
Behavior influenced by timing between operations; not every nondeterministic order is a bug.
State machine
Stored execution state and transitions; the compiler uses one to preserve an async method across suspension.
Structured lifetime
A scope owns its child operations and accounts for them before leaving.
SynchronizationContext
An abstraction for dispatching continuations to a host’s execution environment, such as a UI thread.
Thread pool
A runtime-managed set of reusable worker threads.
Timeout
A duration limit on an operation or a particular wait; specify which.
Virtual thread
A JVM-managed thread multiplexed onto carrier threads.
You now have three separate questions to ask of every async design: What can overlap? Who owns each operation? What must still happen when it fails?
