01 / THE PROBLEM · CIRCA 2004

Three instruments. Six seconds. Almost no CPU work.

You have a digital multimeter, a current meter, and a frequency counter. Each takes roughly two seconds to integrate a signal and return a reading. A straightforward program asks one question at a time:

double voltage = meter.MeasureVoltage();
double current = currentMeter.MeasureCurrent();
double frequency = counter.MeasureFrequency();

The second call starts only after the first returns. The third starts after the second. Elapsed time is about 2 + 2 + 2 = 6 seconds, plus communication overhead. The computer is not necessarily doing six seconds of arithmetic. Most of that time can be spent waiting for electronics, an integration interval, or bytes.

A blocking call prevents the calling thread from progressing until the call returns. A thread is an execution context with a stack and scheduling state. While a blocked thread normally consumes little CPU, it still occupies resources and, in a bounded pool, one of the available workers. A thread pool reuses workers to avoid constantly creating threads; it does not turn blocking I/O into nonblocking I/O.

Concurrency

Several operations are in progress during overlapping time intervals. One CPU can coordinate three instruments that work independently.

Parallelism

Several computations execute at the same instant, typically on different cores. It helps CPU work; it is not required to overlap device waiting.

If the instruments are genuinely independent, initiate all three measurements before collecting their results. Their waiting intervals overlap, and total time approaches the longest interval: about two seconds. A two-worker pool running three blocking calls needs two waves, so it takes about four seconds. Shared buses, a common trigger, session locking, and instrument limits can change the result.

02 / JAVA 5 · 2004

A handle to work that has not finished yet.

Future<T> made it practical to separate submission from result retrieval using the standard concurrency library. A Callable<T> produces a result and may throw; an ExecutorService schedules it; the returned Future lets the caller observe its outcome. This standardized an important pattern rather than inventing the general idea of futures.

  1. Submit a callable.
  2. Receive its Future without waiting for the measurement result.
  3. The executor schedules the callable, possibly after a queue delay.
  4. The caller does other work.
  5. The Future reaches a terminal result, failure, or cancellation state.
  6. get() waits if necessary, then returns or throws.
ExecutorService executor = Executors.newFixedThreadPool(2);
try {
    Future<Double> future = executor.submit(() -> measureVoltage());
    System.out.println("Doing other work");
    double voltage = future.get();
} finally {
    executor.shutdown();
}

The lambda above requires Java 8. The complete FutureLab.java below uses a Java 5-style anonymous Callable and adds timeout handling and executor termination. Submission may still throw, for example if the executor rejects work; “immediate” means it does not wait for the operation’s result, not that submission is guaranteed to succeed or have zero cost.

The key distinction: passing the reference is equally easy. A raw Thread reference is equally easy to pass. The awkward part is that Thread does not supply a typed measurement result or carry its failure back through Join(). You must also pass a result holder, define when it is safe to read, and arrange error handling. A Future—or C# Task<T>—packages those concerns behind one standard interface.

The captured variables form the shared result holder here. Read them after Join has completed; reading while the worker writes would require additional synchronization. ExceptionDispatchInfo preserves the original exception stack when rethrowing. A reusable implementation also needs ownership, shutdown, and cancellation policies.

Store it where? Copy what? Pass it to whom?

A Future is an ordinary Java object representing an eventual outcome. Store its reference in a local variable, an object field, a list, or a map in the running process. It is not a completed Thread, not the returned voltage, and not a portable snapshot of a running job. An executor thread may finish one job and go on to another while your completed Future remains usable.

Future<Double> pending = executor.submit(() -> measureVoltage());
Future<Double> alias = pending;        // Same object, not another measurement.
this.pendingVoltage = pending;         // Store in an object field.
pendingMeasurements.add(pending);       // Retain in a list.
displayWhenReady(pending);              // Pass to a method before completion.

alias = pending copies a reference. Both variables refer to the same Future, and multiple callers may wait on it. Repeating get() does not rerun the computation. If the result is a mutable object, get() does not clone that object either; sharing and mutating the returned object need their own rules.

Passing to a method on the same thread is ordinary parameter passing. Publishing to an already-running thread requires a safe handoff, such as BlockingQueue<Future<Double>>, a concurrent collection, or correctly synchronized access. A shared ArrayList or ordinary field alone does not establish that handoff. The Future's completion guarantees do not make the surrounding collection thread-safe.

// Producer:
inbox.put(pending); // inbox is a BlockingQueue<Future<Double>>.
// Consumer (potentially another thread):
Future<Double> received = inbox.take();
double voltage = received.get(); // Same operation, potentially still pending.

A raw Thread reference is just as easy to pass. But a generic consumer holding only that Thread cannot obtain a typed measurement through Thread's API. It also needs your custom result/error holder and its synchronization contract. A Future gives consumers one standard typed handle and hides which worker ran the operation. In all cases, passing a reference does not automatically transfer exclusive ownership or responsibility for cancellation.

Complete storage and passing example · FuturePassingLab.java
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.Callable;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.LinkedBlockingQueue;
import java.util.concurrent.TimeUnit;

/** Store and pass the same pending outcome handle, including a safe cross-thread handoff. */
public class FuturePassingLab {
    /** An object field can retain a pending Future, just like any other object reference. */
    static class MeasurementRequest {
        final Future<Double> voltage;
        MeasurementRequest(Future<Double> voltage) { this.voltage = voltage; }
    }

    public static void main(String[] args) throws Exception {
        ExecutorService worker = Executors.newSingleThreadExecutor();
        try {
            Future<Double> pending = worker.submit(new Callable<Double>() {
                public Double call() throws Exception { Thread.sleep(1000); return 5.01; }
            });
            Future<Double> alias = pending; // Copy reference, not work or eventual value.
            MeasurementRequest request = new MeasurementRequest(pending);
            List<Future<Double>> measurements = new ArrayList<Future<Double>>();
            measurements.add(pending); // This list is only accessed by this caller.
            System.out.println("All references point to same Future: " +
                (alias == request.voltage && alias == measurements.get(0)));

            // In production this could be consumed by another already-running component.
            BlockingQueue<Future<Double>> inbox = new LinkedBlockingQueue<Future<Double>>();
            inbox.put(pending); // Safe publication to another thread, no waiting for the result.
            Future<Double> received = inbox.take(); // A receiver retains the same handle.
            System.out.println("Queue handoff preserved identity: " + (received == pending));
            System.out.println("Value: " + readResult(received));
            System.out.println("Read again, no rerun: " + alias.get());
        } finally {
            worker.shutdownNow();
            if (!worker.awaitTermination(5, TimeUnit.SECONDS)) {
                throw new IllegalStateException("Worker did not terminate");
            }
        }
    }

    /** A normal method parameter can accept a Future while it is pending or completed. */
    private static double readResult(Future<Double> measurement)
        throws InterruptedException, ExecutionException {
        return measurement.get();
    }
}

A Future is a handle you can use now to manage an outcome available later. Its limitation is composition, not an inability to exist or be passed before completion.

The limitation is composition. “When voltage finishes, calibrate it, then read again, while current runs independently” requires manually arranging dependencies, worker tasks, or blocking joins. The original Future interface has no continuation combinators.

03 / JAVA 8 · 2014

Describe what happens next.

CompletableFuture combines a Future with completion-stage composition. Instead of waiting for each intermediate value, construct a graph whose edges describe dependencies. Only the steps with dependencies must run sequentially.

APIUse in our laboratory
supplyAsyncSchedule a supplier. Without an explicit executor, normally uses the common ForkJoinPool. Blocking hardware calls often deserve a dedicated executor.
thenApplyTransform a completed voltage into calibrated volts: T → U.
thenComposeStart a dependent asynchronous read: T → CompletableFuture<U>, flattening the nested future.
thenCombineCombine two independent eventual results, such as volts × amps.
allOfA completion barrier returning CompletableFuture<Void>; collect typed results from the original futures afterward.
anyOfThe first terminal outcome, successful or exceptional, as CompletableFuture<Object>. Losers continue.

A non-Async continuation may run on a completing thread or an attaching caller if already completed. thenApplyAsync schedules through its executor. Neither spelling guarantees a particular thread identity for your whole chain.

CompletableFuture<Double> volts = supplyAsync(() -> readVoltage(), io);
CompletableFuture<Double> amps  = supplyAsync(() -> readCurrent(), io);
CompletableFuture<Double> watts = volts.thenCombine(amps, (v, i) -> v * i);
// No get() between submissions. Both reads can now progress.

exceptionally supplies a recovery value; handle transforms either success or failure; whenComplete observes an outcome, but can itself introduce a failure. join() blocks and exposes exceptional completion through CompletionException; get() uses checked ExecutionException. A recovery value should not disguise a failed safety measurement.

CompletableFuture.cancel(true) marks exceptional completion with CancellationException; its interrupt flag does not control the underlying computation. It is not a general upstream or sibling cancellation mechanism. Design the operation’s cancellation separately.

import java.util.concurrent.*;
/** Java 8+. Dedicated executor for blocking instrument simulations. */
public class CompositionLab {
    static double read(double value) {
        try { Thread.sleep(200); return value; }
        catch (InterruptedException ex) {
            Thread.currentThread().interrupt(); throw new CompletionException(ex);
        }
    }
    public static void main(String[] args) {
        ExecutorService io = Executors.newFixedThreadPool(3);
        try {
            CompletableFuture<Double> v = CompletableFuture.supplyAsync(() -> read(5.0), io);
            CompletableFuture<Double> i = CompletableFuture.supplyAsync(() -> read(0.2), io);
            // Register the race before waiting for dependent results.
            CompletableFuture<Object> firstTerminal = CompletableFuture.anyOf(v, i);
            CompletableFuture<Double> calibrated = v.thenApply(volts -> volts * 1.001);
            CompletableFuture<Double> power = calibrated.thenCombine(i, (volts, amps) -> volts * amps);
            CompletableFuture<Double> followup = calibrated.thenCompose(volts ->
                CompletableFuture.supplyAsync(() -> read(volts + 0.01), io));
            // A raw value alone does not identify which instrument produced it.
            System.out.println("First observed terminal value: " + firstTerminal.join());
            CompletableFuture.allOf(power, followup).join();
            System.out.println(power.join() + " W; followup " + followup.join());
            System.out.println(CompletableFuture.<Double>supplyAsync(() -> {
                throw new IllegalStateException("Simulated failure");
            }, io).exceptionally(ex -> Double.NaN).join());
        } finally { io.shutdown(); }
    }
}

04 / A DIFFERENT ROUTE TO SCALABILITY

Keep the blocking style. Make the waiting thread cheaper.

Java virtual threads became final in Java 21. A platform thread is tied to an OS thread. A virtual thread is scheduled by the JVM onto carrier threads and can unmount during supported blocking operations, freeing its carrier for other work. This scales large numbers of waiting operations; it does not make an FFT run faster or remove device bandwidth limits. Native calls and runtime-specific pinning behavior require care.

Java virtual thread

Preserves a thread-oriented, blocking-style call stack. The runtime can suspend that virtual thread while supported I/O waits.

C# asynchronous I/O

An async method suspends via a compiler-generated state machine. The pending operation is represented by a Task; no dedicated blocked thread is inherently required.

Complete Java 21 program · VirtualLab.java
import java.util.concurrent.*;
/** Java 21+, stable virtual threads; no preview APIs. */
public class VirtualLab {
    public static void main(String[] args) throws Exception {
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            var v = executor.submit(() -> { Thread.sleep(2000); return 5.0; });
            var i = executor.submit(() -> { Thread.sleep(2000); return 0.2; });
            System.out.println(v.get() * i.get());
        } // Waits for tasks. This is not a fail-fast sibling-cancellation policy.
    }
}

Structured concurrency is about ownership

Related work belongs to a scope: start children, join their outcomes, and finish their lifetimes before leaving. A scope’s policy can propagate failure and request cancellation of siblings. Cancellation still relies on cooperation. Merely using a virtual-thread executor does not choose a fail-fast policy.

Java 26 used the sixth preview. Examples written for older previews may not compile against a newer one. 05 / .NET’S EVENTUAL OUTCOME

A Task is an operation, not a thread.

The Task Parallel Library arrived with .NET 4 (2010); C# 5 added async/await (2012). Task<T> represents one eventual typed result, fault, or cancellation. A non-generic Task represents completion without a result value. Tasks can represent CPU work, network I/O, a timer, or an externally completed promise.

Task<double> measurement = MeasureVoltageAsync();
DoOtherWork();
double voltage = await measurement;

Calling an ordinary async method starts executing its body synchronously until it reaches an incomplete await. The returned task is usually already in progress; awaiting it observes and composes its outcome. There are exceptions to “tasks start automatically”: explicitly constructing new Task(...) creates an unstarted task. Prefer normal async APIs or Task.Run rather than that constructor.

No return value does not mean nothing to observe. A Task tells you when an action has finished and whether it succeeded. Channels carry items; completion-only Tasks can represent the lifetime of an entire producer or consumer loop.

06 / THE CENTRAL IDEA

Save the method’s place. Give the thread back.

Consider a user clicking “Measure.” The method begins on the UI thread, sends a command, and receives a task representing the pending reply. At await, the generated code checks whether the awaiter is already complete. If it is, execution continues inline. If not, it records the method’s state and arranges a continuation, then returns control to the caller.

The compiler transforms locals and control flow into a state machine. On completion, the continuation resumes at the next state, retrieves the result or throws the operation’s exception, and executes the next source statement. The continuation is not a second invocation of the entire method.

Experiment 4 · Follow one await

An actual asynchronous socket or OS I/O implementation can arrange completion notification without reserving a worker to wait. An API named Async can also wrap blocking native calls on a worker; inspect the implementation and driver contract. The keyword alone cannot guarantee nonblocking I/O.

Where does the continuation run?

By default, Task await can capture a suitable SynchronizationContext (for example, a desktop UI context), or a non-default TaskScheduler. The UI context posts the continuation back to its UI thread. In a console application or typical ASP.NET Core request, there usually is no such context; continuation placement is then governed by task completion and scheduling, often on the thread pool. It is not a guarantee of a new thread, or even a different thread.

Reusable library code that does not need a caller’s context often uses await operation.ConfigureAwait(false). This avoids requesting that context for that await. It does not force a thread switch, suppress all ExecutionContext flow, or make blocking safe everywhere. UI code that updates controls normally needs its UI context.

// I/O: use the asynchronous operation directly.
string text = await httpClient.GetStringAsync(uri, token);
// CPU: optionally offload substantial work to keep a UI responsive.
Spectrum result = await Task.Run(() => ComputeFft(samples), token);

Task.Run queues work to the thread pool. Its token can prevent work that has not started; the calculation itself must check cancellation to stop after it starts. Wrapping every async I/O call in Task.Run adds scheduling overhead without solving an I/O problem. Wrapping a blocking legacy driver is sometimes a containment strategy, but the worker remains occupied and cancellation needs driver support.

Can I forget to wait?

Yes. A Task is a handle, not an automatic synchronization barrier. Calling an ordinary C# async method begins executing it; keeping or ignoring the returned Task does not wait for completion. Someone must await it, return it to a caller who will observe it, or otherwise own its completion and failures.

An easy instrument-control mistake

meter.ConfigureAsync(config, token); // Completion is ignored.
double voltage = await meter.MeasureAsync(token);
// Acquisition may begin before configuration completes.
await meter.ConfigureAsync(config, token);
double voltage = await meter.MeasureAsync(token);

The first version is not made correct by the fact that ConfigureAsync was called first. Only its completion establishes that configuration is ready. A driver may serialize its own session, but callers should follow the explicit API contract rather than assume that hidden serialization supplies every required dependency.

What does the compiler catch?

C# issues warning CS4014 for many unawaited calls, but this is not a guarantee that every Task will be observed. Assigning the Task to a variable or explicitly discarding it can avoid that warning:

Task pending = meter.ConfigureAsync(config, token);
// Legal: the programmer can still forget to observe pending.

_ = meter.ConfigureAsync(config, token);
// Explicit discard: no waiting, cancellation, or error handling is added.

An unobserved operation may continue, fail without its caller handling the failure, or outlive resources it needs. Discarding the handle does not cancel it. Intentionally starting background work requires an owner that tracks completion, handles errors, and coordinates shutdown. Treat CS4014 as an error in builds if appropriate, and use analyzers to catch more patterns; neither replaces ownership design.

You do not have to await immediately. Starting independent measurements and awaiting Task.WhenAll later is deliberate concurrency. Returning a Task from a non-async forwarding method also legitimately transfers observation to its caller. The mistake is losing responsibility for the operation, not merely leaving off await at one particular call site.

The classic deadlock

A UI handler calls ReadAsync().Result. ReadAsync awaits incomplete I/O and captures the UI context. The handler blocks the UI thread waiting for the result. I/O completes, but its continuation needs that same UI thread. Neither can proceed. Use await through the caller chain. On a server without that context, blocking can still exhaust workers even without this exact deadlock.

Async changes how a method waits. It neither guarantees concurrency nor creates a thread.

using System;
using System.Diagnostics;
using System.Linq;
using System.Threading;
using System.Threading.Tasks;

public class BrowserLab
{
    public static async Task Main()
    {
        bool concurrent = true; // false: await each acquisition before starting the next
        bool failCounter = false; // true: the counter times out after 1.2 s
        int cancelAfterMs = 0; // 0: no deadline; try 800 for cooperative cancellation
        using var cancel = new CancellationTokenSource();
        if (cancelAfterMs > 0) cancel.CancelAfter(cancelAfterMs);
        var clock = Stopwatch.StartNew();
        void Log(string message) => Console.WriteLine($"{clock.Elapsed.TotalSeconds:F3}s | {message}");
        var devices = new[]
        {
            new Instrument("DMM", "DC voltage", 5.01, "V", 2000),
            new Instrument("Counter", "frequency", 1000, "Hz", failCounter ? 1200 : 2000, failCounter),
            new Instrument("Scope", "peak-to-peak voltage", 2.0, "Vpp", 2000)
        };
        Task<double[]>? all = null;
        try
        {
            if (concurrent)
            {
                // Calling MeasureAsync starts each operation up to its first await.
                var pending = devices.Select(d => d.MeasureAsync(Log, cancel.Token)).ToArray();
                all = Task.WhenAll(pending); // Does not cancel siblings on failure.
                double[] values = await all;
                Log($"All results: {string.Join(", ", values)} (V, Hz, Vpp)");
            }
            else
            {
                foreach (var device in devices)
                    await device.MeasureAsync(Log, cancel.Token);
            }
        }
        catch (OperationCanceledException) { Log("Cancelled cooperatively."); }
        catch (Exception ex)
        {
            Log($"await threw {ex.GetType().Name}: {ex.Message}");
            if (all?.Exception is { } aggregate)
                Log($"WhenAll retained {aggregate.InnerExceptions.Count} fault(s).");
        }
        finally { Log("Cleanup: all started calls observed; no physical outputs were enabled."); }
    }
}

TPL Dataflow: give the work a route.


Our channel example already has the essential pieces: a bounded queue, several consumer loops, and tasks that tell us when those loops finish. Now suppose every DMM reading must be calibrated, checked, and recorded. Each step has a different concurrency limit. We could connect several channels and write the coordination ourselves. TPL Dataflow packages those queues, processing delegates, scheduling policies, and completion tasks into composable blocks. It builds on tasks and async/await; it does not replace them.


Dataflow emerged in the .NET 4.5 era (2012; public previews in 2011). It is an established library, not a new C# language feature. This lesson targets modern .NET: System.Threading.Tasks.Dataflow is included in .NET 6 and later, including our .NET 8 companion and bundled .NET 10 browser runtime. .NET Framework/.NET Standard projects use the NuGet package. The most elegant starting point: a consumer pool in one block


An ActionBlock<T> accepts messages and invokes your delegate for each one. If the delegate returns a Task, the block tracks it until it completes. Three asynchronous operations can be in flight without dedicating three threads to their waiting. No explicit list of idle consumers is needed.


using System;
using System.Threading.Tasks;
using System.Threading.Tasks.Dataflow;

// Three interchangeable asynchronous consumers, managed by one block.
var writers = new ActionBlock<int>(async reading =>
{
    await Task.Delay(200); // Simulated file write; no actual file in this demo.
    Console.WriteLine($"Recorded reading {reading}");
}, new ExecutionDataflowBlockOptions
{
    MaxDegreeOfParallelism = 3,
    BoundedCapacity = 4 // Includes active delegate calls, not four extra slots.
});

for (int reading = 1; reading <= 12; reading++)
{
    if (!await writers.SendAsync(reading))
        break; // Declined: observe Completion below for the block's outcome.
}
writers.Complete(); // No more input; drain accepted work on normal completion.
await writers.Completion; // A Task: all writes finished, or failure observed.
Console.WriteLine("All writes finished.");



SendAsync returns a Task<bool> for admission: true means the block accepted the message. It does not mean the file was written. Completion is a different Task: it describes the entire block's lifetime. This is the same useful “just tell me it finished” abstraction we used for file writes—no dummy result value is needed.


Complete() requests the end of input; it does not wait. On the successful path, accepted messages finish before Completion succeeds. On a fault or cancellation path, queued work may be discarded. The compact example has no external cancellation or fallible producer; the supervised example below adds both lifetime coordination and injected sink failure. It still offers no transaction, rollback, retry, or durable-delivery guarantee.

Backpressure is an admission policy, not a magic memory limit


Post(item) returns immediately with a Boolean. A full or closed block can decline it; ignoring false silently loses the intended submission. await SendAsync(item, token) allows a bounded target to postpone acceptance. It can return false if the target declines permanently, or throw when the send is cancelled. Always handle the result. Cancelling a pending send does not undo an item that was already accepted.


For an execution block, bounded capacity accounts for work in flight, not just messages visibly waiting in its input queue. A transform may also retain completed output until downstream accepts it. Thus capacity four with concurrency three does not mean four waiting plus three active. With ordering enabled, completed later results can occupy capacity behind a slow earlier result.


Our producer awaits each send before submitting another, leaving at most one pending offer outside the first block. Launching a million SendAsync calls and collecting their tasks would allocate a million pending operations despite bounded blocks. Message counts are not byte budgets: a single waveform might contain megabytes, and delegate-local allocations also count toward application memory.


Observe “Offer” and “Accepted” timestamps in the log. A gap means admission waited. No single gap duration is guaranteed; scheduling and runtime load affect it. SendAsync contract · BoundedCapacity.



Concurrency, ordering, and thread safety are separate choices


The default execution-block degree is one. Setting MaxDegreeOfParallelism = 3 allows up to three active delegate operations, subject to input and capacity; it neither reserves three dedicated threads nor promises simultaneous execution. Async I/O can overlap while threads do other work. CPU-bound delegates need actual execution resources to gain parallel speedup.


EnsureOrdered = true (the default) preserves transform output order even if delegates finish out of order. Reading 2 can be calibrated before reading 1 but withheld until reading 1's output is available. This is head-of-line blocking. Setting it false permits earlier emission of ready outputs; it does not guarantee a particular permutation. Include sequence IDs when order matters to a later stage.


Ordered output does not serialize effects inside concurrent delegates. An ActionBlock with concurrency three can finish writes out of order; EnsureOrdered does not turn its side effects into a transaction. Our serial recorder owns its List, which is read only after all owned tasks finish. Keep a single instrument session serial, or enforce its documented concurrency contract. Use immutable readings between stages, and do not assume copying a reference isolates mutable buffers.

Completion flows downstream. Failure ownership must cover the whole network.


  1. The producer submits all requests and calls Complete on the head.
  2. The head finishes accepted work and forwards its outputs before normal completion.
  3. Links with PropagateCompletion request completion of their target when the source completes; faults also propagate downstream.
  4. The owner awaits completion tasks to know when the entire operation has ended.


The propagation option is false by default. It is directional: a recorder failure does not automatically cancel acquisition. A bounded upstream transform could keep output that nobody accepts, preventing its completion while the producer waits for capacity. Awaiting WhenAll does not solve this dependency cycle.


Our SuperviseAsync wrappers watch each block independently. A fault or cancellation requests the shared stop token, including pending sends and cooperative delegate delays. We then await every owned task before leaving the scope. The aggregate retains faults even when sibling tasks are cancelled; individual terminal states need not all match. These wrappers do not preempt a delegate that ignores cancellation. Production hardware still needs timeout/abort/recovery policy and finally-based safety cleanup.


Completion is a Task: you can store it, pass it, or await it from multiple observers. Awaiting it does not consume a message. ReceiveAsync on an ordinary queue-like block, by contrast, consumes an output. Forgetting to await block completion can let your application exit before accepted work finishes or hide faults.


For fan-in (two sources linked to one target), do not blindly propagate completion from both: the first completed source could close the target while the other is still sending. Give a coordinator ownership of both sources, complete the shared target after both finish successfully, and define a failure policy that also releases blocked producers. Similarly, dispose links only after their intended lifetime; unlinking an undrained source can strand its output. Propagation contract.



Routing is not broadcasting


Connecting an ordinary TransformBlock or BufferBlock to two targets normally routes each message to one accepting target. This can distribute work; it is not a guarantee of fair round-robin scheduling. Filtered links need a destination for every possible message or an explicit discard policy, otherwise unmatched output can stall the source. Use a final NullTarget only when dropping those messages is intended and documented.


A BroadcastBlock retains the current value and offers it to subscribers, replacing it as newer values arrive. Slow subscribers must not rely on receiving the full history. For an audit recorder and an analyzer that both require every sample, use an explicit fan-out stage that awaits acceptance by both branches, with a bounded queue on each and shared failure ownership. Even then, one branch may accept before the other fails: this is not atomic delivery. Durable retry/idempotency needs an additional design. BroadcastBlock contract.



Test contracts, not a lucky schedule


For the simple consumer block, test that every accepted ID is processed once on the successful path and that the active delegate count never exceeds its limit. For a bounded block, hold its first delegate at a TaskCompletionSource gate, fill its capacity, and assert that another SendAsync remains pending; release the gate and await admission. No stopwatch or arbitrary sleep is needed.


For ordered transforms, hold item 1 while allowing item 2's delegate to finish. Verify that output remains unavailable until item 1 is released; repeat with EnsureOrdered false and verify item 2 can emerge first. For lifecycle supervision, inject a sink exception while the source is waiting for capacity, then verify that the producer and all block completion tasks reach terminal states. A generous watchdog diagnoses a hang; it is not proof of a performance requirement. See downloadable DataflowTests.cs for executable gated tests.

Control completion instead of guessing timing. Use incomplete Tasks as gates. Explicitly release an operation when the test needs it to complete; do not sleep for 100 ms and hope the scheduler has reached the right point.

A deterministic overlap test


The following xUnit/NSubstitute test uses the lesson's Patterns.DifferenceAsync. Each substitute signals that it was called, then returns a still-pending Task. The test waits until both calls have begun before releasing either reading. A mistakenly sequential implementation cannot reach that checkpoint. Both completion orders must produce 5 − 3 = 2.


Gate<T>() creates a TaskCompletionSource<T> with TaskCreationOptions.RunContinuationsAsynchronously. This prevents SetResult from directly executing consumer continuations inline; it does not force a particular thread or completion order.


    [Theory]
    [InlineData(true)]
    [InlineData(false)]
    public async Task Independent_measurements_overlap_and_allow_either_completion_order(bool firstFinishesFirst)
    {
        var first = Substitute.For<IDigitalMultimeter>();
        var second = Substitute.For<IDigitalMultimeter>();
        var firstStarted = Gate<bool>();
        var secondStarted = Gate<bool>();
        var firstResult = Gate<double>();
        var secondResult = Gate<double>();
        first.MeasureAsync(Arg.Any<CancellationToken>()).Returns(_ => {
            firstStarted.TrySetResult(true);
            return firstResult.Task;
        });
        second.MeasureAsync(Arg.Any<CancellationToken>()).Returns(_ => {
            secondStarted.TrySetResult(true);
            return secondResult.Task;
        });

        Task<double> run = Patterns.DifferenceAsync(first, second, default);
        try
        {
            // Both calls must begin while neither result has been released.
            // Five seconds is a hung-test safeguard, NOT a performance assertion.
            await Task.WhenAll(firstStarted.Task, secondStarted.Task)
                .WaitAsync(TimeSpan.FromSeconds(5));
            Assert.False(run.IsCompleted);
            if (firstFinishesFirst) firstResult.SetResult(5.0);
            else secondResult.SetResult(3.0);
            Assert.False(run.IsCompleted); // One result is still required.
            if (firstFinishesFirst) secondResult.SetResult(3.0);
            else firstResult.SetResult(5.0);
            Assert.Equal(2.0, await run.WaitAsync(TimeSpan.FromSeconds(5)));
        }
        finally
        {
            // Release test-owned gates even when an assertion fails.
            firstResult.TrySetResult(5.0);
            secondResult.TrySetResult(3.0);
            try { await run.WaitAsync(TimeSpan.FromSeconds(5)); }
            catch { /* Preserve the original test failure. */ }
        }
    }



A test timeout is a safeguard, not evidence of concurrency. The proof here is that both invocation signals arrive while both result gates remain closed. The five-second WaitAsync only prevents a broken implementation from hanging the test indefinitely. It does not cancel the underlying operation; finally releases the test-owned gates and attempts to drain the run. For arbitrary hung drivers, isolation and a runner-level timeout remain necessary.


Write asynchronous tests as async Task and await the operation and asynchronous exception assertions. Avoid async void tests, forgotten awaits, and blocking Result/Wait calls. Await the whole operation before final interaction assertions so late failures are observed. A single pending-state assertion is a checkpoint, not an exhaustive proof over every possible scheduler interleaving.


These controlled unit tests verify orchestration. They do not establish hardware timing, transport correctness, or thread safety under every race. Use driver integration tests for protocol behavior, controlled or virtual time for timeout logic when the implementation accepts a clock, and targeted stress tests for shared-state races. A performance benchmark is a separate test with measured timing requirements.

/// <summary>Owns run tasks and attempts output disable, including after startup failure.</summary>
public sealed class ExperimentRunner(IGenerator generator, IDigitalMultimeter meter)
{
    private static readonly ActivitySource Activities = new("AsyncLesson.Experiments");
    public async Task<ExperimentResult> RunAsync(IEnumerable<double> frequencies, CancellationToken token)
    {
        var points = new List<Point>();
        string state = "Created";
        string? error = null, cleanupError = null;
        using var activity = Activities.StartActivity("frequency-response");
        void Log(string next) {
            state = next;
            Console.WriteLine(JsonSerializer.Serialize(new { state, count = points.Count, at = DateTimeOffset.UtcNow }));
        }
        Log("Created");
        try
        {
            Log("Startup");
            token.ThrowIfCancellationRequested();
            // Async wrappers capture even synchronous implementation failures as Tasks.
            // Both started children are drained before cleanup can touch their sessions.
            async Task ConfigureGeneratorAsync() => await generator.ConfigureAsync(token);
            async Task ConfigureMeterAsync() => await meter.ConfigureAsync(new(10, 0.02), token);
            await Task.WhenAll(ConfigureGeneratorAsync(), ConfigureMeterAsync());
            token.ThrowIfCancellationRequested();
            await generator.EnableAsync(token);
            Log("Running");
            foreach (var frequency in frequencies)
            {
                token.ThrowIfCancellationRequested();
                await generator.SetFrequencyAsync(frequency, token);
                await Task.Delay(20, token); // Explicit illustrative settling policy.
                double output = await meter.MeasureAsync(token);
                const double input = 1.0; // Simulated known source; real work measures/calibrates it.
                if (output <= 0) throw new InvalidOperationException("Positive RMS voltage required");
                points.Add(new(frequency, input, output, 20 * Math.Log10(output / input)));
                Console.WriteLine(JsonSerializer.Serialize(new { kind = "point", point = points[^1] }));
            }
            state = "Completed";
        }
        catch (OperationCanceledException) when (token.IsCancellationRequested) { state = "Cancelled"; }
        catch (Exception ex) { state = "Failed"; error = ex.ToString(); }
        finally
        {
            string outcome = state;
            Log("Cleanup");
            // A cancelled run token must not suppress the safety cleanup attempt.
            using var cleanup = new CancellationTokenSource(TimeSpan.FromSeconds(2));
            try { await generator.DisableAsync(cleanup.Token); }
            catch (Exception ex) { cleanupError = ex.ToString(); outcome = "Failed"; }
            Log(outcome);
        }
        return new(state, points, error, cleanupError);
    }
}

    }

public static class Patterns
{
    public static async Task<double> DifferenceAsync(IDigitalMultimeter a, IDigitalMultimeter b, CancellationToken token)
    {
        // Capture synchronous driver throws as faulted Tasks, so every started child is drained.
        async Task<double> ReadAsync(IDigitalMultimeter device) => await device.MeasureAsync(token);
        Task<double> first = ReadAsync(a);
        Task<double> second = ReadAsync(b);
        double[] results = await Task.WhenAll(first, second);
        return results[0] - results[1];
    }
    public static async Task<double> WithTimeoutAsync(IDigitalMultimeter meter, CancellationToken user)
    {
        using var deadline = CancellationTokenSource.CreateLinkedTokenSource(user);
        deadline.CancelAfter(TimeSpan.FromSeconds(3));
        try { return await meter.MeasureAsync(deadline.Token); }
        catch (OperationCanceledException) when (!user.IsCancellationRequested && deadline.IsCancellationRequested)
        { throw new TimeoutException("Measurement exceeded its cancellation budget"); }
    }
    public static async Task<double> BoundWaitAsync(IDigitalMultimeter meter, CancellationToken user)
    {
        using var operation = CancellationTokenSource.CreateLinkedTokenSource(user);
        Task<double> pending = meter.MeasureAsync(operation.Token);
        try { return await pending.WaitAsync(TimeSpan.FromSeconds(3), user); }
        finally {
            if (!pending.IsCompleted) operation.Cancel();
            // Drain can outlive three seconds; no generic safe forced Task abort exists.
            try { await pending; } catch (Exception) { /* Preserve original wait failure. */ }
        }
    }
}

Practical failure rules
  • Task-returning async methods normally store body failures in their returned task. Non-async wrappers can throw before returning a task, so partial-start failures also need ownership handling.
  • Use async Task for composable operations. Reserve async void for event handlers that require it; callers cannot await or normally catch its asynchronous failures.
  • Never infer success from IsCompleted alone; terminal includes cancelled and faulted.
  • A completed task can be awaited more than once. A source-backed ValueTask generally cannot.
  • Use an explicit result type when “failed measurement” is a normal domain outcome; do not silently substitute zero volts.

Simultaneous execution of computations.
Partial order
Required before/after relationships that leave independent events unordered.
Race
Behavior influenced by timing between operations; not every nondeterministic order is a bug.
State machine
Stored execution state and transitions; the compiler uses one to preserve an async method across suspension.
Structured lifetime
A scope owns its child operations and accounts for them before leaving.
SynchronizationContext
An abstraction for dispatching continuations to a host’s execution environment, such as a UI thread.
Thread pool
A runtime-managed set of reusable worker threads.
Timeout
A duration limit on an operation or a particular wait; specify which.
Virtual thread
A JVM-managed thread multiplexed onto carrier threads.
You now have three separate questions to ask of every async design: What can overlap? Who owns each operation? What must still happen when it fails?
