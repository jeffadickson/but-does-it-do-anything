Inversion of Control: who builds, and who calls?

From pre-Spring frameworks to Spring XML, Java annotations, and modern C#/.NET. A practical investigation of where control moves—and when that is worth doing.

The caller lets go
New hands assemble the parts
Choices bloom at dawn

v1.0.0~35–45 minutesOffline conceptual simulation

What you will be able to do

Explain the different meanings of inversion; replace tightly coupled construction with manual constructor injection; choose whether a container is warranted; recognize ownership and lifetime bugs; and locate where Spring and .NET moved composition.

Prerequisites: interfaces, constructors, simple unit tests. Platform: any modern browser for the interactive model; the copied Java and C# listings require their respective SDKs/framework dependencies for real execution.

Execution honesty: The lifetime and design experiments below execute JavaScript models in your browser. They do not compile Java, invoke Spring, or run the .NET DI container. Code listings are reference examples for external use.

1. A reasonable beginning: construct what you need

Imagine a checkout service that charges a card. There is exactly one gateway today. Direct construction is simple, readable, and initially correct.

public sealed class CheckoutService
{
    private readonly StripeGateway gateway = new();
    public string Checkout(decimal amount) => gateway.Charge(amount);
}
public sealed class StripeGateway
{
    public string Charge(decimal amount) => $"charged {amount:C}";
}

The new requirement: run a test without charging a real card, and select an alternate gateway in another environment. A hard-coded new StripeGateway() forces production construction inside the business object; substituting a fake requires modifying code or reaching for awkward seams. The flaw is not new itself, but placing a variable policy decision in the wrong class.

2. Inject a dependency without a framework

Put the business service in control of the payment decision, not construction. The caller supplies a compatible dependency when the object is created. This is constructor injection; it requires no container.

public interface IPaymentGateway { string Charge(decimal amount); }
public sealed class CheckoutService
{
    private readonly IPaymentGateway gateway;
    public CheckoutService(IPaymentGateway gateway) =>
        this.gateway = gateway ?? throw new ArgumentNullException(nameof(gateway));
    public string Checkout(decimal amount) => gateway.Charge(amount);
}
public sealed class FakeGateway : IPaymentGateway
{
    public int Calls { get; private set; }
    public string Charge(decimal amount) { Calls++; return "approved"; }
}
// Composition root: choose and construct dependencies here.
var fake = new FakeGateway();
var checkout = new CheckoutService(fake);
if (checkout.Checkout(12m) != "approved" || fake.Calls != 1)
    throw new Exception("Unexpected test result");

Now tests can pass a fake and verify one charge request. Real production composition can instead pass a real gateway. Notice that this example used ordinary constructors, not a container, reflection, attributes, or XML.

3. The history predates Spring

The broad idea is that an external mechanism calls application-specific code instead of the application running the entire sequence. Ownership of control flow can be inverted even when no dependencies are injected. Dependency injection is a narrower inversion of object assembly.

DateDocumented milestoneWhat it did—and did not invent
1970sEvent loops, parsers and framework-style programming existed before the DI vocabularyConceptual predecessors, not evidence for a single inventor or universal start date.
1983Richard Sweet's Mesa paper uses “Hollywood's Law,” as traced by FowlerEarlier expression of callback-driven control; not Spring-style container management.
1988Ralph Johnson and Brian Foote's Designing Reusable ClassesEarly published “inversion of control” terminology; Fowler cautions its provenance is not certain.
1990sObject-oriented frameworks, JavaBeans patterns and Apache Avalon-era approachesEstablished extension points and assembled component systems; no Spring invention claim.
2002Rod Johnson's enterprise Java work that informed SpringPrecursor to Spring's container, not the origin of inversion of control.
14 Jan 2004Martin Fowler publishes his DI/container analysis (revised 23 Jan)Clarifies and names dependency injection as a specific form of IoC, comparing service locator.
24 Mar 2004Spring Framework 1.0 finalPopularizes practical lightweight Java bean wiring with constructor/setter injection.
19 Nov 2007Spring 2.5Makes full annotation-driven DI and component autodetection mainstream within Spring.
16 Dec 2009Spring 3.0 GAIntegrates JavaConfig-style @Configuration and standardized JSR-330 injection support.
2010s–2020sSpring Boot, ASP.NET Core and .NET Generic Host ecosystemsExpand convention-based assembly and application lifecycle ownership; not a new invention of IoC.

Dating discipline: a publication date proves the documented terminology or product milestone, not necessarily the first-ever use of a design principle. See original/official sources below.

4. From Spring XML to Java configuration

Spring 1.x: declarative XML wiring

Object construction moves out of the service and into an external bean definition. This is illustrative Spring-style 1.x XML; actual runnable projects require Spring jars, a configuration loader and the Java classes.

<beans xmlns="http://www.springframework.org/schema/beans">
  <bean id="gateway" class="demo.StripeGateway"/>
  <bean id="checkout" class="demo.CheckoutService">
    <constructor-arg ref="gateway"/>
  </bean>
</beans>

Tradeoff: changes to assembly may avoid recompiling the service, but XML needs correct names/types and can obscure dependencies when wiring becomes extensive. XML was an assembly mechanism, not the definition of DI.

Spring 2.5: component scanning and @Autowired

@Component
public class StripeGateway implements PaymentGateway {
    public String charge(int cents) { return "approved"; }
}
@Service
public class CheckoutService {
    private final PaymentGateway gateway;
    @Autowired // explicit in this era; modern Spring can omit on one constructor
    public CheckoutService(PaymentGateway gateway) { this.gateway = gateway; }
    public String checkout(int cents) { return gateway.charge(cents); }
}
// Enable component scanning in the Spring context.

Scanning reduces XML declarations but can hide how components are discovered; qualifiers or explicit beans matter when multiple implementations qualify.

Spring 3.0: @Configuration and @Bean

@Configuration
public class AppConfig {
    @Bean
    public PaymentGateway paymentGateway() { return new StripeGateway(); }
    @Bean
    public CheckoutService checkoutService(PaymentGateway gateway) {
        return new CheckoutService(gateway);
    }
}

Code-based configuration makes dependency assembly explicit and type-checked while keeping business classes plain. Spring Boot later added extensive defaults and auto-configuration, a separate shift from merely injecting dependencies.

5. Modern C#: a composition root with Microsoft.Extensions.DependencyInjection

The service stays framework-agnostic. The host owns startup and shutdown; registrations connect interfaces to implementations. The following is a complete console example with the Microsoft.Extensions.DependencyInjection package (the package version should be pinned in a real project).

using Microsoft.Extensions.DependencyInjection;
var services = new ServiceCollection();
services.AddSingleton<IPaymentGateway, FakeGateway>();
services.AddTransient<CheckoutService>();
using var provider = services.BuildServiceProvider(
    new ServiceProviderOptions { ValidateScopes = true, ValidateOnBuild = true });
var checkout = provider.GetRequiredService<CheckoutService>();
Console.WriteLine(checkout.Checkout(12m)); // approved

public interface IPaymentGateway { string Charge(decimal amount); }
public sealed class FakeGateway : IPaymentGateway
{
    public string Charge(decimal amount) => "approved";
}
public sealed class CheckoutService(IPaymentGateway gateway)
{
    public string Checkout(decimal amount) => gateway.Charge(amount);
}

External reproduction: dotnet new console; dotnet add package Microsoft.Extensions.DependencyInjection; replace Program.cs; dotnet run. This requires a compatible .NET SDK, package restoration and an internet connection for first restore. A production app normally uses the Generic Host rather than building many providers directly.

In ASP.NET Core, the framework also decides when to invoke endpoint/controller code. This is lifecycle IoC, distinct from assembling constructor arguments. A callback is one mechanism by which control can be inverted, but calling a callback doesn't by itself create DI.

6. Interactive lifetime and ownership lab

Transient creates a new instance per resolution. Scoped reuses one per scope (often one HTTP request). Singleton shares one per provider. Container-managed disposable transients can remain captured until their scope ends.

Start a scope to see instance IDs.

Disposal rule: in Microsoft DI, the provider disposes objects it constructs and owns when their scope/provider ends. A caller should not dispose an injected service; instances registered as externally constructed objects remain the caller's responsibility. Never let a singleton capture a scoped request service. Scope validation can catch such lifetime mismatches.

Configuration: inject typed options/configuration when appropriate; don't turn the service provider into an ad hoc string-keyed settings repository. Avoid fetching IServiceProvider inside every business method (service locator). Test: direct constructor tests with mocks/fakes are usually quicker and more focused than booting a container in every unit test.

7. Separate the five related ideas

ConceptPrecise meaning
Inversion of Control (IoC)A broad reversal of who directs a particular action or life cycle.
Dependency injection (DI)Dependencies are supplied to a component from outside rather than chosen internally.
DI containerAn optional general-purpose mechanism for composing and managing object graphs.
Dependency Inversion Principle (DIP)A design principle about high-level policy and low-level details depending on abstractions—not synonymous with DI.
Callback/framework lifecycleFramework invokes application hooks; may invert flow without performing DI.

When is a container worth it?

Choose manual construction for a small stable graph, short script, library, or isolated unit test. Choose a container when an application needs consistent wiring across many components, environment-specific implementations, scoped resources, interception or integration with hosting. A container does not repair unclear architectural boundaries; it can make them harder to see.

Common mistakes: injecting every tiny value or entity; hidden service locator calls; multiple root providers; wrong scoped/singleton pairings; assuming injection implies testability; ambient static state; disposing dependencies you don't own; using a mock to “prove” database integration; depending on scanning without checking registration; and treating IoC, DI and DIP as synonyms.

Decision experiment

Choose realistic requirements; the rule is a heuristic, not a framework benchmark.

8. Revisit the original checkout problem

The initial code was not wrong: it simply combined payment policy with the choice of gateway. Constructor injection fixes that seam without introducing a framework. Container-managed composition becomes useful only as the broader application's object graph, lifetimes and hosting obligations grow.

Further investigations: compare Spring Boot auto-configuration to explicit @Bean methods to understand defaults; build an ASP.NET Core integration test to see scopes in a real request; study factories for runtime arguments and IAsyncDisposable for resources requiring asynchronous shutdown.
