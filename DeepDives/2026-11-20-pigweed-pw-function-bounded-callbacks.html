The engineering decision

Use an inline-owning callable when work must survive the caller; borrow only within one synchronous call.

Pigweed's pw_function makes a common embedded design trade explicit: a callback is not merely a function address. It may own captured state, borrow someone else's state, or represent a single-use completion. Each choice has a different lifetime contract, storage bound, and failure mode.

0 heap allocations*For pw::InlineFunction / InlineCallback storage themselves; captured objects can still allocate internally.
3 lifetime patternsBorrow synchronously; own for later; consume exactly once.

Recommendation: Use pw::FunctionRef for non-retained visitors, pw::InlineFunction<Signature, N> for stored deterministic callbacks, and pw::InlineCallback for a completion that is consumed once. Reserve pw::DynamicFunction for explicitly permitted allocation domains. This is a candidate design for RISCue, not a claim it has been adopted there.

01 · Why callbacks are an embedded-systems problem

A plain function pointer is compact and predictable but cannot natively own a capturing lambda. std::function offers convenient type erasure but its capacity and spill-to-heap behavior are not part of a portable application-level bound. Many systems therefore invent parallel callback signatures, context-pointer trampolines, and ad hoc ownership rules.

Pigweed's design offers separate semantic types rather than relying on hope: FunctionRef borrows; InlineFunction owns in fixed internal storage; Callback consumes a callable; and DynamicFunction explicitly permits dynamic backing allocation. The precise distinctions matter more than a generic claim of “zero overhead.” [1–4]

In a deterministic RTOS or simulation engine, the key questions are: Can a callback outlive the producer's stack? Is capture size checked during compilation? Does a full work queue return a status or fail fast? Who records event order? What happens on a second completion? The wrapper answers only some of these.

The API reference defines InlineFunction and InlineCallback as aliases of the Fuchsia fit inline implementations. The default pw::Function inline capacity is generally one pointer, not “any small object.” Compile the real project configuration to establish it. [1, 2]

2026 update: pw::FunctionRef appeared in the April 2026 Pigweed changelog. May 2026 added lifetime-bound annotations so Clang can identify some temporaries that would dangle. An analyzer warning is useful evidence, not a replacement for a lifetime proof. [3, 4]

03 · Visual model: lifetime, ownership, and storage

Small-buffer optimization is not the same as bounded total system memory. The lambda itself might contain a pointer to heap memory, an owning container, or a reference to a short-lived stack object. A bounded callable only bounds where the callable object is stored.

04 · Example: a synchronous observer with no ownership transfer

Suppose a deterministic simulator walks a fixed event trace and offers a hook to count selected records. The visitor runs before Visit returns. That is a good FunctionRef boundary.

The temporary capturing lambda remains alive for the full function call. Its reference to matches is also valid throughout that call. Do not store a FunctionRef in an asynchronous task or active object's pending-work record unless the program separately proves the referenced callable outlives that storage.

Scheduling caveat: A visitor is just a synchronous call. It does not establish real-time safety if the visitor blocks, allocates, takes a mutex, throws, or mutates state with nondeterministic side effects.

06 · Example: single-use completion

Completions are often semantically different from subscriptions. A one-shot callback consumes its target after the first invocation, making accidental repeat completion visible as an invalid operation.

Null checks are essential where control flow may retry, cancel, or double-complete. A single-use wrapper does not itself resolve concurrent races: two threads can still observe a non-null object without a separately designed synchronization protocol. Nor is callback consumption equivalent to a requirements-level guarantee of exactly-once delivery under crashes or power loss.

07 · Application patterns for RISCue and active objects

Active-object events

Keep the event queue typed and fixed-capacity; use bounded callbacks at adapter boundaries rather than allocating a closure for each message. Define producer backpressure explicitly.

Hierarchical state machines

Prefer explicit event/state transition tables for core semantics. Use inline callables for replaceable entry/exit hooks or test seams when their lifetime is controlled.

Deterministic simulation

Use FunctionRef for in-step observers, InlineFunction for owned scheduled hooks, and record ordering separately. Same callback ≠ same replay across architectures.

Proven Pigweed integration: work queue

The pw_work_queue module actually queues pw_function::Closure for execution by a worker thread. Its official examples use WorkQueueWithBuffer<10>. The API offers PushWork, which returns RESOURCE_EXHAUSTED when full, and CheckPushWork, which crashes when the work cannot be queued. That is a real integration and a particularly useful contrast for RISCue. [5, 6]

Do not assume ISR eligibility from this article. The official work-queue documentation provides an interrupt-handler illustration and states thread/interrupt-safe APIs; practical ISR behavior still depends on the chosen Pigweed thread/notification backend, priorities, interrupt masking, object placement, and target architecture. Do not call ordinary stored lambdas from an ISR without reviewing their bodies.

For a RISCue event dispatcher, define queue capacity independently of callable capacity and attach trace IDs to typed events rather than to opaque callback addresses. A pointer address is not a portable or stable event identity.

The wrapper gives storage and lifetime semantics. It does not guarantee bounded execution time, absence of global allocator activity inside the callback, reentrancy, thread safety, or deterministic callback order.

09 · Integration: pin source, configure CMake, build with Ninja

Official Pigweed instructions show linking the pw_function CMake target. Pigweed's build documentation reports full Bazel support and partial CMake support; treat CMake as a qualifying integration, not as an automatically trivial header drop-in. Pin a revision rather than tracking a moving development branch. [1, 7, 8]

This is illustrative integration wiring, not a verified build recipe for every Pigweed revision. The full upstream setup can require dependencies/backends and a compatible toolchain before CMake configuration succeeds. For device builds, use a separate build tree and board toolchain. Record CMAKE_CXX_COMPILER_ID, version, target ABI, linker flags, and Pigweed SHA.

Configuration coherency is part of correctness

Pigweed documents build-time configurable inline storage and optional allocation. The April 2026 changelog introduces a PW_FUNCTION_CONFIG_HEADER override facility; verify the selected revision's exact config macro names and inclusion path. Do not combine separately compiled components with different callback type configurations: aliased template types and binary interfaces may become incompatible. [1–3]

10 · Designing a reproducible callback trace

A good simulation trace should not serialize callback storage or unstable addresses. Instead record explicit event identity, logical timestamp, sequence number, producer, and outcome. During replay, invoke the registered handler for that typed event. Handler registration and ordering become audited inputs to the experiment.

To qualify reproducibility, run a golden trace on the host and target using normalized serialized fields, then check bytewise equality (or an explicitly documented architecture-normalized comparison). Include simultaneous timestamps and multiple event producers; assert tie-break rules explicitly.

Compared with yesterday's Microsoft GSL report, this is not primarily a bounds-checking library: it is a callable lifetime and storage policy. 13 · Qualification campaign: what a green build must actually prove

  1. Pin source: record upstream SHA and all vendored/submodule revisions; review the actual fit implementation and license inventory.
  2. Positive and negative compile tests: exact-fit and oversized capture; over-aligned captures; move-only captures; no-copy guarantees; host and device compiler flags.
  3. Allocation instrumentation: override or intercept allocation entry points in controlled test binaries, warm up static initialization, invoke construction/move/call/destruction, and count allocations from captured object behavior separately.
  4. Lifetime checks: exercise by-reference captures with ASan/UBSan on host; enable Clang lifetime warnings; prohibit retained FunctionRef via review and static analysis.
  5. Failure contracts: death-test empty invocation and second invocation of a consumed callback. Do not run these death cases inside the primary long-lived simulator process.
  6. Concurrency: single-thread vs. multicore, callback reentrancy, ownership transfer, cancellations, and double-completion races; add TSAN tests where supported.
  7. Queue saturation: integrate PushWork with bounded queue size and assert RESOURCE_EXHAUSTED without silent loss; measure maximum queue depth.
  8. Timing and memory: compare function pointer, template, FunctionRef, and InlineFunction at -O2/-Os with LTO on selected targets. Record binary sections, object sizes, cycles distributions, and compiler disassembly. Do not label percentile timing a WCET bound.
  9. Replay: run the same fixed trace across different optimization levels and architecture targets; compare normalized event order and outcomes rather than pointer representations.
  10. Reproducibility: run CMake/Ninja from clean build directories; capture toolchain hashes and per-target Pigweed config. Disallow host-only heap fallback from hiding device compilation failures.

Exit criteria: no unexpected allocation in designated paths; every stored callback's capacity is compile-time bounded; lifetimes are explicit; callback-induced scheduling and failure modes are tested; no open critical difference between host and device behavior. A local compilation and hardware benchmark are not claimed in this article.

14 · Licensing, origin, and deployment decision

Pigweed's primary source tree identifies Apache License 2.0, not MIT. Apache-2.0 generally permits modification, redistribution and commercial use subject to attribution, license inclusion, notice handling and other conditions, and includes an express patent license subject to its terms. Source files carry Apache headers. Because pw_function relies on Fuchsia fit code, assess the actual checked-out third-party files, license/NOTICE material and transitive dependency inventory before distributing firmware or a library package. Do not assume the entire combined tree is under one license merely because the top-level Pigweed project is Apache-2.0. [9–11]

For allocation-free C++20 systems the benefit is compelling, but this is a conditional adoption: first prototype with FunctionRef at synchronous boundaries and explicit InlineFunction for one owner-managed callback. Move to generic work queues only after capacity, ISR, ordering, and shutdown semantics are specified.
