01 / Engineering verdict

Worth a bounded protocol prototype.

Recommendation: use boost::endian::endian_load and endian_store at serialization boundaries where binary formats are defined byte-by-byte. Keep buffers externally owned, validate lengths and field ranges, and compare with a hand-written or standard-library implementation before introducing another dependency.

02 / The failure that hides in plain sight

Is 0x01020304 stored as 01 02 03 04?

Sometimes. A big-endian representation places the most-significant byte first: 01 02 03 04. A little-endian representation places the least-significant first: 04 03 02 01. The integer value is identical; the byte sequence differs. A network packet or file format must prescribe one byte sequence independently of the CPU running the code. The official Boost.Endian documentation calls out portable binary exchange as its primary use. [1]

The critical distinction

std::uint32_t n = 0x01020304; defines a numeric value, not a portable on-wire byte sequence. Writing the four bytes of n with reinterpret_cast silently couples the format to the machine. Read and write by declared wire order instead.

03 / The library under the microscope

Three ways to express byte order

1. Conversion functions

native_to_big, big_to_native, endian_reverse. Useful when operating on native integer values. Caution: a converted integer is still an integer; its in-memory bytes require care.

2. Endian buffers

big_uint24_buf_t and related unaligned storage types encode a specified number of bits in a specified byte order. The library supports 1–8 octet buffers, including non-native widths. [2]

3. Explicit load/store

endian_store<T, N, order::big>(p, value) and its load counterpart operate on caller-owned bytes. This is the approach used below: explicit lengths, offsets and orders. [3]

The library is header-only and licensed under the Boost Software License 1.0. No runtime allocator, OS service, or linked Boost object library is required for the operations shown. Inclusion and dependencies still affect build integration. [4]

05 / Put the agreement in writing

A deliberate mixed-endian frame

This frame is made up for the lesson. The mixed order is intentional: it forces both orientations to be explicit and makes the golden-vector test meaningful. It is not a NASA, CCSDS, JPL or flight telemetry specification.

Offsets are measured in octets from the beginning of the frame. All fields are unaligned in the wire representation.
OffsetBytesFieldOrderChecks
0–12Magic 0xA65CBigExact match
21Versionn/aMust equal 1
31Flagsn/aBits 2–7 must be zero
4–74Sequence (uint32_t)BigFull 32-bit range
8–92Temperature (int16_t, 0.1 °C)Big−400 to +1250
10–112Samples (uint16_t)Little0 to 5000

The golden vector for sequence 0x01020304, temperature −125, 300 samples, flags 1 is A6 5C 01 01 01 02 03 04 FF 83 2C 01. Notice that the signed negative temperature is FF 83 and the little-endian 300 (0x012C) is 2C 01.

06 / Copy, compile, inspect

C++20 example: no allocator in the API

std::span carries a pointer and a length, while std::optional represents successful decoding or rejection. A single caller-owned std::array<unsigned char,12> suffices. Keep this example in a wire.hpp file (or a translation unit) and expose it only to the host tests until validated for the target.

#include <boost/endian/conversion.hpp>
#include <array>
#include <climits>
#include <cstddef>
#include <cstdint>
#include <optional>
#include <span>

static_assert(CHAR_BIT == 8);

namespace wire {
constexpr std::size_t size = 12;
constexpr std::uint16_t magic = 0xA65C;

struct Frame {
    std::uint32_t sequence;
    std::int16_t tenths_c;
    std::uint16_t samples;
    std::uint8_t flags;
    friend bool operator==(const Frame&, const Frame&) = default;
};

constexpr bool valid(const Frame& f) noexcept {
    return f.tenths_c >= -400 && f.tenths_c <= 1250 &&
           f.samples <= 5000 && (f.flags & 0xFCu) == 0;
}

inline bool encode(std::span<unsigned char> out, const Frame& f) noexcept {
    if (out.size() != size || !valid(f)) return false;
    using namespace boost::endian;
    endian_store<std::uint16_t, 2, order::big>(out.data(), magic);
    out[2] = 1;  // Protocol version
    out[3] = f.flags;
    endian_store<std::uint32_t, 4, order::big>(out.data() + 4, f.sequence);
    endian_store<std::int16_t, 2, order::big>(out.data() + 8, f.tenths_c);
    endian_store<std::uint16_t, 2, order::little>(out.data() + 10, f.samples);
    return true;
}

inline std::optional<Frame> decode(std::span<const unsigned char> in) noexcept {
    if (in.size() != size) return std::nullopt;
    using namespace boost::endian;
    if (endian_load<std::uint16_t, 2, order::big>(in.data()) != magic ||
        in[2] != 1) return std::nullopt;
    Frame f {
        endian_load<std::uint32_t, 4, order::big>(in.data() + 4),
        endian_load<std::int16_t, 2, order::big>(in.data() + 8),
        endian_load<std::uint16_t, 2, order::little>(in.data() + 10),
        in[3]
    };
    if (!valid(f)) return std::nullopt;
    return f;
}
}  // namespace wire

Why this is not a raw struct copy

No assumptions about padding, member ordering, native endianness or natural alignment leak into the wire representation. Every field has a documented width and offset. endian_load handles partial widths and sign extension; unlike casting a byte pointer to a uint32_t*, it does not assume that wire memory satisfies a CPU integer's alignment. [3]

07 / Tests, including tests that fail

Golden bytes are an executable requirement.

Tests reject short buffers, incorrect magic, unknown version, reserved flag bits, invalid sample counts and out-of-contract temperatures. A separate signed 24-bit test exercises the library's documented sign extension. This is test evidence, not a claim of embedded timing qualification.

#include "wire.hpp"  // Save the code above as wire.hpp; remove its duplicate includes.
#include <array>
#include <cstdio>

#define REQUIRE(expr) do { if (!(expr)) { \
    std::fprintf(stderr, "FAIL line %d: %s\n", __LINE__, #expr); \
    return 1; } } while (false)

int main() {
    using namespace wire;
    constexpr Frame original{0x01020304u, -125, 300, 1};
    constexpr std::array<unsigned char, size> golden{
        0xA6,0x5C, 0x01,0x01, 0x01,0x02,0x03,0x04,
        0xFF,0x83, 0x2C,0x01
    };
    std::array<unsigned char, size> bytes{};
    REQUIRE(encode(bytes, original));
    REQUIRE(bytes == golden);
    REQUIRE(decode(bytes).has_value());
    REQUIRE(*decode(bytes) == original);

    auto bad = bytes;
    bad[2] = 2; REQUIRE(!decode(bad));         // unknown version
    bad = bytes;
    bad[0] = 0; REQUIRE(!decode(bad));         // wrong magic
    bad = bytes;
    bad[3] = 0x80; REQUIRE(!decode(bad));      // reserved flag
    bad = bytes;
    bad[10] = 0xFF; bad[11] = 0x7F;
    REQUIRE(!decode(bad));                   // sample count > 5000
    REQUIRE(!decode(std::span<const unsigned char>(bytes.data(), 11)));
    REQUIRE(!encode(std::span<unsigned char>(bytes.data(), 11), original));
    REQUIRE(!encode(bytes, Frame{0, 1251, 0, 0}));
    const unsigned char signed24[]{0xFF, 0x00, 0x01};
    REQUIRE((boost::endian::endian_load<std::int32_t, 3,
             boost::endian::order::big>(signed24) == -65535));
    return 0;
}

Test integration note: the snippet above includes wire.hpp. The locally executed check used the same encoder and decoder combined in one source file, with the same behavioral assertions. As usual, add an include guard or #pragma once if saving wire.hpp as a separate reusable header.

Locally exercised

GCC 14.2.0, Boost 1.83, CMake 3.31.6 and Ninja 1.12.1. Release and Debug both compiled, and CTest passed (1/1 in each configuration) with -Wall -Wextra -Wpedantic -Werror -fno-exceptions -fno-rtti. Tests use explicit runtime checks, not assert, which disappears under NDEBUG.

Not established

Boost versions newer than 1.83 were not compiled here. Neither ARM target code, toolchain-specific builtins, worst-case execution time, flight allocation instrumentation, undefined-behavior sanitizers, nor deployed Github Pages rendering have been qualified.

08 / Evidence, not folklore

Who actually uses this API?

Verified source

Ceph · rbd-nbd

The Ceph repository's rbd-nbd.cc source includes boost/endian/conversion.hpp and calls big_to_native/native_to_big on request, reply, and network-block-device fields. This demonstrates a real source dependency; it is not evidence Ceph is allocation-free. [5]

Verified source

Boost.Unordered · UUID benchmark

The upstream UUID benchmark invokes store_little_u64 and load_little_u64 to convert byte sequences. This is a real developer/test use inside Boost, not a claim that the main hash-table runtime depends on Endian. [6]

What is not claimed

No repository inspection established Boost.Endian currently deployed aboard a particular spacecraft, inside RISCue, or in VeloSim. The official documentation's mixed-endian GIS example is a demonstration of handling a real file-format convention, not proof that a specific GIS product ships this library. [2]

09 / Make it reproducible

CMake, Ninja, package pinning

In the verified local experiment the Boost header was available under /usr/include. For portable builds, resolve a declared Boost package, pin a version in the build environment and link its header-only CMake interface target. This does not link a Boost binary library.

cmake_minimum_required(VERSION 3.20)
project(endian_lab LANGUAGES CXX)

# Pin and provision an approved Boost version in your build image.
find_package(Boost 1.83 CONFIG REQUIRED)
add_executable(endian_lab main.cpp)
target_compile_features(endian_lab PRIVATE cxx_std_20)
target_link_libraries(endian_lab PRIVATE Boost::headers)

enable_testing()
add_test(NAME endian_lab COMMAND endian_lab)

# On a Unix toolchain, optionally add -fno-exceptions -fno-rtti
# to this target after validating the rest of the application.
cmake -S . -B build-release -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build-release
ctest --test-dir build-release --output-on-failure

cmake -S . -B build-debug -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build-debug
ctest --test-dir build-debug --output-on-failure

To reproduce the single-file local experiment rather than the two-file excerpts, concatenate the implementation and test program into main.cpp (excluding the test's #include "wire.hpp"). A package found with Boost::headers must be supplied by your chosen Boost CMake integration; do not rely on an uncontrolled system version in a flight build.

Licensing

Boost Software License 1.0 (BSL-1.0), not MIT. Review notice/redistribution requirements with the actual source package and its dependency licenses. Library usage does not place your application under an open-source license. [7]

Toolchains

10 / Where it goes wrong

A byte-perfect parser is not yet a flight packet processor.

Hazard / tradeoffEngineering response
Truncated, oversized, or malicious packetCheck length before passing pointers to endian_load. The library reads exactly N bytes; it does not know total buffer length.
Undefined field meaning / reserved bitsVersion the contract; check magic, ranges, flags and unknown enum values explicitly.
Integrity and corruptionByte order provides no error detection, authentication, CRC, or FEC. Add protocol-appropriate integrity coverage and test it separately.
Object layout or unaligned accessPrefer explicit byte-pointer loads/stores; don't alias unaligned wire bytes as native typed pointers.
Signed or fractional telemetrySpecify signed representation, scaling, valid range and saturating/rejection policies; negative values here rely on the library's integer conversion semantics.
Static timing and memory evidenceHeader-only and inline do not imply constant-time execution or allocation-free entire call chains. Measure generated code and instrument hot paths on each real target.
Dependency footprintOn a small target, four explicit shifts may be easier to audit. Compare object code size and compiler intrinsics before standardizing on Boost.
Cross-language interoperabilityC# BinaryPrimitives.ReadUInt32BigEndian and WriteUInt16LittleEndian can encode the same declared wire contract; no Boost binary or managed dependency is required. Confirm with identical golden vectors.
11 / Engineering transfer

Where this could go next

Proposed, not implemented

RISCue / hardware adapters

Use the packet contract at an I/O boundary; hand the decoded typed event to a single-owner active object. A zero-copy wire reader is not inherently thread-safe and does not replace queue ownership rules.

Proposed, not implemented

VeloSim / deterministic replay

Keep a versioned byte trace with golden vectors so a Windows host and an embedded target decode identical event values, including signed and non-native-width fields.

Proposed, not implemented

SharpTestBench / property tests

Generate valid random frames with fixed seeds; assert encode→decode identity and identical bytes across compilers. Fuzz invalid lengths and reserved fields before hardware-in-the-loop work.

Recommended qualification experiment

  1. Freeze the format: document offsets, widths, order, signedness, limits, version and integrity layer in a requirements-controlled schema.
  2. Cross-check: compare Boost.Endian, manual shift-based codec and C# BinaryPrimitives against the same goldens (including boundary values and corruption).
  3. Instrument: measure CPU cycles, text size, stack peaks and allocations on the actual target, with optimization and exception/RTTI policy matching flight.
  4. Decide: adopt the library only when its auditability and portability justify build and qualification overhead.
