01 · Executive brief

Why this library deserves a bench test

Imagine one interrupt or dedicated producer task generating events, and one consumer task processing them. You want to pass an event without acquiring a mutex, allocating a node, or waiting for another thread to release a lock.

✅ A genuinely useful narrow primitive

boost::lockfree::spsc_queue<T, capacity<N>> places its bounded storage in the queue object. With a simple fixed-size T, push and pop have explicit success/failure paths and no growing heap buffer.

⚠️ Not an active-object message bus

Exactly one concurrent producer and one concurrent consumer may use a given instance. Two tasks plus an ISR all posting into one queue violates the central contract.

Recommendation: prototype it for dedicated 1:1 channels, not as a universal RISCue event mailbox. Its strongest feature is not maximum benchmark throughput; it is a restricted concurrency model simple enough to budget and test. The Boost documentation calls these operations wait-free, subject to hardware atomics and the behavior of T itself. [1] [2]

Evidence labels in this report: SOURCE VERIFIED means upstream documentation or inspected real project code; HOST TESTED means a test actually ran here; PROPOSED means an integration or engineering hypothesis, not adoption.
02 · Architecture

The ring is small. The concurrency contract is not.

Each successful push publishes the next element at the producer's write position; each successful pop consumes the oldest element at the consumer's read position. Both positions wrap around. Boost's implementation uses atomic indices and acquire/release synchronization so the consumer sees a completely published event. There is no per-operation lock or node allocation for a compile-time-sized queue. [1] [3]

Important distinction: Boost's internal ring can reserve a sentinel position to distinguish full from empty. The public capacity remains the requested N; it does not promise sizeof(queue) == N * sizeof(T). Cache-line separation, indices, and platform layout cost memory.

03 · API & correctness

Know precisely what is guaranteed

Operation / choiceBehaviorEngineering implication
capacity<N>Storage capacity chosen at compile time.Static memory budgeting; no queue-buffer growth at runtime.
push(event)true if inserted, false when full.Explicit backpressure policy required. No automatic overwrite.
pop(out)true if one oldest item delivered; false when empty.Consumer must handle empty without treating it as a fault.
read_available()Snapshot of occupancy.Useful diagnostics; do not use as a reservation or synchronization barrier.
reset()Clears ring state; documented as not thread-safe.Stop both contexts before resetting.
is_lock_free()Queries implementation's lock-free status.Necessary platform check, not proof of system-wide WCET.
Three ways to accidentally defeat the real-time story: (1) use std::string or another allocating T; (2) spin on a full queue inside a high-priority ISR; (3) use the same queue from multiple producers. “Wait-free queue operations” does not make arbitrary copy constructors, callbacks, logging, or scheduler behavior wait-free.

For the minimal example, Event is trivially copyable and has no dynamic members. The host compiler checks that property. The exact type and platform require review against the targeted Boost version: Boost 1.92 documents default-constructible, copyable-or-movable element requirements. [2]

05 · Tested C++20

A runnable capacity, wraparound and cross-thread probe

This is the exact source compiled in the local Linux validation environment. It makes no side-effecting calls inside standard assert macros, so its checks still execute under a Release build with NDEBUG. The threaded portion is a host stress smoke test; its retry-with-yield policy is intentionally unsuitable for a hard real-time ISR.

main.cpp · C++20 · tested on Boost 1.83
#include <boost/lockfree/spsc_queue.hpp>
#include <atomic>
#include <cstdint>
#include <iostream>
#include <thread>
#include <type_traits>

struct Event {
    std::uint32_t sequence{};
    std::uint16_t signal{};
    std::uint16_t value{};
};

static_assert(std::is_trivially_copyable_v<Event>);
using EventQueue = boost::lockfree::spsc_queue<
    Event, boost::lockfree::capacity<8>>;

#define REQUIRE(expr) do { \
    if (!(expr)) { std::cerr << "FAILED: " << #expr << '\n'; return 1; } \
} while (false)

int main() {
    EventQueue q;                       // Storage is fixed at construction.
    REQUIRE(q.is_lock_free());          // Check the tested host configuration.
    for (std::uint32_t i = 0; i < 8; ++i)
        REQUIRE(q.push(Event{i, 7, 42}));
    REQUIRE(!q.push(Event{99, 7, 42})); // Full: no growth, no overwrite.

    Event out{};
    for (std::uint32_t i = 0; i < 5; ++i) {
        REQUIRE(q.pop(out));
        REQUIRE(out.sequence == i);
    }
    for (std::uint32_t i = 8; i < 13; ++i)
        REQUIRE(q.push(Event{i, 7, 42})); // Wrap around.
    for (std::uint32_t i = 5; i < 13; ++i) {
        REQUIRE(q.pop(out));
        REQUIRE(out.sequence == i);
    }
    REQUIRE(!q.pop(out));                // Empty: explicit failure.

    // Host-only concurrency validation (not an RTOS integration example).
    EventQueue shared;
    constexpr std::uint32_t count = 200'000;
    std::atomic<bool> done{false};
    std::atomic<bool> ordered{true};
    std::atomic<std::uint32_t> received{0};
    std::thread consumer([&] {
        Event e{};
        std::uint32_t expected = 0;
        while (!done.load(std::memory_order_acquire) || !shared.empty()) {
            if (shared.pop(e)) {
                if (e.sequence != expected) ordered.store(false);
                ++expected;
            } else {
                std::this_thread::yield();
            }
        }
        received.store(expected, std::memory_order_release);
    });
    for (std::uint32_t i = 0; i < count; ++i) {
        while (!shared.push(Event{i, 7, 42}))
            std::this_thread::yield(); // TEST ONLY: not an ISR/flight policy.
    }
    done.store(true, std::memory_order_release);
    consumer.join();
    REQUIRE(ordered.load());
    REQUIRE(received.load() == count);
    std::cout << "PASS: capacity 8, overflow, wrap, FIFO, "
              << count << " cross-thread events; sizeof(queue)="
              << sizeof(EventQueue) << " bytes\n";
}

Design nuance: The queue has one thread performing all pushes, and a distinct thread performing all pops. The initial sequential checks are conducted before either thread starts; they exercise the public FIFO semantics without pretending to validate cross-core synchronization on their own.

06 · Integration

CMake + Ninja without a hand-written compiler command

Boost.Lockfree's SPSC header can be used without linking a separate Lockfree binary library. Here, Boost::headers supplies Boost headers and Threads::Threads supports the host test. Using CONFIG selects Boost's package configuration rather than relying on older FindBoost behavior in newer CMake versions. [6]

CMakeLists.txt
cmake_minimum_required(VERSION 3.21)
project(boost_spsc_probe LANGUAGES CXX)
find_package(Boost 1.70 CONFIG REQUIRED)
find_package(Threads REQUIRED)
add_executable(boost_spsc_probe main.cpp)
target_compile_features(boost_spsc_probe PRIVATE cxx_std_20)
target_link_libraries(boost_spsc_probe PRIVATE Boost::headers Threads::Threads)
enable_testing()
add_test(NAME boost_spsc_probe COMMAND boost_spsc_probe)
Configure, build, test
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
ctest --test-dir build --output-on-failure

For embedded deployment: add the Boost headers as an audited dependency, use the cross-compiler/toolchain file, and test your actual hardware's atomics, ABI, interrupt model, stack budget, linker map, latency and failure handling. This host test does not establish bare-metal compatibility.

09 · Suggested engineering applications

Where the pattern might pay for itself

RISCue: dedicated diagnostic channel PROPOSED

A single event producer feeds one diagnostic consumer. Start with a fixed POD event, an explicit drop counter, a named capacity and a test demonstrating full/empty conditions. Do not repurpose it when many active objects share the producer role.

VeloSim: traced handoff PROPOSED

Connect one simulation event stream to one recorder. Record sequence numbers and drops, then replay the resulting stream deterministically. Arrival timing between host threads is not itself deterministic.

A tiny interface for a flight-friendly policy

Design sketch — illustrative, not compiled as part of the probe
bool post_from_single_producer(const Event& e) noexcept {
    if (queue_.push(e)) return true;
    ++producer_local_drop_count_; // A single owner writes this counter.
    return false;                 // Never block inside an ISR.
}

That sketch assumes queue_ and its producer-local counter are suitably initialized and exclusively owned; it is not a turnkey interrupt-safe wrapper. If the actual design has several independent posters, consider one queue per producer feeding an arbiter, or a queue specifically designed for multiple producers. Avoid attaching a lock around the queue and then advertising the resulting path as wait-free.

Flight software review gate: analyze queue placement and cache effects, atomics on the exact MCU, interrupt nesting, push/pop WCET, synchronization ordering, lost-event handling, overflow telemetry, reset/quiescence, object lifetimes, and traceability from requirements to tests.

11 · Deliberate tradeoffs

Choose the topology before the container

OptionSuitable whenWatch for
Boost.Lockfree SPSCPrecisely one producer / consumer, bounded queue, low-overhead handoff.No intrinsic blocking wait; explicit overflow and target validation.
Boost.Lockfree queueSeveral producers/consumers need a general concurrent queue.Different progress guarantee; boundedness and allocation policies require separate analysis.
RTOS mailbox / event queueScheduler wakeups, priorities and explicit blocking are central.Scheduler latency, critical sections, priority handling, certification evidence.
Mutex + bounded ringSimplicity and low traffic matter more than nonblocking progress.Blocking, priority inversion policy, lock hold times.
Dedicated SPSCQueue libraryYou want a smaller standalone dependency.Audit alternative capacity semantics and blocking vs try-APIs separately. [10]

Boost's own documentation cautions that nonblocking containers are not always the fastest choice and recommends workload-specific benchmarking. “Wait-free” describes operation-level progress, not end-to-end delivery when the application retries indefinitely on full. [1]

13 · Adoption decision

Worth prototyping — with a sharply bounded scope

For a single diagnostic producer feeding one recorder, spsc_queue is a credible foundation: finite capacity, explicit failure, FIFO semantics and a widely reviewed upstream codebase. The test here also demonstrates that a small fixed-capacity event type can use the queue with no dynamic data members and with functioning threaded handoff on the tested host.

For RISCue's general active-object mailboxes, the design likely requires multiple producers. That is where this library's defining restriction becomes an architectural problem rather than an optimization opportunity. Evaluate an RTOS-native mailbox or a separately verified MPSC/MPMC queue instead.

Next practical experiment: instrument a single-producer queue on the intended board, run the saturation and interrupt-preemption tests, measure maximum observed push/pop cycles and memory footprint, and compare with RISCue's existing message path under identical workload and priority settings. Do not select from desktop throughput rankings.
