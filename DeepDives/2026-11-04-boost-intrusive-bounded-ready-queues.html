01 / decision

Verdict: prototype for a bounded ready list

Boost.Intrusive is a strong candidate for a single-owner list of preallocated RTOS task or event objects. Insertion, cancellation of a known item, and dispatch from the head do not need separate list-node allocations. Crucially, this is not proof that the application allocates nothing, that list operations synchronize between threads, or that measured worst-case timing is bounded.

Promising

Scheduler-owned ready list

Stable, preallocated task control blocks; one owner; constant-time insert and known-node erase. A clear, auditable resource model.

Wrong abstraction

Cross-core mailbox

Not a replacement for a lock-free SPSC channel. A concurrent sender and scheduler cannot safely mutate the same list without a synchronization policy.

What makes it different: the Nov 2 Boost.Lockfree SPSC queue was a communication primitive. Boost.Intrusive is an object organization primitive. It addresses node storage and identity, not concurrency.

02 / mechanism

Store pointers inside the event

A conventional std::list<Event> ordinarily owns nodes and allocates separate node storage. An intrusive list embeds a list_member_hook in each application-owned event. The queue holds references to those objects through their hooks. Objects remain owned by the application and must outlive their list membership. This behavior is documented by the official list reference and usage guide.

preallocated Event 10: [id=10 | previous pointer | next pointer]
preallocated Event 20: [id=20 | previous pointer | next pointer]
                                 ↑
                 intrusive ready list connects these hooks
                  (no separate heap-allocated list nodes)

The diagram is conceptual: actual struct layout, padding, pointer representation and per-target memory footprint must be measured.

The object may still allocate: a task payload with a dynamic std::string, heap-owning callback, or runtime-allocated task object defeats a whole-program “allocation-free” claim even though the list operations themselves do not allocate.

Operation-level accounting

OperationComplexityPrecondition or detail

Lifecycle invariant: one hook cannot belong to two lists simultaneously. Use separate hooks for separate memberships. The default safe_link mode helps detect double insertion in development, but safety depends on checked ownership and lifetime. Do not destroy or recycle a linked object.

The official doubly linked list description specifies two pointers of overhead per node for its hook; object padding and other fields vary by ABI. Default safe-link assertions and cleanup behavior should be evaluated in the production build configuration. auto_unlink is a separate mode, incompatible with maintaining constant-time size: this report does not use it. O(1) is an asymptotic guarantee, not an end-to-end worst-case execution-time measurement. [2] [3]

04 / evidence

Real uses verified in primary source code

These are concrete integrations inside other Boost components, verified from their own repositories; they demonstrate architectural precedent, not proof of RISCue suitability.

Verified source-level use

Boost.Fiber

The scheduler header defines intrusive ready and worker lists; an intrusive multiset handles sleeping contexts, and another intrusive list handles terminated ones. This is the closest ready-queue precedent.

Verified source-level use

Boost.Cobalt

The channel header uses intrusive read and write operation lists with auto-unlink hooks and non-constant-time size options—a deliberately different lifetime policy.

Verified source-level use

Boost.Beast

HTTP field elements use an intrusive list hook and a set hook, illustrating that one object can participate in multiple views with separate hooks. This does not imply a no-allocation HTTP parser.

Proposed application only

RISCue / VeloSim

Preallocated active-object control blocks or deterministic event ownership lists are plausible future prototypes. No existing integration or deployed use in these projects is claimed.

05 / C++20 implementation

Ready queue with explicit event identity

Code follows the upstream documented member_hook, safe_link, iterator_to and list APIs. All events are constructed before the list, and cannot be copied. This avoids a common error: relocating a hooked event in a growing vector.

#include <boost/intrusive/list.hpp>
#include <cassert>
#include <cstdint>
#include <iostream>

namespace bi = boost::intrusive;

struct Event {
    explicit Event(std::uint16_t n) : id(n) {}
    Event(const Event&) = delete;
    Event& operator=(const Event&) = delete;
    std::uint16_t id;
    bi::list_member_hook<> hook;  // default safe_link
};
using Ready = bi::list<Event,
    bi::member_hook<Event, bi::list_member_hook<>, &Event::hook>>;

int main() {
    // These events outlive the ready list and never move.
    Event telemetry{10}, command{20}, watchdog{30};
    Ready ready;
    ready.push_back(telemetry);
    ready.push_back(command);
    ready.push_front(watchdog);
    assert(ready.size() == 3 && ready.front().id == 30);

    ready.erase(ready.iterator_to(command)); // known node: O(1)
    assert(!command.hook.is_linked());
    Event& first = ready.front();
    ready.pop_front(); // detaches, does not destroy the Event
    assert(first.id == 30 && !first.hook.is_linked());
    assert(ready.front().id == 10);

    ready.clear(); // detach before object lifetime ends
    assert(ready.empty() && !telemetry.hook.is_linked());
    std::cout << "ready queue invariants passed\n";
}

Expected sequence: after three insertions, [30, 10, 20]; after cancelling 20, [30, 10]; after dispatching 30, [10]; after clearing, empty. The example uses assertions for illustration, not a complete unit-test framework.

Verification boundary: APIs and lifetime rules were checked against official documentation, but this specific snippet has not been compiled or executed in this run.

07 / costs

What could go wrong?

Benefits

Separate list-node allocation eliminated; identity-preserving removal; constant-time list maintenance for known nodes; no object copies; multiple distinct hooks can create multiple indexes.

Risks

Strong ownership/lifetime coupling; embedded pointers cost RAM; hooked objects cannot be casually relocated; lists are not thread-safe; priority searches can be linear; accidental linked-object destruction is dangerous.

Do not infer “lock-free.” A short list mutation is not a memory-ordering algorithm. If an ISR and scheduler both touch this container, you must design and qualify the synchronization and ownership protocol independently.

Allocation boundaries: allocating an Event at dispatch time, capturing a heap-owning callback, or storing a dynamic payload could still allocate. For a fixed-memory architecture, all object storage and payload capacity must be provisioned in advance.

WCET: O(1) insert and removal are helpful for proof obligations, but do not bound cache effects, critical-section contention, compiler changes or event-handler code. For deadline ordering, a fixed-capacity heap or intrusive ordered structure may be more appropriate.

Suggested architecture, not existing implementation: use an independently qualified bounded SPSC mailbox to transfer IDs from the sole producer into the scheduler. Inside that one scheduler context, organize preallocated ready objects using Boost.Intrusive. This distinguishes inter-context transfer from ownership and scheduling.

09 / adoption mechanics

CMake/Ninja, dependency policy, license

Boost.Intrusive is header-only but relies on other Boost headers. The official vcpkg package lists version 1.92.0 as of the November 4, 2026 research and its transitive dependencies. Production CI should pin a vcpkg baseline and approved compiler/Boost versions.

Install and configure

vcpkg add port boost-intrusive
cmake -S . -B build -G Ninja -DCMAKE_TOOLCHAIN_FILE=<vcpkg-root>/scripts/buildsystems/vcpkg.cmake
cmake --build build
./build/ready_queue

Replace the placeholder with the actual path; on Windows use the produced executable filename and appropriate path separator. CMake toolchain selection must occur during configuration.

Minimal CMakeLists.txt

cmake_minimum_required(VERSION 3.20)
project(intrusive_ready_queue LANGUAGES CXX)
find_package(Boost REQUIRED)
add_executable(ready_queue main.cpp)
target_compile_features(ready_queue PRIVATE cxx_std_20)
target_link_libraries(ready_queue PRIVATE Boost::headers)

The Boost::headers imported target is widely supported by CMake Boost packages, but verify the exact package and target exported by your toolchain. This example was not configured in a real local build during this run.

Fair alternatives

For simple FIFO without known-node cancellation, a fixed-size ring buffer may have smaller metadata overhead. For ownership semantics with no preallocated object pool, conventional std::list is simpler but normally allocates nodes. Boost.Lockfree SPSC solves a narrower concurrent transfer problem. A fixed-capacity heap is often better for deadline-based ordering. Pick based on requirements and measurements, not framework popularity.
