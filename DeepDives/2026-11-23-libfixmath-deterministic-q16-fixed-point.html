Engineering decision

Recommendation: libfixmath is a credible candidate for a bounded, tested fixed-point kernel, not a drop-in safety-certified numeric type or a constant-time primitive. For RISCue and deterministic simulation, start with caches disabled, overflow checking enabled, a separately typed error channel, and a pinned source revision.

Critical trap: the upstream header defines both fix16_minimum and fix16_overflow as 0x80000000. The same raw word means the mathematical endpoint −32,768 or an error. You cannot resolve that ambiguity by inspecting the result alone.

This deep dive evaluates upstream revision aa19cbf9142c, dated November 19, 2026, including a recent software-modulus repair. It does not claim actual deployment in RISCue, VeloSim, flight hardware or a safety-critical product.

What libfixmath actually is

libfixmath is a C fixed-point math library with a fix16_t raw integer type, checked arithmetic, saturating variants, trig, exponential/log functions, square root, formatting/parsing and an optional C++ wrapper. Its README describes the repository as a mirror of an older Google Code SVN project and says it is not actively maintained. A November 19, 2026 source commit is nevertheless observable; a recent patch is not a long-term maintenance guarantee.

Official sources inspected for this article include the public header, arithmetic implementation, exponential cache, trigonometry implementation, test configurations, the build files and MIT license.

Supplied

C99-style math API, multiple CPU-specific implementation branches, configurable rounding/overflow behavior, CMake static library, upstream test sources.

Not supplied

Strong engineering units, a separate success/error return type, WCET certification, per-task cache instances, formal proof or a RISCue-specific adapter.

Q16.16, made concrete

Interpret a signed 32-bit integer as real value = raw / 65,536. fix16_one is 65,536; 0x00018000 means 1.5. Multiplication needs a wider intermediate or a multiword algorithm; a 32-bit product alone cannot generally preserve both the integer and fractional parts. The range is approximately −32,768 to +32,767.9999847.

Fixed-point eliminates several sources of floating-point variability but does not automatically establish cross-platform bit-for-bit behavior, correct rounding, physical-unit validity or bounded execution time. Shift semantics, signed overflow and compile definitions still matter.

The safe integration boundary

Do not allow arbitrary Q16.16 raw words to cross an active-object boundary without a documented domain and scale. Treat a representation plus unit, range, rounding mode and fault policy as the full numeric contract. Version that contract with the logged trace format.

The sentinel and conversion hazards

Consider two calls: fix16_add(fix16_minimum, 0) mathematically produces −32,768; fix16_add(fix16_maximum, fix16_one) overflows. In the default interface both can yield the same raw sentinel. This is a design-level ambiguity, not something a test for == fix16_overflow can repair after the fact.

For a safety-oriented bounded domain, reject that endpoint at ingress, make range limits much narrower than numeric limits, and return an independent error enum. If the complete signed range is essential, use a different error protocol or a separate audited implementation. Do not assume that every saturating operation is a validity proof.

Conversion trap: the header implements fix16_from_int as an unchecked multiplication by fix16_one; float/double conversion paths cast scaled values to int32_t. Perform explicit range/finite checks before calling conversion functions. The F16(x) macro is documented for constant expressions and may evaluate x more than once.

Always test division by zero yourself; the raw sentinel channel alone is insufficient for safe ingress. Specify behavior for invalid negative square roots, logarithms of nonpositive values, and the bounds of transcendental approximations.

Static storage is not the heap—but it is state

In the examined math sources, no dynamic allocator is called on the ordinary arithmetic paths. However, the default build includes writable static lookup caches. The README attributes about 32 KB to exponential caching and 80 KB to trigonometric caching. These are substantial for a small MCU, even if the linker can discard unused objects.

The source shows arrays such as _fix16_exp_cache_index[4096] and sine/atan cache arrays. They are mutated without visible locks or atomics. Shared use across preemptive tasks therefore raises a data-race issue, and cache hits can change execution time based on prior calls. FIXMATH_NO_CACHE removes those caches from their guarded code paths.

Default cached path

Potential repeated-call savings, but global writable state, concurrency exposure and input-history timing variance.

Cache disabled

No cache-derived shared mutations or RAM cost; still not automatically constant-time or WCET-qualified.

Use the actual embedded link map, not the README's sum, to determine flash, BSS and stack consumption after dead-code elimination. Audit any remaining library-global state before multi-core or interrupt-level use.

The November 19 modulus fix—and a remaining deadline risk

The inspected November 19, 2026 commit repairs fix16_mod() in FIXMATH_NO_HARD_DIVISION mode for negative divisors. The old repeated-subtraction logic could iterate in the wrong direction; the patch normalizes divisor magnitude and adds a regression comparison to fmod().

Still important: this software modulus path uses repeated subtraction, so execution time can scale with the quotient magnitude. A tiny nonzero divisor can produce an enormous iteration count. An input divisor of zero is invalid in both hardware-remainder and repeated-subtraction modes; the latter can fail to terminate. Validate a nonzero minimum divisor magnitude and bound the quotient, or avoid this routine on a hard-deadline path.

Ring-buffer indices are often better served by power-of-two masking or standard bounded integer remainder after explicit checks. A fixed-size value type does not imply a fixed-time algorithm.

C++20 fail-closed adapter

The following original example restricts ingress to ±100 units, uses an exactly representable gain (1.5), and exposes a separate status. It avoids runtime floating-point conversion, heap allocation, and silently propagating a raw sentinel.

Complete main.cpp · C++20
#include <cstdint>
#include "libfixmath/fix16.h"

enum class Fault : std::uint8_t {
    None, InvalidEncoding, OutsideDomain, Overflow
};

struct [[nodiscard]] Result {
    fix16_t raw{};
    Fault fault{Fault::None};
    [[nodiscard]] constexpr bool ok() const noexcept {
        return fault == Fault::None;
    }
};

[[nodiscard]] Result apply_gain(fix16_t input) noexcept {
    constexpr fix16_t limit = 100 * 65536; // +/-100.0
    constexpr fix16_t gain  = 0x00018000;   // 1.5

    if (input == fix16_overflow)
        return {0, Fault::InvalidEncoding};
    if (input < -limit || input > limit)
        return {0, Fault::OutsideDomain};

    const fix16_t result = fix16_mul(input, gain);
    if (result == fix16_overflow)
        return {0, Fault::Overflow};
    return {result, Fault::None};
}

int main() {
    constexpr fix16_t sample = 60 * 65536;
    const Result r = apply_gain(sample);
    return r.ok() && r.raw == 90 * 65536 ? 0 : 1;
}

Expected exit code is 0 for 60 × 1.5 = 90. The enum and admission gate are application-level C++20 code, not features of upstream. They are intentionally conservative: an input with the minimum raw encoding is rejected, even though it could represent a mathematical endpoint.

Reproducible CMake + Ninja wiring

Upstream supplies a static target named libfixmath and recommends FetchContent. Pin the inspected commit instead of tracking a branch. Scope compile definitions carefully: macros such as FIXMATH_NO_OVERFLOW change header-inline implementations and must not disagree between the compiled C library and its C++ consumer.

CMakeLists.txt · CMake
cmake_minimum_required(VERSION 3.24)
project(q16_trial LANGUAGES C CXX)
include(FetchContent)

FetchContent_Declare(libfixmath
  GIT_REPOSITORY https://github.com/PetteriAimonen/libfixmath.git
  GIT_TAG aa19cbf9142cc41344608bd2dec07fa12e35b55a
)
FetchContent_MakeAvailable(libfixmath)

# PUBLIC keeps consumer/header and library profiles aligned.
# Overflow checking and rounding stay at upstream defaults.
target_compile_definitions(libfixmath PUBLIC FIXMATH_NO_CACHE)

add_executable(q16_demo main.cpp)
target_compile_features(q16_demo PRIVATE cxx_std_20)
target_link_libraries(q16_demo PRIVATE libfixmath)

Proposed RISCue and simulation applications

RISCue active-object calibration

Bounded ADC gain, threshold or rate computations where every input and intermediate fits the contract. Convert faults to explicit reject/error events.

Deterministic simulation

Compare serialized raw-bit model outputs across x86-64 and target builds; log pin SHA, compiler flags, rounding and no-cache profile.

HSM transition guards

Use validated values and simple operations for guard conditions. Keep variable-cost divide/trig/modulus out of hard-deadline guards unless measured.

Trace and interoperability

Represent the wire format as signed raw 32-bit value, fixed scale, physical unit, schema version and independent fault status—not just four undocumented bytes.

These are suggested use cases. No RISCue/VeloSim/SharpUnits/Native AOT integration has been verified. A .NET 10 Native AOT caller could in principle use a small C ABI over fixed-width integers; that is a design opportunity, not reported existing work.
