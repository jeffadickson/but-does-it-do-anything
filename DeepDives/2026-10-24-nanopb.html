01 · Structured messages without a desktop runtime

Nanopb implements Protocol Buffers encoding and decoding in C for constrained systems. A schema describes the messages; generated C structures and field descriptors let a compact runtime translate between those structures and wire bytes. The runtime can operate without heap allocation. [1]

For your work, the attractive problem is the boundary between an embedded active object and host tooling: how do they exchange structured data without sharing C++ object layouts, pointer values or compiler-specific padding?

Why today’s selection: Nanopb makes message capacity an explicit design choice. That connects naturally to static queues, deterministic input replay and a C# analysis tool. Its generator is Python-based, however, which creates a real mismatch with your current tooling policy. The article treats that as an integration constraint rather than hiding it.

Research snapshot: the maintainer’s downloads page lists 0.4.9.2 as latest/LTS when checked. The documentation applies to the 0.4 family; pin runtime, generator and schema tooling together for an evaluation. [2]

02 · The schema and the memory representation are separate

Schema + optionsField numbers, types, maximum counts.
Generated C modelStructures and trusted descriptors.
Runtime codecBuffer or callback stream ↔ wire bytes.

Protocol Buffers encodes numbered fields using wire types such as variable-length integers and length-delimited values. The wire representation is independent of a C struct’s layout. Nanopb adds configuration for how variable-length data is represented in firmware. [3] [4]

A bounded repeated field can become an inline array plus a count. Without suitable bounds, variable-length fields commonly use callbacks instead. A callback can stream data without storing the whole field, but you must bound its work, handle errors and manage any state it touches. [4]

The runtime uses generated descriptors to locate fields. The public API provides buffer-backed input/output streams and boolean success/failure results. Optional dynamic decoding is controlled by PB_ENABLE_MALLOC. For a static profile, leave that macro undefined; do not assume defining it to zero disables a feature guarded by its presence. [5]

04 · Why it may interest you

Proposed applications

  • Active-object boundary: decode into a fixed local candidate, validate it, then post a bounded application event. Avoid letting a partially decoded object escape into the state machine.
  • Deterministic simulation: retain input frames with virtual arrival times and replay them through the same decoder. Keep transport timing, queue overflow and parser outcomes explicit.
  • Requirements traceability: attach a requirement to each message capacity, allowed value range and rejection behavior. Schema field numbers alone are not requirement identifiers.
  • C# host interoperation: generate a host-side representation from the same schema and compare semantic values across implementations. Protobuf’s C# compiler output is documented; the exact selected runtime’s trimming and .NET 10 Native AOT behavior would need a separate test. [9]
  • Allocation evidence: combine inspection of generated structures with symbol audits and allocation traps. The codec’s static mode does not prove that callbacks, logging or transport code are allocation-free.

05 · A small bounded telemetry decoder

The example schema separates portable wire definitions from Nanopb-specific capacity settings. The eight-sample limit becomes a fixed array in the generated representation. The options file must actually be found by the generator; verify the generated header rather than inferring success from a generation command’s exit status. [4] [5]

// telemetry.proto
syntax = "proto3";
message Telemetry {
  uint32 sequence = 1;
  repeated sint32 samples = 2;
}

// telemetry.options (separate file)
Telemetry.samples max_count:8

Here, samples represent temperatures in thousandths of a degree Celsius. The C++20 wrapper accepts an already-framed payload, applies an outer byte budget and publishes only after decoding and application checks succeed. Its output remains unchanged on failure. The buffer-backed API pattern follows the maintainer’s example. [8]

#include <cstdint>
#include <span>
#include <pb_decode.h>
#include "telemetry.pb.h" // Generated from the schema above.

bool decode_frame(std::span<const std::uint8_t> frame,
                  Telemetry& accepted) noexcept {
    if (frame.empty() || frame.size() > 128) return false;
    Telemetry candidate = Telemetry_init_zero;
    auto input = pb_istream_from_buffer(frame.data(), frame.size());
    if (!pb_decode(&input, Telemetry_fields, &candidate)) return false;
    if (candidate.samples_count == 0) return false;
    for (pb_size_t i = 0; i < candidate.samples_count; ++i) {
        if (candidate.samples[i] < -40000 ||
            candidate.samples[i] > 125000) return false;
    }
    accepted = candidate; // Publish only a fully validated message.
    return true;
}

Example status: original illustrative schema and wrapper, not generated, compiled or executed during this run. A generated telemetry.pb.h/.c, matching runtime and compatible configuration are prerequisites. No generator was installed or run. The 128-byte envelope is an application choice, not a claimed universal protobuf size limit.

Successful decoding establishes structural validity, not that a temperature is meaningful or a sender is authorized. The candidate-before-publish approach follows from Nanopb’s documented separation between trusted descriptors/streams and untrusted input values. [10]

06 · Deterministic replay is not canonical serialization

Protobuf permits more than one byte representation of equivalent message content. Google explicitly distinguishes deterministic serialization from a canonical form and cautions against treating serialized-message hashes as stable semantic fingerprints across versions and implementations. [11]

For your regression system: hash exact captured bytes to identify an input artifact. Compare explicitly selected decoded fields to test semantic equivalence. Those are two different assertions. Define how unknown fields, missing fields and schema revisions affect each test.

Nanopb’s overview also notes that unknown fields are not retained through decode/re-encode and that runtime reflection is unavailable. That is a practical tradeoff for a compact embedded representation; it matters if you expected firmware to act as a transparent forward-compatible message relay. [1]

Framing, integrity/authentication, rate limits and application authorization belong in the surrounding protocol. A decoder for a protobuf payload does not, by itself, establish those properties. Keep decoding out of an ISR in the proposed architecture and budget it in the worker that owns the message.

07 · Tooling fit and integration costs

The Python generator is a policy mismatch

Upstream uses a Python generator to produce the C model and descriptors; downloadable tool bundles package generator dependencies. A bundled executable does not make the generator a C#/.NET implementation. Under your current Python-tool restriction, invoking it in StateForge’s normal workflow would require a deliberate policy decision. A C# wrapper around it would not remove the underlying dependency. [1] [2]

Possible evaluation boundary: externally produced, reviewed generated artifacts could be consumed by a native build, with their schema, options, generator identity and hashes recorded. That is only a proposed workflow and still needs your policy decision for regeneration and provenance. Reimplementing a generator in C# would be a substantial compatibility project, not a trivial conversion.

CMake/Ninja freshness

The upstream CMake example uses find_package(Nanopb) and nanopb_generate_cpp to create a target. For a future integration, pin tools and give Ninja explicit generated outputs and dependencies: schema, options, imported protos and generator version/configuration. Do not run generation unconditionally for every build. [12]

TradeoffWhat to evaluate
Fixed arrays reserve maximum capacityPer-message RAM, number of simultaneous instances and queue depth.

License

The core uses a permissive zlib-style license: commercial use and modification are allowed; origin must not be misrepresented, altered sources must be identified, and the notice must remain in source distributions. Check generator dependencies and the host protobuf runtime separately. [13]

08 · The first experiment I would run

Suggested acceptance plan

  1. Generate and review one bounded message outside any production repository under an agreed tooling policy.
  2. Decode zero, one, eight and nine samples; truncate every byte position of valid frames; test oversized frames and invalid temperature values.
  3. Assert that every rejected frame leaves the published output unchanged and produces a deterministic error classification.
  4. Cross-check decoded values with a selected C# implementation. Include schema evolution and unknown-field cases; do not require cross-runtime canonical byte identity.
  5. Record compiler, runtime/generator revisions, schema/options hashes, allocation audits and measured stack/latency. Parallelize independent corpora with bounded concurrency and isolated outputs.

The security model documents stream and structure bounds under its trust assumptions. Keep malformed-input tests alongside application-range tests; neither substitutes for the other. [10]

My recommendation: Nanopb is worth studying for its explicit static message representation and cross-language wire contract. The generator policy mismatch is substantial enough that I would evaluate the architecture and tooling boundary before proposing adoption.
