01 / the design problem

Ship meaning, not megabytes

An embedded sensor may need to report sequence 17, temperature 21.500°C, status 3. JSON makes the numbers readable, but it repeats field names and punctuation. A carefully designed CBOR array encodes the three values as six bytes, without a heap-backed string builder. zcbor can operate on caller-provided byte buffers and fixed-size stack state.

RISCue opportunity · proposed

Bounded active-object events or diagnostic snapshots could use an explicit CBOR envelope at a communication boundary. This is a design proposal, not a current RISCue integration.

VeloSim opportunity · proposed

Capture independently replayable binary traces and compare canonical byte sequences. Pinning schema and library versions would support reproducibility. This is not documented adoption.

Boundary matters: CBOR describes bytes; it does not supply transport reliability, authentication, replay protection, or application-level state-machine correctness. zcbor is a codec, not an RTOS or safety proof.

02 / wire anatomy

Six bytes, three typed fields

Our illustrative wire contract is one CBOR definite-length array: [uint sequence, int temperature_mC, uint flags], in that order. Units are millidegrees Celsius; 21500 means 21.500°C. This is a new example protocol, not a real flight packet.

83array of 3
11seq 17
19uint16 marker
53temperature
FCtemperature
03flags 3

The two temperature bytes 53 FC represent hexadecimal 0x53FC = decimal 21,500. For larger magnitudes or negatives, CBOR uses different additional bytes; six bytes is this example’s size, not the universal size of this schema.

3 bits: major type

Array, positive integer, negative integer and other CBOR families. The leading 83 is an array with three members.

5 bits: extra info

Small values 0–23 fit directly in one byte. Larger values carry 1, 2, 4 or 8 follow-on bytes.

Range rules are external

CBOR can represent values your application must reject. For example, the sequence field must be ≤65,535.

04 / C API

Caller-owned storage; errors are explicit

This example uses zcbor’s documented ZCBOR_STATE_E/ZCBOR_STATE_D macros, typed integer helpers, and list delimiters. It stages decoded values in a temporary structure and publishes only after full validation. Define ZCBOR_CANONICAL consistently for the library build and test it on your pinned version.

/* Telemetry demonstration — zcbor direct API (C11, callable from C++20).
 * Wire contract: exactly [sequence:uint, temperature_mC:int, flags:uint].
 * Deliberately use an array (not a map) for stable field positions.
 * See build instructions below; schema validation is explicit here.
 */
#include <zcbor_encode.h>
#include <zcbor_decode.h>
#include <zcbor_common.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

typedef struct {
    uint32_t sequence;         /* 0 .. 65535 */
    int32_t temperature_mc;    /* -50000 .. 125000 */
    uint32_t flags;            /* 0 .. 255 */
} Telemetry;

static bool valid(const Telemetry *t) {
    return t && t->sequence <= 65535u &&
        t->temperature_mc >= -50000 && t->temperature_mc <= 125000 &&
        t->flags <= 255u;
}

bool telemetry_encode(uint8_t *out, size_t capacity,
                      const Telemetry *t, size_t *written) {
    if (!out || !written || !valid(t)) return false;
    *written = 0;
    /* A nested list requires one backup state; outer item count = 1. */
    ZCBOR_STATE_E(s, 1, out, capacity, 1);
    const bool ok = zcbor_list_start_encode(s, 3) &&
        zcbor_uint32_put(s, t->sequence) &&
        zcbor_int32_put(s, t->temperature_mc) &&
        zcbor_uint32_put(s, t->flags) &&
        zcbor_list_end_encode(s, 3);
    if (!ok) return false;
    *written = (size_t)(s->payload - out);
    return true;
}

bool telemetry_decode(const uint8_t *in, size_t length, Telemetry *result) {
    if (!in || !result) return false;
    Telemetry tmp = {0};
    ZCBOR_STATE_D(s, 1, in, length, 1, 0);
    const bool ok = zcbor_list_start_decode(s) &&
        zcbor_uint32_decode(s, &tmp.sequence) &&
        zcbor_int32_decode(s, &tmp.temperature_mc) &&
        zcbor_uint32_decode(s, &tmp.flags) &&
        zcbor_list_end_decode(s) &&
        zcbor_payload_at_end(s);
    if (!ok || !valid(&tmp)) return false;
    *result = tmp;  /* Publish only after complete validation. */
    return true;
}

/* Golden vector with ZCBOR_CANONICAL enabled:
 * [17, 21500, 3] => 83 11 19 53 FC 03 (6 bytes).
 * Production tests should reject truncated, extra, wrong-type,
 * out-of-range, duplicate/ambiguous (if using maps) and noncanonical data.
 */

Review status: Function names and macro signatures were checked against upstream headers, but this newly composed C example was not compiled or executed against the zcbor library in this run. Treat it as a review candidate, not qualified production code. The upstream hello_world sample is the independently buildable reference.

05 / CDDL & generation

Turn protocol rules into generated C

CDDL is an IETF-defined language for describing CBOR shapes. zcbor’s host-side Python tool can generate C encoder/decoder and typed structs, while also enforcing supported field constraints. It is especially valuable for decoding untrusted input, where missing a validation check can become a defect.

Telemetry = [
  sequence: 0..65535,
  temperature_mC: -50000..125000,
  flags: 0..255
]

; Suggested schema for the generated-code path. Pin and test the
; zcbor generator version; do not assume this page generated code.

Example generator invocation following Nordic’s documented CLI shape:

# Host-side generation (not a target/device runtime dependency)
python -m pip install 'zcbor==0.9.1'
zcbor code -c telemetry.cddl -t Telemetry -d -e \
  --output-cmake generated/CMakeLists.txt
# Include generated/CMakeLists.txt in a separate integration build.
# Generated public function/type names: inspect produced headers;
# do not guess symbols before code generation.

Engineering rule: pin zcbor’s source and Python generator revisions together; review the produced headers; commit the schema and generated artifacts; use known-good and malformed CBOR golden vectors. Not every RFC 8610 feature is supported, and the project documents experimental support for decoding unordered maps.

06 / reproducible integration

CMake / Ninja: avoid hidden assumptions

For a non-Zephyr CMake project, Nordic’s own hello-world sample compiles three C sources (zcbor_common.c, zcbor_encode.c, zcbor_decode.c) and includes include/. A minimal integration skeleton is:

# Folder layout: ./zcbor/ (pinned upstream checkout), ./main.c, ./CMakeLists.txt
cmake_minimum_required(VERSION 3.20)
project(zcbor_telemetry C)
set(CMAKE_C_STANDARD 11)
add_library(zcbor_core STATIC
  zcbor/src/zcbor_common.c
  zcbor/src/zcbor_encode.c
  zcbor/src/zcbor_decode.c)
target_include_directories(zcbor_core PUBLIC zcbor/include)
target_compile_definitions(zcbor_core PUBLIC ZCBOR_CANONICAL)
add_executable(telemetry_test main.c)
target_link_libraries(telemetry_test PRIVATE zcbor_core)
# cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
# cmake --build build
# ctest --test-dir build --output-on-failure  # only after adding tests

The build sketch expects a local pinned checkout. It is not a claim that a complete CTest suite was configured or run here. For Zephyr, use CONFIG_ZCBOR instead of manually compiling the library. Keep code generation on the development host; the firmware only needs the generated C and C runtime components.

08 / threat & timing model

Useful does not mean free

StrengthConstraint / mitigation
Binary CBOR can be compactNot self-describing at application-semantic level; version the schema and units.
Fixed input/output buffers and state arraysProve bounded nesting, state backup count, buffer size and stack use per schema; library operation alone does not prove zero allocations in a whole program.
Generated validationGenerator is a build-time Python dependency; audit generated code and supported CDDL constructs. Regenerate deterministically.
ZCBOR_CANONICALUpstream explicitly does not check map-key ordering or minimum float representation on decode; a signed/cross-platform protocol must define its own complete canonical policy.
Typed C API compatible with C++Manual decoding is repetitive; errors must be checked at every step. Generated code improves coverage but is not a security guarantee.
CBOR flexibilityUnbounded arrays, maps, strings and recursion are not appropriate for hard-real-time boundaries without strict limits.

Do not confuse: “canonical CBOR” (a set of encoding rules) with deterministic execution time, deterministic simulation, or data authenticity. They are separate engineering obligations. For signed material, RFC 8949 and your security profile govern the exact byte representation.

09 / dependency decision

Apache-2.0, not MIT

zcbor is licensed under the Apache License 2.0 (verified in the repository’s LICENSE and SPDX identifiers). It allows modification and redistribution, including commercial use, subject to preserving required notices, including the license, identifying modified files, and handling any applicable NOTICE. It provides an explicit patent license subject to its terms. The IETF CBOR/CDDL RFCs specify formats; they are not zcbor’s software license.

Adoption gate — go to prototype

Appropriate for small, schema-locked binary telemetry and recovery messages after cross-compiler tests and heap instrumentation. Start with a single bounded message type, a fixed arena and positive/negative vectors.

Adoption gate — do not claim yet

No flight suitability, RISCue integration, worst-case-time bound, code-size benchmark, static-allocation proof, generator reproducibility or security certification was established in this report.
