01 / Why would you need MPMC?

Imagine two sensors or worker threads producing events while two processing threads compete to handle the next event. A classic SPSC queue—single producer, single consumer—does not support that topology without extra coordination.

MPMCMultiple producers; multiple consumers. Each successful pop transfers one queued item to one consumer, not a broadcast.
N slotsThe user chooses the capacity at construction. No automatic growth.
try_*Return success/failure without waiting for an empty/full condition; retries remain your responsibility.
Ticketed ringMonotonically advancing head/tail tickets identify slots and their reuse cycles.

The library is header-only and targets C++11 or newer. The project’s README defines the API; the actual header is the authority for the memory ordering and allocation behavior.

Important topology point: MPMC consumers divide work. If VeloSim needs every observer to see every event, a single MPMC queue is the wrong primitive; use fan-out or per-subscriber queues.

02 / Tickets, turns, and the ring

Each producer claims a head ticket and each consumer claims a tail ticket. A ticket t maps to index = t % capacity. The reuse cycle is turn = floor(t / capacity).

A slot's three important states

  1. Write permitted: its turn counter equals 2 × turn.
  2. Item published: producer constructs the item, then stores 2 × turn + 1 with memory_order_release.
  3. Item consumed: consumer observes the published state with memory_order_acquire, moves the item, destroys it, and releases the slot by storing 2 × turn + 2.

That acquire/release relationship is central to publishing the payload safely. The code pads slots and the head/tail counters to reduce cache-line false sharing; actual benefit depends on the architecture.

Subtlety: push()/pop() spin while waiting for their slot. The nonblocking-flavored try_push()/try_pop() can also retry compare-and-exchange when other threads contend. Neither API provides a proven constant step bound for all scheduling scenarios.

    05 / A concrete C++20 stress probe

    The following complete example launches two producers and two consumers. Every event carries a unique ID. It checks that all 20,000 events were received once, with a valid producer identifier; failures return a nonzero exit code even in optimized Release builds. It is intended as an initial host-side regression test, not a substitute for TSAN, formal analysis, or target-specific qualification.

    // main.cpp — host-side stress probe, NOT a hard-real-time guarantee.
#include <rigtorp/MPMCQueue.h>
#include <array>
#include <atomic>
#include <cstdlib>
#include <cstdint>
#include <iostream>
#include <thread>
#include <type_traits>

struct Event {
  std::uint32_t id;
  std::uint32_t producer;
};
static_assert(std::is_nothrow_copy_constructible_v<Event>);
static_assert(std::is_nothrow_move_assignable_v<Event>);
static_assert(std::is_nothrow_destructible_v<Event>);

int main() {
  constexpr std::uint32_t perProducer = 10'000;
  constexpr std::uint32_t total = 2 * perProducer;
  rigtorp::MPMCQueue<Event> q(64); // Allocates at initialization.
  std::array<std::atomic<unsigned>, total> seen{};
  std::atomic<std::uint32_t> consumed{0};
  std::atomic<std::uint32_t> invalid{0};

  auto produce = [&](std::uint32_t producer) {
    for (std::uint32_t i = 0; i < perProducer; ++i) {
      Event e{producer * perProducer + i, producer};
      while (!q.try_push(e)) { std::this_thread::yield(); }
    }
  };
  auto consume = [&] {
    Event e{};
    while (consumed.load(std::memory_order_relaxed) < total) {
      if (q.try_pop(e)) {
        if (e.id >= total || e.producer != e.id / perProducer) {
          invalid.fetch_add(1, std::memory_order_relaxed);
        } else {
          seen[e.id].fetch_add(1, std::memory_order_relaxed);
        }
        consumed.fetch_add(1, std::memory_order_relaxed);
      } else {
        std::this_thread::yield();
      }
    }
  };

  std::thread c1(consume), c2(consume);
  std::thread p1(produce, 0), p2(produce, 1);
  p1.join(); p2.join(); c1.join(); c2.join();

  // Checks stay active in optimized Release / NDEBUG builds.
  if (consumed.load() != total || invalid.load() != 0) {
    std::cerr << "FAIL: missing/invalid event\n";
    return EXIT_FAILURE;
  }
  for (auto& count : seen) {
    if (count.load() != 1) {
      std::cerr << "FAIL: duplicate or missing event\n";
      return EXIT_FAILURE;
    }
  }
  std::cout << "PASS: " << total
            << " events delivered exactly once\n";
}
    Code review: Event is trivially copyable, assignable, and destructible; the library demands noexcept-compatible operations. The queue is constructed before threads start and destructed after they join. No consumer counts its input by relying on approximate size(). This example was reviewed against upstream signatures but not compiled against the library in this run.

    Then increase contention, run longer stress campaigns, test with sanitizers where supported, inject artificial producer stalls, and preserve failing seeds. Be careful: a queue stress test can hang on a broken implementation. Run CI scenarios under an external timeout.

    06 / CMake, Ninja, and deployment

    Vendor a reviewed upstream revision into external/MPMCQueue, then build its header-only interface target. The upstream CMake project exports MPMCQueue::MPMCQueue.

    cmake_minimum_required(VERSION 3.20)
project(mpmc_probe LANGUAGES CXX)
add_subdirectory(external/MPMCQueue) # Vendor a reviewed revision.
find_package(Threads REQUIRED)
add_executable(mpmc_probe main.cpp)
target_compile_features(mpmc_probe PRIVATE cxx_std_20)
target_link_libraries(mpmc_probe PRIVATE
    MPMCQueue::MPMCQueue Threads::Threads)
enable_testing()
add_test(NAME mpmc_probe COMMAND mpmc_probe)

# Configure and run:
# cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
# cmake --build build
# ctest --test-dir build --output-on-failure

    The upstream repository also has a CMake project and can be installed through vcpkg. Pin a specific commit and record its SHA, compiler version, target architecture, and exception policy. Do not fetch a moving branch during reproducible builds.

    Footprint and ownership: the constructor checks that capacity is at least one and allocates capacity + 1 padded slots with an allocator. Destruction releases them. This is not a static-allocation-only container as shipped. A custom allocator template argument is supported, but would require its own alignment, lifecycle, and exception-policy review.

    07 / Tradeoffs worth deciding up front

    Fit for deterministic and embedded workloads
    PropertyWhat is supportedWhat is not guaranteed
    Memory growthFixed queue capacity; slot allocation at constructionNo allocation at startup, no payload allocation, or bounded byte overhead without measurement
    ConcurrencyThread-safe pushes/pops and acquire/release slot transferFreedom from starvation, bounded scheduling delay, or ISR safety
    Backpressuretry_push can report failureAutomatic loss policy, retries, drop counters, or deadline enforcement
    Type safetyCompile-time noexcept constraints on construction/assignment/destructionCorrect lifetime of referenced payload memory outside the queue
    ObservabilityApproximate size()/empty() snapshotsA reliable admission-control decision under concurrency
    PortabilityC++11 interface; C++20 client compiles in principleLock-free atomics, low latency, or any specific microcontroller/RTOS support

    Don't confuse three different claims

    Bounded means the container has a fixed number of element slots. Lock-free is a system-wide progress property, not a synonym for “there are atomics.” Wait-free would require a bound on each operation's progress. Spinning and CAS contention make hard real-time admission especially sensitive. Classify the implementation on your actual compiler and target; do not assume a formal lock-free guarantee just because the project is described as lock-free elsewhere.

    Unlike the earlier Boost.Lockfree SPSC deep dive, this queue solves the multiple-producer/multiple-consumer topology. But SPSC remains the cleaner default when every event channel naturally has one writer and one reader.

    08 / Proposed RISCue / VeloSim qualification gate

    1. Map the topology. Prove whether each event stream is really MPMC. Reject broadcast use cases. Prefer SPSC when possible.
    2. Bound memory. Record construction-time heap use, per-slot padding and the custom allocator contract; instrument any payload allocations separately.
    3. Define overflow behavior. Distinguish drop, retry, deferred handling and fault escalation, with counters and explicit deadlines.
    4. Check scheduling. Establish whether the consumer can be preempted while holding the slot; test stalled writers/readers and priority inversion scenarios.
    5. Verify target atomics. Check required atomic width, lock-free status, cache coherence, alignment and interrupt legality on actual silicon.
    6. Measure worst-case behavior. Report P50/P99/P99.9 only as supplementary diagnostics; WCET and guaranteed deadlines need stronger evidence.
    7. Capture reproducibility. Preserve library SHA, compiler flags, target, sanitizer outcomes, stress traces and negative tests as verification evidence.

    Recommendation: Trial rigtorp/MPMCQueue in a host-side VeloSim or SharpTestBench workload before considering it on an RTOS dispatch path. Its simplicity and bounded queue slots are attractive, but no compiled target data or timing qualification was obtained for this report.
