01 · A compact language for behavior

SML lets you express states, events, guards and actions as a typed transition table. A small runtime object tracks the active state while templates describe the machine’s structure. The project targets C++14 and later, so it can be evaluated within a C++20 codebase. [1]

Consider a device controller: a request moves it from idle to busy, a completion returns it to idle, and cancellation takes a defined recovery path. With SML, those relationships appear together instead of being spread through nested conditionals.

Why this selection: you are already building hierarchical machines and active objects. SML offers a useful alternative representation to study and test against selected behaviors. It does not supply the entire runtime architecture that StateForge and RISCue need.

Naming matters: despite its namespace and familiar spelling, Boost.Ext SML is not an official Boost library. The project explicitly states this. [1] The official release page lists v1.2.0 as latest at research time; the notes below distinguish that release from moving master documentation. [2]

02 · The table is executable structure

Typed eventA C++ type identifies the input.
Transition selectionActive source + event + guard.
Behavior updateAction and destination state.

A transition combines a source state, an event, an optional predicate, an optional action and a destination. The initial state is marked with an asterisk. Actions and guards are callables; dependencies can be supplied to the machine and requested by their parameter types. Event processing is invoked with process_event. [3]

The compile-time description enables the compiler to specialize event handling. It is not a general runtime interpreter for arbitrary models loaded from a file. That distinction makes it interesting for fixed firmware behavior, while making runtime model replacement a different problem.

Typed inputEvents carry payloads through normal C++ types.
Injected dependenciesActions can work with caller-owned services and test doubles.
Visible structureA transition table keeps the behavioral relationships together.

API model: [3], [4]. The latter paragraphs are engineering interpretation, not a runtime-performance measurement.

Hierarchy is represented by using another machine as a composite state. The maintainer’s composite example checks both parent and nested active states. Orthogonal regions and history also have dedicated examples, but their names alone do not establish equivalence with another framework’s semantics. [5] [1]

04 · Why it may interest you

Proposed applications

  • Behavioral comparison: express a small, independently specified controller in both SML and StateForge. Compare externally visible outputs and active-state traces over the same event sequences.
  • Allocation-conscious composition: inject references to fixed-storage services. Keep queues, event lifetimes and overflow policy explicit rather than assuming a library-wide allocation guarantee.
  • Deterministic simulation: let a virtual-clock test driver deliver timestamped events. Simulated time and scheduling remain responsibilities of the harness.
  • Requirements traceability: assign stable requirement and transition identifiers in your own model/test metadata. A compact DSL is helpful to reviewers, but it does not automatically produce a StrictDoc trace matrix.
  • C# Native AOT tooling: a bounded-parallel runner could generate reproducible event transcripts, launch native comparison executables and produce ordered JSON evidence. This is a suggested workflow, not an existing SML tool.

For your clean-room rewrite, use independently written behavioral expectations and original implementation code. Studying this library is not a reason to transplant implementation details into StateForge.

05 · A small C++20 controller

This original example uses named state types and caller-owned counters. It accepts a request only while idle and checks both completion and cancellation. The public API and testing example show the relevant construction, injection and state-query patterns. [4] [9]

#include <boost/sml.hpp>
#include <cassert>
namespace sml = boost::sml;
struct begin {};
struct done {};
struct cancel {};
struct idle {};
struct busy {};
struct counters { unsigned accepted{}; };
struct controller {
    auto operator()() const noexcept {
        using namespace sml;
        const auto count = [](counters& c) noexcept { ++c.accepted; };
        return make_transition_table(
            *state<idle> + event<begin> / count = state<busy>,
             state<busy> + event<done>          = state<idle>,
             state<busy> + event<cancel>        = state<idle>
        );
    }
};
int main() {
    counters c{};
    sml::sm<controller> machine{c};
    machine.process_event(begin{});
    assert(machine.is(sml::state<busy>));
    machine.process_event(begin{}); // No matching transition while busy.
    assert(c.accepted == 1);
    machine.process_event(done{});
    assert(machine.is(sml::state<idle>));
    machine.process_event(begin{});
    machine.process_event(cancel{});
    assert(machine.is(sml::state<idle>) && c.accepted == 2);
}

Execution status: illustrative example, not compiled or run for this article. Build it against a pinned SML revision with assertions enabled. It has no queue or timer policy, no dynamic containers and no hardware I/O; those omissions define the example’s scope rather than proving a complete firmware memory bound.

A suitable evaluation command with a configured GCC or Clang is c++ -std=c++20 -Wall -Wextra -Werror -pedantic -I<pinned-sml>/include demo.cpp -o demo. Validate on both your actual Linux and Windows toolchains before treating the example as portable evidence.

06 · A state machine is only one layer

The overview describes a core with no external library dependency. That is useful for integration, but it is a different claim from “every chosen policy and every application action allocates nothing.” [10]

The upstream deferred/processed-event example explicitly selects std::deque and std::queue policies. Those choices need scrutiny in an allocation-free firmware profile. A fixed-capacity replacement would need the required interface, defined full-queue behavior and acceptance tests; substituting a container name is not sufficient evidence. [11]

Recommended boundary for an embedded experiment: one worker owns the machine. Producers post into a caller-owned bounded queue; the worker dequeues and calls process_event. Keep the storage, priorities, ISR handoff and event lifetime rules in the surrounding RTOS/OSAL design.

The documented thread_safe<Lockable> policy requests lock/unlock behavior. It does not establish an interrupt-context contract, priority inheritance, a bounded lock delay or a scheduler. Blocking inside an action also makes that dispatch take as long as the action takes. [4] These are reasons to measure your chosen composition, not objections to typed state machines.

07 · What I would test first

The maintainer’s testing example injects fake data and selects a starting state with the testing policy. That makes isolated transition tests convenient. Keep end-to-end reachability tests as well: forcing a state does not show that normal execution can reach it. [9]

Release details that deserve regression tests

v1.2.0 documents changes to wildcard handling after submachine termination, deferred-event cleanup on composite re-entry and live-state visibility in guards. It also disables an empty-machine minimum-size optimization by default after undefined-behavior problems. These are concrete reasons to pin versions and rerun semantic and UBSan tests after upgrades. [2]

08 · Tradeoffs, integration and licensing

  • Compile-time structure: strong specialization can move complexity into templates, diagnostics and build cost. Measure the machine shapes you actually use; historical README benchmark figures are not your results.
  • Behavioral coverage: hierarchy, queueing and history need explicit tests before claiming parity with another engine. Similar feature labels are not a conformance specification.
  • Application cost: logging, dependencies, locks and actions can dominate runtime and memory even when the machine object is small.

The pinned upstream CMake file defines options for examples, tests, benchmarks and exceptions. For a small evaluation, keep unrelated suites off, attach includes through a target and request C++20 for the consumer. A vendored header avoids a network dependency during routine builds. Ninja will still rebuild consumers when that header changes. [12]

License: SML uses the Boost Software License 1.0. It permits commercial use and modification, requires the specified notices/license text in covered source copies and derivatives, and contains an exception for copies solely in machine-executable object-code form. Retain the license with vendored sources and review other dependencies separately. [13]

My recommendation: use SML first as a small comparison experiment for transition-table ergonomics and selected hierarchical behaviors. Evaluate it alongside your allocation, traceability and scheduling requirements before choosing whether it belongs in any production architecture.
