Make failure boring.

How a tiny C test-double library called Fake Function Framework (FFF) helps you make a sensor fail on purpose, observe exactly what the controller did, and test a fail-closed contract—without connecting a motor, sensor, or board.

02 / The mental model

A stand-in that remembers what happened

Imagine a controller with two dependencies: sensor_read() reports 1 for ready, 0 for unsafe, or -1 for a read error; actuator_write(int) turns an output on or off. We define a contract: enable only when status equals 1. A bug that treats any nonzero value as success will accidentally enable the actuator when the sensor reports -1.

Sensor fakeReturn 1, 0, or -1 on command
→
Controller under testEnable only on exactly 1
→
Actuator fakeRecord on/off without hardware

The test—not a physical sensor—chooses the fault sequence. FFF's generated fake records call_count, latest arguments, bounded argument history, and a shared call-order history. Tests assert behavior, including dangerous edge cases. The upstream README documents the actual macros and structures.

03 / Evidence versus proposal

Who really uses it?

Documented adoption: Zephyr RTOS

Zephyr's Ztest documentation explicitly documents FFF integration using <zephyr/fff.h>. Zephyr's fake CAN controller and fake regulator are described as FFF implementations with configurable responses and recorded call information.

Evidence type: official project documentation and named test-driver APIs. This establishes real integration, not a claim about deployment in production CAN or regulator firmware.

Verified upstream demonstration: driver tests

The FFF maintainer's driver_testing example is a concrete example within the upstream repository. It demonstrates test usage, not third-party commercial adoption.

Proposal only: RISCue scheduler and HAL tests, TinyTMR fault-injection seams, VeloSim bridge adapter callbacks. No evidence reviewed here shows these projects currently link FFF.

Evidence discipline: A popular pattern (using mocks in embedded systems) is not proof that a named product uses this exact library. Only the specifically linked Zephyr documentation and official FFF example are claimed as verified use.

04 / Behind the macros

Small enough to fit in your head, not automatically in your RAM budget

FAKE_VALUE_FUNC

Creates a free-function fake that returns a configured value or sequence, along with a named state object. FAKE_VOID_FUNC does the same for a function with no return value.

SET_RETURN_SEQ

Supplies a caller-owned array of return values. The last element repeats when exhausted. That array must remain alive while the fake can use it.

RESET_FAKE

Clears one fake's state before a case. FFF_RESET_HISTORY() separately clears the global call-order history. Reset both for isolated tests.

FFF's current checked header defaults to 50 saved argument entries per fake and 50 shared call-history slots; these are compile-time configuration macros (FFF_ARG_HISTORY_LEN and FFF_CALL_HISTORY_LEN). Our example overrides both to 4 and 8 before including the header. Note that some README prose refers to ten argument-history entries; the checked header is authoritative for this pinned snapshot.

FFF state lives in generated structs and static/global storage, not in an automatically allocated heap-backed history container. That does not prove that the whole test process makes no allocations; custom fakes and test frameworks can allocate. Moreover, call_count keeps increasing while stored arguments stop at capacity. The shared call log also stops at capacity—neither one is a rolling recorder.

Changing these macros across translation units that share fake declarations can cause incompatible structure layouts. Centralize configuration and define each fake in exactly one implementation unit; use DECLARE_FAKE_* in shared headers and DEFINE_FAKE_* in source files when splitting a suite. Never compile the test fake into the flight or embedded production image unintentionally.

06 / Runnable host-side experiment

A real C++20 test harness

This is a deliberately self-contained, proposed application seam. It injects five sensor readings and checks the output, retained arguments, dropped-argument count, and global call-history saturation. It does not depend on GoogleTest and intentionally uses explicit checks rather than assert(), so -DNDEBUG does not silently erase its test logic.

test_controller.cppHost test · C++20
// test_controller.cpp — host-only C++20 contract test
// Dependency: meekrosoft/fff, pinned to commit 5111c61e1ef7848e3afd3550044a8cf4405f4199
#define FFF_ARG_HISTORY_LEN 4
#define FFF_CALL_HISTORY_LEN 8
#include "fff.h"
#include <cstdio>

DEFINE_FFF_GLOBALS;
FAKE_VALUE_FUNC(int, sensor_read);
FAKE_VOID_FUNC(actuator_write, int);

// Illustrative application seam: 1 means READY; 0 or -1 means NOT READY.
// This is a proposed RISCue-style contract, NOT existing RISCue source.
bool controller_step() {
    const int status = sensor_read();
    const bool safe = (status == 1);
    actuator_write(safe ? 1 : 0);
    return safe;
}

int main() {
    RESET_FAKE(sensor_read);
    RESET_FAKE(actuator_write);
    FFF_RESET_HISTORY();

    // Storage remains alive for the duration of the test.
    int readings[] = {1, 0, -1, 1, 1};
    const bool expected[] = {true, false, false, true, true};
    SET_RETURN_SEQ(sensor_read, readings, 5);

    bool okay = true;
    for (int i = 0; i < 5; ++i) {
        if (controller_step() != expected[i]) okay = false;
    }

    // Every call counted; the first four write arguments retained.
    if (sensor_read_fake.call_count != 5u) okay = false;
    if (actuator_write_fake.call_count != 5u) okay = false;
    const int retained[] = {1, 0, 0, 1};
    for (int i = 0; i < 4; ++i) {
        if (actuator_write_fake.arg0_history[i] != retained[i])
            okay = false;
    }
    if (actuator_write_fake.arg_histories_dropped != 1u) okay = false;

    // Five steps make ten calls; global history holds only eight.
    if (fff.call_history_idx != 8u) okay = false;

    if (!okay) {
        std::fputs("FAIL: contract or bounded-history mismatch\n", stderr);
        return 1;
    }
    std::puts("PASS: fail-closed behavior and bounded FFF histories");
    return 0;
}

Expected test output: PASS: fail-closed behavior and bounded FFF histories. This output is a specified expectation, not a claimed observed run. On any mismatch, the program returns nonzero. For production code, move controller_step() into its own source file so the same implementation can link with real target drivers or with these test fakes.

Technical nuance: this example uses simple C++ free functions; it is not a fake for a class member, virtual method, coroutine, ISR context, or thread-safe event channel. It tests which outputs were requested, not what a real actuator physically did.

07 / Reproducible build

Pin the dependency, quarantine the fake

The upstream CMakeLists.txt declares an interface library target named fff, with upstream test generation disabled by default. Its own CMake configuration sets a C++11 baseline, but the test executable below explicitly requests C++20. The SHA below was read from the upstream master reference on 2026-11-16; no unverified release-version claim is made.

CMakeLists.txtNinja + CTest + fixed upstream commit
# CMakeLists.txt — separate host-side test project
cmake_minimum_required(VERSION 3.24)
project(fff_contract_lab LANGUAGES C CXX)
include(CTest)
include(FetchContent)

# Uses upstream's interface target; upstream tests and header generator
# default to OFF. Pin an immutable commit, not 'master'.
FetchContent_Declare(fff
  GIT_REPOSITORY https://github.com/meekrosoft/fff.git
  GIT_TAG 5111c61e1ef7848e3afd3550044a8cf4405f4199
)
FetchContent_MakeAvailable(fff)

add_executable(fff_contract_lab test_controller.cpp)
target_link_libraries(fff_contract_lab PRIVATE fff)
target_compile_features(fff_contract_lab PRIVATE cxx_std_20)
add_test(NAME fail_closed_contract COMMAND fff_contract_lab)

# Run:
# cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug
# cmake --build build
# ctest --test-dir build --output-on-failure

For offline or controlled-build environments, vendor the pinned fff.h and LICENSE into a test-only third-party directory and use a local include path instead of an online FetchContent step. Keep all generated fakes in the host test target; avoid pulling FFF into the target's shipping build. Check upstream's license notice when redistributing the header.

08 / What FFF does not prove

Precise tests, limited observations

Not thread-safe by default

Shared counters and arrays are unsynchronized. A concurrent multi-producer test can race and invalidate observations. Use single-threaded deterministic seams or explicit external synchronization.

Memory is finite; evidence is partial

When configured capture limits are reached, historical evidence is lost. Use arg_histories_dropped, call_count, and independent test bounds; never assume the saved list is complete.

Mocks are not hardware

FFF cannot validate electrical timing, scheduler preemption, physical actuator behavior, actual fault injection on a board, or worst-case execution time. Separate HIL and target tests remain necessary.

Macro ergonomics

Great for C/free-function boundaries; awkward for C++ overloaded functions, methods, template-heavy APIs, complex types, and signatures with function pointer arguments.

Global reset hygiene

Failure to reset both per-function fakes and the shared history can make tests order-dependent. A single generated fake definition must own storage across linked units.

Performance relevance

Fixed-array history is appealing, but the measurement applies to the test double, not the genuine ISR/RTOS implementation. Do not turn mock timings into WCET evidence.

09 / Project-specific opportunities

Where would it earn its keep?

RISCue RTOS — proposed priority: high

Put a free-function seam around timer reads, interrupt-enable requests, or actuator output commands. Inject a timer failure or absent peripheral and assert fail-closed transitions. Combine with your separate deterministic state-machine tests; do not replace them.

VeloSim — proposed priority: medium

Use fakes at a C ABI or C-style adapter boundary to inject failed callbacks and record call ordering. For VeloSim's C# and C++ internal interfaces, choose fakes at narrow native boundaries rather than pretending FFF can replace managed abstractions directly.

Requirements traceability — proposed

Name a unit test after its requirement ID. Record setup, injected fault, expected output and failure observation. FFF supplies evidence of calls; the report-to-requirement mapping still belongs to your test infrastructure.

SharpHDL / TinyTMR — proposed

Fake host-facing board services or a deterministic I/O boundary before hardware build or place-and-route. This is not a substitute for formal checking, independent simulation, or measured synthesis evidence.

10 / Adoption gate

A six-test qualification plan

  1. Reproduce: fetch the pinned upstream SHA, configure CMake/Ninja on Windows and Linux, compile and run the exact example above.
  2. Negative control: change status == 1 to status != 0; confirm the injected -1 reading causes test failure.
  3. Reset isolation: run the test twice in one process with explicit resets; verify no state leaks between cases.
  4. History boundary: check exactly four and five actuator calls and eight and ten global calls; document the first-entry retention behavior.
  5. Memory and concurrency: inspect static layout/footprint, prohibit unsynchronized concurrent fake use, and measure any test process allocations separately.
  6. Target independence: prove that the production firmware link map contains no FFF symbols and that hardware-in-the-loop/target timing tests remain in the plan.
