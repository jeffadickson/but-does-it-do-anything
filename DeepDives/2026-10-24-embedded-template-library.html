Embedded Template Library (ETL)

STL-like containers and event-oriented building blocks with bounded storage, aimed at predictable embedded C++.

Technical focus: deterministic capacity, message routers, state machines and RTOS integration.

What problem does it solve?

In embedded software, unbounded heap use makes memory exhaustion and worst-case behavior harder to reason about. The Embedded Template Library (ETL), maintained by John Wellbelove, supplies familiar container interfaces whose capacity is established at compile time. It also includes messaging, state-machine, utility and type-trait facilities, designed to work without an STL dependency. ETL supports older C++ as well as modern C++; this report focuses on C++20.

For a practical example, etl::vector<Sample, 64> carries its elements in fixed-capacity storage. If used after startup, it does not secretly grow by allocating heap memory. The application must still define an overflow policy and verify timing.

How it works

Bounded containers

Most non-intrusive ETL containers hold elements in internal fixed-capacity storage, with full() and available() for capacity checks. A local vector’s backing space belongs to its object and therefore may consume stack space; static placement or owning-task storage is often preferable for larger buffers. Contiguous storage improves locality, but copying a vector copies its elements.

Messages and dispatch

etl::message<ID> defines typed message identities; etl::message_router uses CRTP and declared message types to dispatch to on_receive handlers. ETL also provides message buses, brokers, packets, and finite/hierarchical state machines. A router’s dispatch is not an RTOS message queue: asynchronous scheduling, ownership and thread safety remain integration responsibilities.

Scope of deterministic behavior

Fixed capacity bounds the storage of specific containers, not the stack usage, scheduler latency, interrupt latency or WCET of the full application. Intrusive containers and some external-buffer variants have different storage semantics. Error handling is configurable; never assume a full-capacity insertion is safe without checking the chosen profile and configuration.

Where it is actually used

Documented, concrete maintainer integrations: the ETL repository contains an Arduino integration/example tree, a Zephyr-related tree, and maintained example programs. Its own release notes explicitly record the addition of Arduino examples and queued message router/FSM example updates. These are evidence of maintained integration and demonstrations, not proof that a named flight product or a particular commercial device ships ETL.

Unverified adoption: this review did not establish an independently documented deployed-product case. Do not claim NASA, JPL, or a particular RTOS product uses it without separate evidence.

Small practical C++20 example

A controller receives a timestamped event, appends it only if the buffer is not full, and can clear the buffer. This uses a fixed-size vector and router, without a dynamic container allocation in the demonstrated logic.

#include <etl/vector.h>
#include <etl/message.h>
#include <etl/message_router.h>
#include <cstdint>

struct Tick : etl::message<1> { std::uint32_t now; };
struct Reset : etl::message<2> {};

class Controller : public etl::message_router<Controller, Tick, Reset> {
public:
  etl::vector<std::uint32_t, 8> timestamps;
  void on_receive(const Tick& m) {
    if (!timestamps.full()) timestamps.push_back(m.now);
  }
  void on_receive(const Reset&) { timestamps.clear(); }
  void on_receive_unknown(const etl::imessage&) {}
};

int main() {
  Controller controller;
  Tick tick; tick.now = 42;
  controller.receive(static_cast<const etl::imessage&>(tick));
  Reset reset;
  controller.receive(static_cast<const etl::imessage&>(reset));
}

Review caution: this example is intentionally illustrative and was inspected against the documented APIs, but it has not been compiled or run against a pinned ETL release here. Validate message construction and route overload resolution with your chosen tag and compiler before adopting it. In a production queue, define whether overflow means reject, overwrite, count-and-drop, or fault.

Minimum validation plan

  1. Pin a release tag; build with GCC/Clang/MSVC where applicable using C++20, -Wall -Wextra -Werror where supported.
  2. Exercise 0, 1, 8 and 9 incoming events; verify no out-of-bounds insertion and an explicit overflow count.
  3. Instrument operator new or use a linker map to show no allocation in the event path.
  4. Verify same-tick delivery order and handler reentrancy under the RTOS scheduler; run sanitizers on the host.

Tradeoffs and pitfalls

  • Pros: bounded storage; STL-like APIs; header-only adoption; message routing and state machines; MIT license; explicit compile-time capacity.
  • Costs: each instantiation reserves capacity even when empty, potentially increasing RAM or stack consumption; capacity changes require recompilation.
  • Safety: no claim of implicit thread safety, lock-free behavior, interrupt safety, or certified WCET. Audit use across tasks and ISRs.
  • Interoperability: standard-library code expecting std::vector, allocator-aware APIs, exceptions or specific iterator behavior may need adapters.
  • Maintenance: ETL release 20.49.0 notes include corrections to vector, variant and profile defaults; pin and regression-test, especially if updating from older versions.

Licensing and CMake / Ninja integration

ETL is MIT licensed. Preserve its copyright and permission notice when distributing a covered copy or substantial portions. ETL’s README documents add_subdirectory(etl), installed find_package, and FetchContent configurations. Pin a tag or immutable commit for reproducibility.

cmake_minimum_required(VERSION 3.24)
project(etl_probe LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
add_subdirectory(external/etl)
add_executable(etl_probe main.cpp)
target_link_libraries(etl_probe PRIVATE etl::etl)

# Configure: cmake -S . -B build -G Ninja
# Build:     cmake --build build

The etl_profile.h file controls target assumptions (for example, bare metal and no STL). The upstream README describes defaults and platform hooks for timekeeping and printing when those facilities are used. For RISC-V, check compiler builtin support, exceptions policy, section placement and whether the selected ETL feature invokes platform-specific hooks. Compare generated binary size and RAM maps before and after integration.
