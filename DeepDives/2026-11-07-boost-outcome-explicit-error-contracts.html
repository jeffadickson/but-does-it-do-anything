01 · Engineering verdict

A function that returns a magic number on failure may leave its caller guessing. Boost.Outcome expresses success or a specific error in one return type. In exception-disabled C++20 firmware, that creates a useful explicit boundary between untrusted wire bytes and the active object that must decide what to do next.

Recommendation: Prototype a bounded result-returning telemetry decoder for a single-owner RISCue message handler. Preserve its error category in a VeloSim replay trace. This is an engineering proposal, not an existing integration.

02 · Value, error, and observation policy

basic_result<T,E,Policy> stores an alternative success value T or error E. The sample chooses a small enumeration as E, so the rejection carries a stable, testable code instead of an allocated diagnostic string. has_value() and has_error() identify which state exists.

Success branch

Four bytes pass length, version, reserved-bit and mode checks. The returned Packet contains a 16-bit sequence and two-bit mode.

Failure branch

Input fails one check and returns Error::wrong_length, wrong_version, reserved_bits or bad_mode.

The policy is part of the contract

We explicitly select outcome::policy::terminate rather than relying on a default policy that may throw. A wrong wide observation terminates. A narrow assume_value() or assume_error() must be used only after checking the state. Other policies such as all_narrow can result in undefined behavior when a nonexistent alternative is accessed.

Not magic: a result type is not a scheduler, thread-safe queue, memory allocator, or proof of constant worst-case execution time. Outcome's BOOST_OUTCOME_TRY macro can propagate errors between functions, but it is not required for the example here.

04 · Executable C++20 parser and tests

The following complete packet.cpp example was compiled and executed with local Boost 1.83, C++20, exceptions and RTTI disabled. It uses std::span and a small error enumeration. The test returns nonzero on failure even under -DNDEBUG (unlike a bare assert).

#include <boost/outcome.hpp>
#include <array>
#include <cstdint>
#include <span>
#include <cstdio>

namespace outcome = boost::outcome_v2;
enum class Error : std::uint8_t {
    wrong_length, wrong_version, reserved_bits, bad_mode
};
struct Packet { std::uint16_t sequence; std::uint8_t mode; };
template<class T> using Result =
    outcome::basic_result<T, Error, outcome::policy::terminate>;

Result<Packet> parse(std::span<const std::uint8_t> b) noexcept {
    if (b.size() != 4) return outcome::failure(Error::wrong_length);
    if (b[0] != 1) return outcome::failure(Error::wrong_version);
    if ((b[1] & 0xfc) != 0) return outcome::failure(Error::reserved_bits);
    if ((b[1] & 0x03) == 3) return outcome::failure(Error::bad_mode);
    auto seq = static_cast<std::uint16_t>(
        (static_cast<unsigned>(b[2]) << 8) | b[3]);
    return outcome::success(Packet{seq, static_cast<std::uint8_t>(b[1])});
}
int main() {
    constexpr std::array<std::uint8_t,4> a{1,2,0x12,0x34};
    constexpr std::array<std::uint8_t,4> b{1,0x82,0x12,0x34};
    constexpr std::array<std::uint8_t,4> c{4,2,0x12,0x34};
    constexpr std::array<std::uint8_t,4> d{1,3,0x12,0x34};
    constexpr std::array<std::uint8_t,3> e{1,2,0x12};
    auto ra = parse(a); auto rb = parse(b); auto rc = parse(c);
    auto rd = parse(d); auto re = parse(e);
    if (!ra.has_value() || ra.assume_value().sequence != 0x1234 ||
        ra.assume_value().mode != 2) return 1;
    if (!rb.has_error() || rb.assume_error() != Error::reserved_bits) return 2;
    if (!rc.has_error() || rc.assume_error() != Error::wrong_version) return 3;
    if (!rd.has_error() || rd.assume_error() != Error::bad_mode) return 4;
    if (!re.has_error() || re.assume_error() != Error::wrong_length) return 5;
    std::puts("PASS: five vectors");
}
State discipline: assume_value() and assume_error() are narrow observers. Never call them without checking the corresponding state. Keep validation ordering explicit; length is checked before any byte access.

05 · CMake/Ninja and licensing

Outcome's demonstrated API is header-based and does not require a compiled Outcome object library. The following CMake configuration worked with a locally installed Boost 1.83 CMake package. For a flight build, pin the exact revision and build using the target compiler.

cmake_minimum_required(VERSION 3.20)
project(outcome_contract LANGUAGES CXX)
include(CTest)
find_package(Boost 1.83 REQUIRED)
add_executable(outcome_contract packet.cpp)
target_compile_features(outcome_contract PRIVATE cxx_std_20)
target_link_libraries(outcome_contract PRIVATE Boost::headers)
if(CMAKE_CXX_COMPILER_ID MATCHES "GNU|Clang")
  target_compile_options(outcome_contract PRIVATE
    -Wall -Wextra -Wpedantic -Werror -fno-exceptions -fno-rtti)
endif()
add_test(NAME outcome_contract COMMAND outcome_contract)

# cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
# cmake --build build
# ctest --test-dir build --output-on-failure

Local CMake emitted a development warning regarding CMP0167 / FindBoost changes, but configuration, Ninja compilation and CTest completed. Use Boost's packaged CMake configuration intentionally when upgrading toolchains.

06 · Source evidence versus imagined adoption

Verified source examples

Boost's own Outcome documentation provides a file-reader returning result<T> and an error-propagation example using BOOST_OUTCOME_TRY. A separately published Boost.Asio adapter contains actual code using Outcome return types. These demonstrate documented use patterns; they do not prove deployment by any mission or company.

A Debian-packaged Ceph source tree vendors boost/outcome.hpp. This proves the header's presence in the tree, not that Ceph production call sites use Outcome.

Suggested future use only

RISCue: turn typed parser errors into rejection events without exceptions. VeloSim: record the exact input bytes and error code for deterministic playback. SharpTestBench: create requirements-linked golden tests. None is claimed to contain a verified Boost.Outcome integration.

Source-level examples, package availability, actual adoption and operating history are different evidentiary categories. This report makes no unsupported production adoption claims.

07 · Alternatives and engineering hazards

ChoiceAdvantageConstraint
Boost.OutcomeTyped error, explicit policy, optional TRY propagationDependency, macro review, policy choices and target qualification
std::expected (C++23)Standardized expected-like return valueNot standard C++20; standard-library deployment must be checked
tl::expectedSingle-header expected-style alternative for earlier C++Separate API and test matrix; different CC0 license
Error enum + output pointerMinimal dependency and straightforward C boundaryTwo channels to audit; an unchecked output may be stale

Hazards that still require engineering

Wrong-state access: an unchecked observer can breach a precondition. Error erasure: generic failures hide the actual violated contract. Payload lifetime: a returned span or pointer does not own underlying storage. Timing: an explicit result does not prove bounded runtime if called operations allocate, lock or format strings.

Review limitation worth recording: An expanded exploratory chain using BOOST_OUTCOME_TRY passed GCC Debug and Clang executions but exited with test status 4 under GCC 14.2 -O3 -DNDEBUG. Its root cause was not established. No defect is attributed to Boost; the expanded chain is not included among qualified examples. The simpler published parser passed its independent Release/Clang tests. Investigate the chain separately before applying that pattern.

08 · RISCue / VeloSim qualification proposal

  1. Specify a stable error code for each invalid packet condition and connect codes to verifiable requirements.
  2. Keep parsing under one execution owner. Pass a rejection event through the RTOS-approved message channel rather than sharing mutable state.
  3. Compile target firmware with actual toolchain and exception/RTTI settings; measure sizeof(Result<Packet>), symbol dependencies and code size.
  4. Use the five golden vectors, then fuzz packet lengths, reserved-bit combinations, fault precedence and unknown versions.
  5. Instrument whole-program allocations and worst-case latency. Compare with a hand-written enum-and-output-parameter implementation.
  6. Replay bytes and failure codes under VeloSim; reject only if the audit trail and timing constraints pass.
Decision gate: Choose Outcome only if explicit contract quality and diagnostic traceability justify its dependency and qualification cost. A compact API alone is not a sufficient reason to change flight software.

09 · Review and verification record

Local verification used GCC 14.2.0, Clang 17.0.0, Boost 1.83. The five-vector parser passed a GCC CMake/Ninja Release build with -fno-exceptions -fno-rtti -Werror and CTest. A separate Clang O2 build ran successfully. This report is self-contained: no CDN, font download, external stylesheet or JavaScript library is required.

Not verified: Boost 1.92 compilation, whole-program allocation instrumentation, embedded-target worst-case execution time, upstream's complete test suite, verified external production adoption, or flight qualification.
