01 / Decision

Excellent host-side evidence. Not hard-real-time proof.

If you need to compare an event-selection loop, a bounded queue operation, a parser, or a memory-pool fast path, nanobench is worth trying. Its v4.6.0 compare() interface measures competing operations in interleaved rounds, reducing systematic error from gradual frequency changes. The library itself is a benchmark harness, not an RTOS component or a worst-case execution-time analyzer. [1–3]

02 / Experimental method

When a benchmark races the CPU governor

Suppose algorithm A runs first, then B. During the test the processor changes frequency, its caches warm up, and background tasks appear. The resulting difference mixes algorithm and when it was measured. More decimal places do not fix a biased experiment.

Sequential A → B

All measurements of A happen earlier than all measurements of B. A smooth drift in clock rate can masquerade as a speedup or regression.

Confounded by time

Interleaved A–B–B–A

Mix the candidates throughout the same period. A balanced ordering can largely cancel a linear drift. It does not magically remove noise, thermal effects, or mismatched workloads.

Better controlled

Nanobench's compare() uses randomized cyclic Latin-square blocks, paired log-ratio measurements, and a documented sign-test interval. For two alternatives, its balancing yields ABBA/BAAB-style ordering. The teaching simulator below uses a simpler deterministic schedule: it is not nanobench's implementation or a claim to reproduce its statistical confidence intervals. [2, 4]

Why not display fabricated nanoseconds or fake 95% confidence?

Real ns/op depends on a specific processor, compiler, build flags, frequency and workload. This toy lab displays fictional latency units and comparative ratios only. A confidence interval requires an explicit statistical model and sampling procedure; the lab does not pretend to implement nanobench's published significance method.

05 / Concrete C++20 application

Two implementations, one dispatch contract

Consider a 32-priority ready mask in a hypothetical RISCue-like scheduler. The lowest set bit wins; an all-zero mask means “no event” and returns 32. A portable loop and std::countr_zero implement the same contract. Test functional equivalence before measuring. Here is a complete host benchmark, using the actual v4.6.0 compare() interface.

// priority_bench.cpp — C++20, host-only benchmark, nanobench v4.6.0
#include <nanobench.h> // Implementation is compiled by the CMake target.
#include <array>
#include <bit>
#include <cstddef>
#include <cstdint>
#include <iostream>

unsigned scan_priority(std::uint32_t mask) noexcept {
    for (unsigned bit = 0; bit < 32; ++bit) {
        if ((mask & (std::uint32_t{1} << bit)) != 0) {
            return bit;
        }
    }
    return 32; // No ready events.
}

unsigned bit_priority(std::uint32_t mask) noexcept {
    // C++20 specifies 32 for countr_zero(uint32_t{0}).
    return static_cast<unsigned>(std::countr_zero(mask));
}

int main() {
    // Correctness is separate from speed. Never compare broken code.
    for (std::uint32_t mask = 0; mask < 65536u; ++mask) {
        if (scan_priority(mask) != bit_priority(mask)) return 2;
    }
    for (unsigned bit = 0; bit < 32; ++bit) {
        const auto mask = std::uint32_t{1} << bit;
        if (scan_priority(mask) != bit_priority(mask)) return 3;
    }
    if (scan_priority(0u) != 32u || bit_priority(0u) != 32u) {
        return 4;
    }
    std::cout << "Correctness: 65,536 masks + 32 one-hot cases + zero\n";

    // Generate identical deterministic inputs for both candidates.
    std::array<std::uint32_t, 256> masks{};
    std::uint32_t state = 0x9e3779b9u;
    for (auto& mask : masks) {
        state ^= state << 13;
        state ^= state >> 17;
        state ^= state << 5;
        mask = state;
    }
    masks[0] = 0u; // Explicit empty-ready-set workload.

    std::size_t scan_index = 0;
    std::size_t bit_index = 0;
    const auto scan = [&] {
        const auto mask = masks[(scan_index++) & 255u];
        ankerl::nanobench::doNotOptimizeAway(scan_priority(mask));
    };
    const auto bits = [&] {
        const auto mask = masks[(bit_index++) & 255u];
        ankerl::nanobench::doNotOptimizeAway(bit_priority(mask));
    };

    // compare() pairs and interleaves candidates. This is a HOST
    // microbenchmark; its timings are NOT an RTOS WCET qualification.
    ankerl::nanobench::Bench()
        .performanceCounters(false) // Portable Windows/Linux/macOS table.
        .epochs(52)                  // More rounds for the comparison.
        .compare("portable 32-bit scan", scan,
                 "C++20 countr_zero", bits);
    return 0;
}
Interpretation: A faster bit scan on one compiler does not justify replacing a production scheduler path without checking architecture-specific code generation, actual priority semantics, zero handling, target timing and integration tests. Both candidates must receive equivalent input distributions; this example cycles separate indices over the same 256 precomputed masks.

Review scope: the two priority-selection kernels and their 65,569 contract checks were compiled and executed using GCC and Clang in C++20 mode. The complete nanobench-linked program was source-reviewed against its official v4.6.0 API, but not compiled against the downloaded library in this execution environment.

06 / Build recipe

Pin the library. Keep it off target firmware.

Place the C++ sample in priority_bench.cpp beside this CMakeLists.txt. The upstream CMake target already compiles ANKERL_NANOBENCH_IMPLEMENT in its own translation unit, so do not define that macro again in your sample.

cmake_minimum_required(VERSION 3.20)
project(riscue_priority_bench LANGUAGES CXX)

include(FetchContent)
FetchContent_Declare(
    nanobench
    GIT_REPOSITORY https://github.com/martinus/nanobench.git
    # Pinned v4.6.0 commit, verified against upstream tag.
    GIT_TAG b709728dba4df0356d467abfb0ba20781a8031c0
)
FetchContent_MakeAvailable(nanobench)

add_executable(priority_bench priority_bench.cpp)
target_compile_features(priority_bench PRIVATE cxx_std_20)
target_link_libraries(priority_bench PRIVATE nanobench)

# Use a release build for meaningful comparisons.
# Do not define ANKERL_NANOBENCH_IMPLEMENT in priority_bench.cpp:
# the upstream CMake target already compiles that implementation.
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
# Linux / macOS:
./build/priority_bench
# Windows (from a compiler-configured PowerShell):
.\build\priority_bench.exe

On Windows, run from a PowerShell or terminal where Visual Studio's cl or another selected C++20 compiler and Ninja are configured. First-time FetchContent configuration needs network access; CI can use a cached/pinned checkout or vendored source. Keep the benchmark executable as a separate host-only CMake target. For a cross-compiled firmware tree, do not pull it into the target binary or link its host-side dependencies.

Alternative upstream-documented integration: include the release nanobench.h and put #define ANKERL_NANOBENCH_IMPLEMENT in exactly one dedicated host-side .cpp. Do not mix that pattern with the compiled upstream CMake target. [3, 5]

07 / Evidence, not association

Where it is actually used

VERIFIED SOURCE ADOPTION

ankerl::unordered_dense benchmark suite

Martin Leitner-Ankerl's unordered_dense quick_overall_map.cpp includes third-party/nanobench.h and calls ankerl::nanobench::Bench().run() for hash-map insertion/erase, iteration, build, churn and lookup workloads. That is direct source evidence of an actual benchmark harness, rather than a generic claim about who uses nanobench.

The nanobench project's own v4.6.0 comparison test directly exercises epochs(52).compare() and the significance API. That proves the example API exists; it is self-use, not independent third-party adoption. [4, 6]

PROPOSAL, NOT EVIDENCE

RISCue / VeloSim

Benchmark priority-bit selection, event-queue operations, or simulation step kernels on a pinned host and compiler. There is no claim that these repositories currently use nanobench.

PROPOSAL, NOT EVIDENCE

MemForge / BomR

Compare host memory-pool fast paths or deterministic resistor-search kernels. This is a suggested experiment, not documented existing adoption or a promise of speedup.

For real hardware, combine this with target-on-board traces, cycle-counter measurements where appropriate, scheduler response-time analysis, sustained load tests and allocation instrumentation. Preserve compiler flags, target CPU, data distributions and commit hashes with every recorded result.

09 / What can go wrong

Tradeoffs a benchmark can hide

Measurement overhead

doNotOptimizeAway and lambda invocation may be significant beside a two-instruction operation. Measure batches and inspect optimized assembly; beware of measuring the harness instead of the workload.

Workload fidelity

A cache-hot array of 256 masks is not a full scheduler. Vary mask occupancy, zero frequency, realistic event arrival patterns and memory contention.

Statistical ambiguity

More digits or a small err% do not prove a causal difference. Prefer a paired comparison and its reported interval; repeat across machines and days.

Not a target runtime

The library uses host timing, reporting and benchmark infrastructure; it is not proposed for the firmware image or zero-allocation ISR code.

Unresolved performance questions: No actual timing or memory measurements of the illustrated priority-selector pair were taken here. The HTML simulator is synthetic. The whole program has not been compiled or run with the nanobench dependency, and no target microcontroller or real-time worst-case analysis was exercised.

10 / Acceptance criteria

A fair first experiment for RISCue

  1. Freeze a behavioral contract: lowest ready priority wins, empty mask returns 32, fixed 32-bit semantics. Add tests for all 65,536 low masks and every one-hot bit.
  2. Build twice: Release with compiler/CPU tuning documented, and sanitizer-enabled correctness builds with the optimization intent stated separately.
  3. Fix test inputs: include sparse/dense/empty ready masks and realistic event burst patterns; exclude setup/allocations only when that matches the production fast path.
  4. Use paired measurement: start with 52 epochs, inspect the library's interval and significance verdict, rerun reversed names/order, record outliers and machine utilization.
  5. Look at generated code: disassemble both callables; compiler lowering of std::countr_zero is target dependent.
  6. Qualify hardware separately: run the real target at defined frequency with interrupt and scheduling interference, then check latency upper bounds, stack, allocations and power.

Decision gate: adopt a change only if functional parity, reproducible target-relevant performance improvement, and all timing/memory budgets are independently established. Nanobench is one piece of that evidence.
