01 · A filesystem for imperfect shutdowns

littlefs gives a microcontroller familiar files and directories while designing around flash erase rules, limited RAM and unexpected power loss. It can use caller-provided buffers, making it relevant to an allocation-free firmware architecture. [1]

Imagine updating a device’s calibration settings. A reset between two flash writes should not leave an unreadable storage volume. littlefs tackles the storage machinery beneath that problem; your application still defines which version of the settings is acceptable.

Why I chose it for you: the strongest connection is its testability. Your deterministic simulator could explore storage interruption points with the same discipline you apply to scheduler interleavings. This is a proposed experiment, not an existing StateForge integration.

Research snapshot: the official release page lists v2.11.3 as latest when checked. Pin a tag and commit for reproducible evaluation; the architecture links below also include moving upstream documentation. [2]

02 · How it works

Flash programming and erasing have different granularity and cost. Updating bytes in place is therefore a poor model for reliable storage. littlefs combines metadata pairs with copy-on-write file structures: small changes can be recorded without rewriting the whole filesystem. [3]

ApplicationOpen, write, close, rename
littlefsMetadata commits + file blocks
Block driverRead, program, erase, sync

Its on-disk specification describes paired metadata blocks, revision counts, tagged records and CRC-protected commits. These let recovery distinguish usable state from an incomplete update. File content uses a different structure from directory metadata. The format is worth reading alongside the design rationale. [4]

MemoryConfigurable boundsCaches and lookahead space are selected by configuration.
WearDynamic distributionAllocation spreads wear across available blocks.
RecoveryCommit boundariesDurability depends on completing the relevant storage operations.

Design properties: [1], [3]. Bounded memory does not establish a worst-case operation time.

04 · Why it may interest you

Proposed applications

  • State-machine persistence: evaluate durable configuration or a versioned checkpoint. Persist defined application data; reconstruct queues, ownership and OS objects after boot rather than serializing live kernel memory.
  • Active-object architecture: route storage requests through one worker with fixed request and response queues. Give flash operations a scheduling budget outside deadline-sensitive handlers.
  • RISCue portability: keep a board block-driver interface beneath the storage service. It could be exercised against both simulated flash and a target implementation without introducing another scheduler.
  • Traceability: map a proposed requirement such as “an interrupted replacement yields the previous or complete new record” to named crash-point tests and retained disk images.
  • C#/.NET 10 tooling: a Native AOT runner could coordinate native test executables in bounded parallel batches and emit deterministic JSON evidence. Keep each run’s flash image independent.

These are my engineering suggestions for your projects. The adoption evidence above is separate.

05 · A small C++20 persistence operation

Assume a mounted filesystem with cache_size=256 and static mount buffers. This illustrative function writes four explicitly encoded bytes to a temporary file, closes it successfully, then replaces the named record. It supplies the file cache through lfs_file_opencfg. [8]

#include "lfs.h"
#include <cstdint>
extern lfs_t fs; // Already mounted; cache_size is 256.
static unsigned char file_cache[256];

// Serialize calls through one storage worker.
int store_epoch(std::uint32_t epoch) {
    lfs_file_t file{};
    lfs_file_config options{};
    options.buffer = file_cache;
    unsigned char data[4];
    for (unsigned i=0; i<4; ++i)
        data[i] = static_cast<unsigned char>(epoch >> (8*i));
    int rc = lfs_file_opencfg(&fs, &file, "epoch.tmp",
        LFS_O_WRONLY | LFS_O_CREAT | LFS_O_TRUNC, &options);
    if (rc < 0) return rc;
    const auto written = lfs_file_write(&fs, &file, data, sizeof data);
    const int closed = lfs_file_close(&fs, &file);
    if (written < 0) return static_cast<int>(written);
    if (written != static_cast<lfs_ssize_t>(sizeof data)) return LFS_ERR_IO;
    if (closed < 0) return closed;
    return lfs_rename(&fs, "epoch.tmp", "epoch.bin");
}

Example status: authored for this article; not compiled or run here. The board driver and mount setup are intentionally outside this fragment. Only one worker may use this shared cache. On boot, validate the record’s length and application schema; ignore leftover temporary files until a deliberate cleanup policy runs.

The replacement protocol is a proposed application pattern built on littlefs’s documented atomic rename and close/sync commit behavior. Its old-or-new recovery property still needs fault-injection tests on the selected driver and geometry. [1]

06 · An experiment worth doing first

The upstream emulated block device exposes write-operation power-cut counters, configurable bad-block behavior, a power-loss callback and I/O counters. It also offers out-of-order power-loss behavior. This is unusually useful infrastructure for exploring recovery rather than only testing successful reads and writes. [9]

  1. Start from the same image containing a valid old record.
  2. Interrupt the replacement at each relevant program/erase boundary; discard volatile filesystem objects.
  3. Remount from the surviving bytes and classify the recovered record: old, complete new, missing, malformed or mount failure.
  4. Require the application’s stated outcome; retain the seed, geometry, cut point, return codes and image hash for failures.
  5. Repeat with nearly full storage, changing directory sizes and selected device faults. Measure erase counts and latency distributions separately.

The sequence above is a proposed acceptance plan. Virtual operation counts make cases reproducible; they do not reproduce every analog failure mode of a flash part. The upstream host emulator is test infrastructure and may allocate; the firmware no-allocation claim must be evaluated separately. [9]

07 · What you trade for resilience

PropertyEngineering consequence
Copy-on-write and metadata maintenancePlan free-space margin and measure compaction/erase paths. A bounded cache is not a latency guarantee. [3]
Dynamic wear levelingDo not describe it as perfect wear equality or assume cold occupied blocks are continuously relocated. [3]
Filesystem atomic operationsDo not infer a transaction spanning multiple unrelated application files. Define an explicit record/commit protocol. [1]
Own on-disk formatProvisioning and diagnostic tools must understand the format; ordinary desktop FAT tooling is not interchangeable. [4]
Driver-dependent durabilityQualify geometry, ordering and actual device behavior. A successful host simulation is only one layer of evidence. [8]

08 · Integration and licensing

For an allocation-free build, define LFS_NO_MALLOC, provide mount read/program/lookahead buffers and a cache for each concurrently open file. Audit the board driver, logging and synchronization paths too. The utility header allows diagnostic/configuration overrides; disabling the library allocator alone does not certify the whole firmware image. [8] [10]

A CMake/Ninja integration proposal: pin the upstream source, compile lfs.c and lfs_util.c as a C target, and apply consistent configuration definitions to that target and its consumers. Keep the board callbacks in a separate target. Let Ninja track source dependencies; host-side qualification should be an explicit target. This is an integration sketch, not a claim that upstream supplies this exact CMake layout.

The core license is BSD-3-Clause. Source redistributions retain notices and conditions; binary redistributions reproduce the required notices/disclaimer in accompanying materials. Contributor names do not grant endorsement rights. Check platform wrappers and dependencies separately. [11]

My evaluation recommendation: begin with a small configuration-record experiment and systematic interrupted replacements. A successful result would justify exploring a storage active object; it would not yet justify persistent execution-state recovery or a hard real-time claim.
