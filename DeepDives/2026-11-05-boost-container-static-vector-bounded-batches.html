01 / executive decision

Why this is worth a prototype

What it guarantees

The number of elements never exceeds template capacity N; element storage lives inside the container object. No element-buffer heap allocation is needed, and size() changes as objects are inserted or removed. Boost documentation.

What it does not guarantee

Zero allocations by your element type, constant-time middle erasure, thread safety, lock-free behavior, deterministic whole-system timing, or graceful overflow if unchecked.

One-line API: boost::container::static_vector<Event, 6> pending;. It is much closer to std::vector ergonomics than a manual array-plus-count, but its physical storage never grows.

Scope: this is a new topic relative to the existing ETL, Boost.Intrusive, and Boost.Lockfree SPSC reports. The question here is in-place bounded sequences and explicit capacity policy, not inter-thread message passing or intrusive lifetime.

02 / mental model

Allocated once in the object, constructed when needed

Imagine a toolbox built with six compartments. A normal std::vector may buy a larger toolbox when it fills. static_vector has only six compartments, permanently. Unlike std::array<Event,6>, it constructs only the currently occupied elements; size() can be zero through six.

OperationTypical boundConsequence
Append within capacityO(1)No internal allocation; element constructor may still do work
Read by indexO(1)Contiguous layout and random access
Pop lastO(1)Destroys the last live element
Find and erase a middle elementO(N)Remaining elements shift; references/iterators may be invalidated
Append when fullRejected by our guardDefault library policy otherwise reports capacity error, commonly via bad_alloc with exceptions

Because storage lives inside the object, copying or moving the container is not simply moving one heap-buffer pointer. Also, declaring a huge static_vector as a local variable can exhaust a thread's stack; consider static lifetime or owner-provided placement where appropriate.

Critical overflow warning: Boost's throw_on_overflow<false> is not a safe “return failure” option. Boost documents undefined behavior when overflow is allowed through this mode (an assertion may run first). Do not choose it as an error-handling strategy. Primary source.

    04 / reproducible implementation

    Complete, tested C++20 example

    This single-owner ready batch deliberately checks size() == capacity() before appending. It models a bounded work list, not the complete RISCue scheduler. Priority 0 is highest; sequence number breaks ties. The demonstration uses 32-bit-ish unsigned sequencing and therefore does not handle wraparound—see limitations.

    #include <boost/container/static_vector.hpp>
#include <algorithm>
#include <cstddef>
#include <cstdio>
#include <cstdlib>
#include <optional>

#define CHECK(expr) do { if (!(expr)) std::abort(); } while (false)

struct Event {
    unsigned id;
    unsigned priority; // 0 is highest
    unsigned sequence; // FIFO when priorities tie
};

class ReadyBatch {
    static constexpr std::size_t limit = 6;
    boost::container::static_vector<Event, limit> events_{};
    unsigned next_sequence_ = 0;

public:
    bool post(unsigned id, unsigned priority) noexcept {
        if (events_.size() == events_.capacity()) return false;
        events_.push_back(Event{id, priority, next_sequence_++});
        return true;
    }

    bool cancel(unsigned id) noexcept {
        auto it = std::find_if(events_.begin(), events_.end(),
                               [id](const Event& e) { return e.id == id; });
        if (it == events_.end()) return false;
        events_.erase(it);
        return true;
    }

    std::optional<Event> dispatch() noexcept {
        if (events_.empty()) return std::nullopt;
        const auto it = std::min_element(events_.begin(), events_.end(),
            [](const Event& a, const Event& b) {
                return a.priority < b.priority ||
                    (a.priority == b.priority && a.sequence < b.sequence);
            });
        const Event selected = *it;
        events_.erase(it);
        return selected;
    }

    std::size_t size() const noexcept { return events_.size(); }
    std::size_t capacity() const noexcept { return events_.capacity(); }
};

int main() {
    ReadyBatch batch;
    CHECK(batch.capacity() == 6);
    CHECK(batch.post(10, 2));
    CHECK(batch.post(11, 0));
    CHECK(batch.post(12, 1));
    CHECK(batch.post(13, 0));
    CHECK(batch.post(14, 2));
    CHECK(batch.post(15, 1));
    CHECK(batch.size() == 6);
    CHECK(!batch.post(99, 0));       // rejection, not an allocation
    CHECK(batch.size() == 6);       // no mutation on rejection
    CHECK(batch.dispatch()->id == 11);
    CHECK(batch.dispatch()->id == 13);
    CHECK(batch.cancel(14));
    CHECK(!batch.cancel(14));
    CHECK(batch.post(16, 0));
    CHECK(batch.dispatch()->id == 16);
    CHECK(batch.dispatch()->id == 12);
    CHECK(batch.dispatch()->id == 15);
    CHECK(batch.dispatch()->id == 10);
    CHECK(!batch.dispatch());
    std::puts("PASS: bounded, priority/FIFO, overflow, cancellation, drain");
}

    Save as main.cpp. The CHECK macro remains active in Release builds (unlike assert under NDEBUG). Every entry is a trivially copyable value, so no user-defined element allocation is involved.

    Contract: rejected posts preserve the size and do not consume a sequence number. cancel removes the first ID match (callers should enforce unique IDs). dispatch scans O(N) and then erases O(N). None of these methods provides synchronization between threads.

    05 / integration

    CMake + Ninja, with a header-only dependency

    cmake_minimum_required(VERSION 3.25)
project(static_vector_check LANGUAGES CXX)
find_package(Boost 1.83 CONFIG REQUIRED)
add_executable(static_vector_check main.cpp)
target_compile_features(static_vector_check PRIVATE cxx_std_20)
target_link_libraries(static_vector_check PRIVATE Boost::headers)
if(CMAKE_CXX_COMPILER_ID MATCHES "GNU|Clang")
  target_compile_options(static_vector_check PRIVATE -Wall -Wextra -Werror -pedantic -fno-exceptions -fno-rtti)
endif()
enable_testing()
add_test(NAME bounded_batch COMMAND static_vector_check)
    cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
ctest --test-dir build --output-on-failure
# Example output: PASS: bounded, priority/FIFO, overflow, cancellation, drain

    This uses the Boost CMake config package and Boost::headers target. For the showcased static_vector, no separately compiled Boost.Container binary is required; some other Boost.Container features have compiled components. For cross-compilation, point CMake to the target-compatible Boost package and use your established toolchain file.

    07 / evidence ledger

    Who actually uses it?

    Verified · Boost's own shipped implementation

    Boost.Container publishes and tests static_vector in its official repository, including capacity and overflow options. That establishes real library implementation and maintained examples—not third-party production deployment. Source.

    Verified report · Existing application

    A developer reported in boostorg/container issue #309 on August 14, 2025 that a real application uses static_vector heavily, and found a regression moving from Boost 1.81 to 1.86. The application is unnamed; we cannot independently identify the product or establish its deployment footprint. The issue records a maintainer fix.

    Documented influence · C++ standardization

    WG21 paper P0843R14 discusses a fixed-capacity vector and culminates in the related std::inplace_vector facility in C++26. This is evidence of design relevance and standardization, not evidence of adoption by RISCue.

    Proposed only · Engineering projects

    RISCue ready batches, VeloSim trace records, and BenchForge bounded sample collections are candidate integrations. No source checked for this report proves that any of those repositories currently uses boost::container::static_vector.

    Performance lesson from real users: issue #309 is unusually instructive: a container can be functionally correct yet suffer a compiler/version-specific vectorization regression. When upgrading Boost, compare generated code and throughput on your actual compiler and target.

    08 / failure analysis

    Six things that can still go wrong

    1. Bound exceeded: unchecked insertion reaches Boost's overflow handling; with exceptions disabled, the default path can terminate or invoke platform exception hooks. Explicitly guard every boundary.
    2. Unchecked “fast” option: throw_on_overflow<false> permits undefined behavior on overflow; it does not implement backpressure.
    3. Stack pressure: an inline N × sizeof(T) buffer makes each container object larger. Copying and passing by value may be surprisingly expensive.
    4. Element-owned allocation: inserting a std::string, owning std::vector, or allocating constructor defeats a program-level no-heap requirement even if the container's own storage never allocates.
    5. Iterator and pointer stability: erasing a middle entry shifts subsequent objects. Do not keep persistent pointers into entries across mutation.
    6. Concurrency and priority: the example is neither thread-safe nor wait-free; scanning/erasing is O(N) and the 32-bit sequence counter wraps after enough posts. For a long-running design use an explicit wrap-safe ordering scheme or epoch discipline.

    09 / choose deliberately

    Alternatives worth comparing

    TypeStorageBest forCaveat
    std::array<T,N>Inline fixed lengthAll N objects logically presentNot a variable-sized sequence
    std::vector<T>Typically heap-backedUnbounded data or separately managed arenaGrowth may allocate and invalidate
    boost::container::static_vector<T,N>Inline fixed capacityVariable count up to known maxNo automatic overload policy
    boost::container::small_vector<T,N>Inline, then may heap-allocateMostly-small workloadsCannot claim no heap past N
    boost::intrusive::listLinks in externally owned nodesKnown-node O(1) erase and stable ownershipPointer/lifetime and hook discipline
    std::inplace_vector<T,N>Inline fixed capacityC++26 toolchainsNot a portable C++20 dependency yet

    Bottom line: static_vector is a compact collection, not a scheduler algorithm. When cancellation of known events is the hot path, revisit yesterday's Boost.Intrusive analysis. For cross-thread transport, a qualified bounded queue remains the right separate abstraction.

    10 / actionable engineering experiment

    RISCue first; VeloSim second

    Suggested RISCue proof of concept (not an implemented change)

    Create a single-owner, fixed maximum batch of event handles or trivially copyable descriptors (not dynamically allocated payloads). Record the reason for every refusal at capacity. Keep producer-to-owner handoff outside this container. Instrument per-cycle enqueue, scan, cancel, and dispatch under maximum occupancy, and enforce the same order under deterministic replay.

    Proposed requirementVerification approachAcceptance evidence
    R-BOUNDED-01: no internal growthFill to N, request N+1Explicit reject, size remains N
    R-ORDER-02: stable priority and FIFO tie-breakingReplay fixed event sequenceByte-identical ID order across seeds/runs
    R-LIFETIME-03: no dangling handlesCancel, dispatch, reuse owned event slotsSanitizers + owner-model review
    R-WCET-04: bounded latencyTarget instrumentation at N=0 and N=maxMeasured upper limits with margin; not a host-only result
    R-HEAP-05: no runtime allocationWrap allocation hooks and all element constructorsZero allocations over qualified scenarios

    Suggested VeloSim usage

    Keep a bounded vector of trace annotations for one simulation time step, then flush or emit a deterministic overflow record at the boundary. This favors contiguous iteration over linked ownership. A trace file format also needs a defined representation for dropped annotations; silent truncation is unsafe for verification.

    BenchForge / SharpHDL note

    Fixed-size benchmark samples or synthesis diagnostic batches could use the same pattern, but those host tools may benefit more from the simplicity and familiarity of std::vector. Do not introduce a dependency unless the upper bound is part of the engineering contract.
