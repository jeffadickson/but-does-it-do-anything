01 · Decision brief

A small function with a narrow promise

Daniel Bahr’s CRC++ is a portable, header-only C++ CRC implementation supporting bit-by-bit and lookup-table algorithms, many named CRC variants, and multipart data. The pinned upstream header, at 62d4791877a636fa4b51acc9181c65ac89364372, identifies itself as version 1.2.3.0. The commit is dated November 5, 2026.

Canonical CRC-320xCBF43926
Output width32 bits
Lookup entries256 × 4 bytes
Recommendation: Pilot CRC++ for bounded RISCue trace records or VeloSim replay artifacts after explicitly serializing every field into an agreed byte order. Begin with the bitwise path, then evaluate table-driven throughput against the RAM/flash/timing budget.

Do not infer: allocation-free behavior for the whole process, a hard WCET bound, cryptographic authenticity, or schema compatibility merely because a CRC matches.

02 · The mathematics

Shift, XOR, repeat

A cyclic redundancy check represents a bit stream as a polynomial over the two-element field GF(2). The remainder from division by a generator polynomial becomes a short integrity code. In a reflected software implementation, shifts and exclusive OR (XOR) compute the remainder; a lookup table can precompute the effect of byte-sized steps.

The complete CRC-32/ISO-HDLC contract

Published reference parameters, not just the vague label “CRC-32”
Width / polynomial32 / 0x04C11DB7
Reflected software polynomial0xEDB88320
Initial remainder0xFFFFFFFF
Input / output reflectedtrue / true
Final XOR0xFFFFFFFF
ASCII “123456789” check0xCBF43926

Parameter set checked against the CRC RevEng manual. Different polynomials, initialization or reflection settings yield different values.

The actual pinned header declares CRC::Calculate(data, size, parameters), overloads taking a CRC::Table, CRC::CRC_32(), and a continuation overload accepting a prior finalized CRC. The header’s table stores table[1 << CHAR_BIT]; on an 8-bit-byte target, a CRC-32 table contributes 1,024 bytes of entries plus parameters and layout overhead.

03 · Evidence and proposed use

CRCs in the real world ≠ adoption of CRC++

Actual documented applications of CRC technology
ApplicationWhat primary documentation confirmsEvidence
PNG imagesEach chunk has a four-byte CRC calculated over chunk type plus data, excluding the length, with the stored value most-significant byte first.W3C PNG specification, §5.5
Ethernet framesA four-byte frame check sequence is recalculated at reception to detect damage in transit. Often handled in networking hardware, not an application library.Cisco Ethernet documentation
CRC++ projectMaintainer documents bitwise and table-based calculation, CRC variants, partial streams, a public header, and tests.Upstream README and API header

Evidence boundary: The first two entries establish real adoption of CRC algorithms, not adoption of Daniel Bahr’s CRC++ library. No independent customer deployment of that specific C++ library was confirmed in this review.

RISCue trace packets — proposal

Record an explicitly encoded event ID, payload length, timestamp and data; save the CRC alongside each record; reject corrupt replay input. A CRC cannot prove the scheduler’s behavior was correct.

VeloSim ↔ VeloFormal — proposal

Fingerprint normalized serialized byte streams before/after transport to flag unintended alteration. A matching CRC would not resolve the structural memories schema mismatch; both sides must validate the same grammar.

For legibility, at most 56 bytes are shown; the CRC always includes the entire input. Bit zero means the least-significant bit of its byte. Non-ASCII text can occupy multiple UTF-8 bytes.

What a CRC cannot do: Checksum collisions are possible; a matching CRC is not proof that no change happened. An attacker can edit data and compute a matching CRC. Use a cryptographic MAC or authenticated encryption for malicious tampering, and use retransmission or error-correcting codes when recovery is required.
05 · Public API example

Fixed-length C++20 verification

Here is an independent educational example based on the pinned upstream declarations. It exercises bitwise and table CRCs, incremental calculation, and a one-bit fault using an application-owned std::array. The test data are explicitly encoded bytes, not an ABI-dependent raw structure image.

// main.cpp — compile with pinned upstream CRC.h
#include "CRC.h"
#include <array>
#include <cstdint>
#include <cstdio>
int main() {
    // Explicit serialized bytes, not a padded C++ struct.
    constexpr std::array<std::uint8_t, 9> bytes{
        '1','2','3','4','5','6','7','8','9'
    };
    constexpr std::uint32_t expected = 0xCBF43926u;
    const auto bitwise = CRC::Calculate(
        bytes.data(), bytes.size(), CRC::CRC_32());

    // 256-entry lookup table; construct before the timed hot path.
    const auto table = CRC::CRC_32().MakeTable();
    const auto fast = CRC::Calculate(
        bytes.data(), bytes.size(), table);

    // CRC++ accepts the previous FINALIZED CRC to resume a stream.
    const auto first = CRC::Calculate(bytes.data(), 4u, table);
    const auto joined = CRC::Calculate(
        bytes.data() + 4u, bytes.size() - 4u, table, first);

    auto damaged = bytes;
    damaged[4] ^= 0x01u;
    const auto changed = CRC::Calculate(
        damaged.data(), damaged.size(), table);

    if (bitwise != expected || fast != expected ||
        joined != expected || changed == expected) {
        std::puts("FAIL: golden vector, chaining, or error detection");
        return 1;
    }
    std::printf("PASS CRC-32: 0x%08lX\n",
                static_cast<unsigned long>(fast));
    return 0;
}

Expected when compiled and executed with the pinned header: PASS CRC-32: 0xCBF43926. This complete example was source-reviewed against upstream signatures, but not compiled against the actual CRC++ header here. The printf line is demonstration I/O, not an RTOS real-time primitive.

06 · Build integration

Vendor once, build offline

Copy the pinned inc/CRC.h to third_party/CRCpp/inc/CRC.h, keep the upstream LICENSE and source SHA in a third-party manifest, and use an INTERFACE target. A local vendored header avoids network access at configure time and makes code review repeatable.

cmake_minimum_required(VERSION 3.24)
project(crc_integrity_lab LANGUAGES CXX)

# Vendor CRC++ inc/CRC.h at upstream commit:
# 62d4791877a636fa4b51acc9181c65ac89364372
# Keep the original LICENSE alongside it.
add_library(crcpp_headers INTERFACE)
target_include_directories(crcpp_headers INTERFACE
    third_party/CRCpp/inc)
add_executable(crc_integrity_lab main.cpp)
target_compile_features(crc_integrity_lab PRIVATE cxx_std_20)
target_link_libraries(crc_integrity_lab PRIVATE crcpp_headers)

if(MSVC)
  target_compile_options(crc_integrity_lab PRIVATE /W4)
else()
  target_compile_options(crc_integrity_lab PRIVATE -Wall -Wextra -Wpedantic)
endif()
enable_testing()
add_test(NAME crc32_known_vector COMMAND crc_integrity_lab)

# cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
# cmake --build build
# ctest --test-dir build --output-on-failure

Because CRC++ is header-only, the consumer does not need a separately compiled binary. The project’s upstream CMake build can also run its own test suite, but a firmware integration should not silently import test and documentation targets. Verify the vendored include path and warning flags in the actual toolchain.

07 · Failure modes

The cost of a 32-bit witness

Engineering tradeoffs, to be measured on the target
ChoiceUpsideCost / hazard
Bitwise CRCAvoids 256-entry table storageMore operations per byte
Byte lookup tablePotential throughput gain1 KiB table entries for CRC-32, initialization, cache and stack/storage choices
Multipart streamNo concatenating allocation requiredMust use correct finalized continuation and exactly ordered bytes
Fixed-size caller bufferPredictable capacityDoes not prove no allocation in the wider process or bounded WCET
CRC matchEvidence against some accidental corruptionsNot collision-free, not cryptographic and not a schema validator
Raw struct bytesConvenient-looking shortcutPadding, endianness, versioning and uninitialized fields corrupt reproducibility

The CRC::Table construction must be accounted for. If built on the stack it needs space, and if held in static storage initialization timing must be reviewed. A table’s 1,024 bytes refer only to its 256 std::uint32_t entries on an eight-bit-byte target, not complete object size.

08 · Next qualification

Five gates before an RTOS pilot

  1. Provenance: lock header SHA and three-clause BSD notice; record compiler/toolchain versions.
  2. Golden vectors: test empty input, 123456789 → CBF43926, one-bit flip, maximum allowed payload, multipart equivalence, and bitwise/table agreement.
  3. Serialization: test length limits, explicit endian encoding, stable bytes across compilers, and no raw struct padding.
  4. Real-time audit: instrument allocations, table initialization, stack/high-water mark, flash usage and timing on target hardware.
  5. Decision: retain only if observed execution bounds meet budget and an independent host model reproduces all protected records.

Suggested first experiment: a 64-byte RISCue replay record with an independently implemented reference CRC. This is a proposal, not a completed integration.
