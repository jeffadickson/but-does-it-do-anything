Boost.Random
The seed is not the replay contract.

A predictable pseudo-random stream is useful for fault injection and randomized scheduling. A bounded, reproducible simulation also needs an explicit mapping algorithm, consumption order, failure policy and versioned trace.

01 / The replay contract

Boost.Random separates generation of pseudo-random words from conversion into statistical distributions. Its Mersenne Twister engine is a deterministic state machine with a long period, not an unpredictable entropy source. Given matching seed, algorithm and call sequence, the same stream can be regenerated. The upstream tutorial demonstrates a six-sided die using an engine and a uniform integer distribution [1].

For a scheduler test, the real requirement is not just “seed 5489.” A new logging call, a changed rejection algorithm or an extra fault-injection draw can shift all subsequent decisions. Identical seeds are also inadequate when the event ordering changes due to thread scheduling. Define an explicit ordering rule, such as virtual tick, priority, actor ID and per-actor sequence number; use distinct named streams for unrelated concerns.

Record an algorithm/version ID, seed derivation version, stream ID, logical event identity, draw count, bounds, accepted result or explicit failure. Prefer logging the decision itself for durable replay across changing implementations. Checkpoints can store engine state and the virtual scheduler state; an in-memory engine copy is not a portable wire format. Avoid dumping object bytes, including padding and platform-dependent members.

02 / Engine versus distribution

The installed Boost 1.83 Mersenne Twister header contains an inline state array and an index. For mt19937 that means 624 32-bit words, plus index and alignment. A call regenerates the state array when its index reaches the state size, then applies tempering operations. This creates a periodic cost spike even when every call is deterministic. On this host the object occupies 2,504 bytes; a hundred such streams would require 250,400 bytes just for engine objects, before logs and scheduler state.

The installed uniform integer implementation contains rejection loops in relevant branches. The public uniform integer distribution takes inclusive endpoints, unlike the half-open mapper below. Never infer a hard call-count bound from a distribution's average throughput. Other distributions may have different state, allocation or floating-point requirements; none were qualified here.

03 / Bounded sampling without modulo bias

For a full-width 32-bit source, there are N = 2³² possible words. For a requested nonzero bound b, let L = N − (N mod b). Accept words below L and return the remainder modulo b. Each of the b outputs has exactly L/b preimages among accepted words. Reject the remaining tail. For example, b = 3 leaves one rejected word (4,294,967,295).

Simply taking a remainder without rejecting the tail gives some outputs extra preimages whenever b does not divide N. The authored mapper stops after four attempts; if all are rejected it returns an exhaustion status, never a biased fallback. Under the ideal independent uniform-word model, the probability of exhaustion is ((N mod b)/N)⁴. This is not a measured property of a specific seed and does not prove independence of pseudo-random outputs. For b just above 2³¹ it can approach 1/16, making failure policy important.

Use 64-bit arithmetic to represent N itself, because it cannot fit in a 32-bit unsigned integer. A zero bound returns before drawing. The API supports bounds 1 through UINT32_MAX; it does not encode the full 2³²-sized result domain. A power-of-two bound never needs tail rejection. On exhaustion the engine has advanced; do not silently rewind or retry outside the budget. The returned value field is meaningless unless status is ok. A target may want a stronger result type to enforce that rule.

The four-call limit applies only to this mapping routine. It is not a cycle bound: engine regeneration, division helpers on smaller MCUs, interrupts and compiler code generation still matter. Use a different mapper or scheduling policy if the operation must always yield a value in a fixed number of draws.

04 / Complete C++20 example

Save as replay.cpp. This is an original example using actual Boost headers, a standard-library comparison engine, and a scripted source to exercise otherwise rare rejection cases. The scripted source is a test double, not a statistical generator. The generic mapper checks advertised word bounds at compile time; callers still own the semantic requirement that the engine actually produces appropriate words and does not throw or allocate. Checks return nonzero exit codes rather than relying on assertions disabled in Release.

#include <boost/random/mersenne_twister.hpp>
#include <boost/random/uniform_int_distribution.hpp>
#include <boost/version.hpp>
#include <array>
#include <cstdint>
#include <cstdio>
#include <limits>
#include <random>

// Contract: engine supplies full-width unsigned 32-bit words.
// Four attempts maximum; no output on invalid bound or exhaustion.
enum class Status { ok, invalid_bound, exhausted };
struct Sample { Status status; std::uint32_t value; unsigned draws; };

template<class Engine>
Sample bounded(Engine& engine, std::uint32_t bound) {
    static_assert(Engine::min() == 0);
    static_assert(Engine::max() == UINT32_MAX);
    if (bound == 0) return {Status::invalid_bound, 0, 0};
    constexpr auto span = std::uint64_t{1} << 32;
    const auto limit = span - span % bound;
    for (unsigned n = 1; n <= 4; ++n) {
        const auto word = static_cast<std::uint32_t>(engine());
        if (word < limit) return {Status::ok, word % bound, n};
    }
    return {Status::exhausted, 0, 4};
}

struct Script {
    std::array<std::uint32_t, 4> words;
    unsigned pos = 0;
    static constexpr std::uint32_t min() { return 0; }
    static constexpr std::uint32_t max() { return UINT32_MAX; }
    std::uint32_t operator()() { return words[pos++]; }
};

int main() {
    unsigned checks = 0;
    auto check = [&](bool ok) { ++checks; return ok; };
    boost::random::mt19937 a(5489), b(5489);
    std::mt19937 standard(5489);
    if (!check(a() == 3499211612u)) return 1;
    b(); standard();
    for (unsigned i = 0; i < 10000; ++i) {
        const auto word = a();
        if (word != b() || word != standard()) return 2;
    }
    if (!check(a == b)) return 3;
    auto snapshot = a;
    const auto first = bounded(a, 7);
    const auto again = bounded(snapshot, 7);
    if (!check(first.status == again.status && first.value == again.value &&
               first.draws == again.draws && a == snapshot)) return 4;
    Script bad{{UINT32_MAX, UINT32_MAX, UINT32_MAX, UINT32_MAX}};
    auto exhausted = bounded(bad, 3);
    if (!check(exhausted.status == Status::exhausted && bad.pos == 4 &&
               exhausted.draws == 4)) return 5;
    Script retry{{UINT32_MAX, 5, 0, 0}};
    auto success = bounded(retry, 3);
    if (!check(success.status == Status::ok && success.value == 2 &&
               success.draws == 2 && retry.pos == 2)) return 6;
    Script zero{{0, 0, 0, 0}};
    if (!check(bounded(zero, 0).status == Status::invalid_bound && zero.pos == 0)) return 7;
    Script power{{UINT32_MAX, 0, 0, 0}};
    auto p = bounded(power, 256);
    if (!check(p.status == Status::ok && p.value == 255 && p.draws == 1)) return 8;
    Script unit{{UINT32_MAX, 0, 0, 0}};
    auto u = bounded(unit, 1);
    if (!check(u.status == Status::ok && u.value == 0 && u.draws == 1)) return 9;
    boost::random::uniform_int_distribution<unsigned> die(1, 6);
    unsigned seen = 0;
    for (unsigned i = 0; i < 10000; ++i) {
        const auto d = die(a);
        if (d < 1 || d > 6) return 10;
        seen |= 1u << d;
    }
    if (!check(seen == 126u)) return 11;
    std::printf("Boost %s; engine bytes=%zu; %u checks passed; 10000 raw matches; 10000 dice in range\n",
                BOOST_LIB_VERSION, sizeof(a), checks);
}

05 / CMake and Ninja

Save as CMakeLists.txt. The example uses header-only facilities; do not link the compiled Boost.Random component unnecessarily. The exact config-package version deliberately matches the tested installation. A source archive or package manager lockfile must also fix provenance and transitive dependencies in production. This is an installed-package example, not a complete vendor manifest.

cmake_minimum_required(VERSION 3.24)
project(random_replay LANGUAGES CXX)
find_package(Boost 1.83.0 EXACT CONFIG REQUIRED)
add_executable(replay replay.cpp)
target_link_libraries(replay PRIVATE Boost::headers)
target_compile_features(replay PRIVATE cxx_std_20)
set_target_properties(replay PROPERTIES CXX_EXTENSIONS OFF)
if(CMAKE_CXX_COMPILER_ID MATCHES "GNU|Clang")
  target_compile_options(replay PRIVATE -Wall -Wextra -Wpedantic -Werror
    -fno-exceptions -fno-rtti)
endif()
enable_testing()
add_test(NAME replay COMMAND replay)
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
ctest --test-dir build --output-on-failure
./build/replay

For cross-compilation, supply a toolchain file and a target-compatible Boost header installation. The GNU/Clang flags disable exceptions and RTTI only for this example; they are not a claim that all Boost.Random APIs can be used with those flags. Do not use the test executable as an embedded deployment artifact. Remove host-only I/O and the comparison engine, then inspect linker map, static RAM and stack usage. Verify any required freestanding support separately.

07 / Actual adoption versus proposed applications

Verified source-level use

The installed Boost.Graph 1.83 header boost/graph/random.hpp includes Boost.Random's uniform integer, uniform real and variate-generator facilities. Its random edge and random outgoing-edge helpers instantiate these distributions and adapt a caller-provided engine. This is actual integration in a separate Boost library, not evidence of a deployed aerospace or RTOS system. The official Boost tutorial also contains illustrative dice and weighted-dice examples, which are examples rather than adoption claims.

Proposed engineering uses

RISCue: host-side randomized event interleavings and fault campaigns, with fixed stream ownership per active object or test role. Record the simulated clock, event IDs and tie-break policy. On target, do not put an unbounded distribution in an interrupt or a deadline-critical dispatcher.

VeloSim: deterministic stimuli and randomized testbench traffic. Add a trace schema for sample status, value, draw count and algorithm version; a change to the mapper should be treated as a trace format/semantic compatibility event. Prefer fixed ordering of streams across worker counts.

Requirements traceability: map every randomness-related requirement to golden vectors, injected rejection cases and regression runs. For C#/.NET 10 Native AOT, consider an independently authored integer mapper with the same explicit arithmetic and versioned test vectors, rather than assuming System.Random shares Boost's sequence. A shared vector file and C++/C# differential tests could establish the actual contract.

08 / Tradeoffs and alternatives

OptionStrengthQualification cost
Boost mt19937Well-established algorithm, inline state, easy comparison to std counterpartLarge state, periodic regeneration, external header dependency
std::mt19937Standard engine, no Boost dependencyObject size and implementation details vary; distribution mapping still needs a contract
Small-state engine (e.g. Boost minstd_rand)Much smaller engine stateDifferent range and quality; cannot reuse this 32-bit mapper without redesign
Counter-based generatorPotentially index random values by stable logical identity rather than consumption orderChoose and qualify an algorithm, counter/key scheme and mapping; not tested here
Recorded decisionsReplay independent of generator changesTrace storage, integrity, versioning and exhaustion handling

Use Boost.Random when the additional engines/distributions or cross-project familiarity pay for the dependency. If the only requirement is a standard Mersenne Twister stream plus a custom mapper, std::mt19937 is a credible simpler baseline. A compact generator may be preferable on a microcontroller, but smaller does not imply adequate statistical quality. Never use these deterministic streams for secrets, authentication tokens or cryptographic randomness.
