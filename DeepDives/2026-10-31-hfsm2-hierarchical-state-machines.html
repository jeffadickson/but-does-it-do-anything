HFSM2: Hierarchy Without the Heap

An RTOS controller is not just on or off. It may be on → ready → executing, with faults, guarded transitions, and independent regions. HFSM2 gives that nested behavior a compile-time shape—without asking the state-machine library to allocate memory.

MIT licensedC++11 minimum; C++20 compatible targetHeader-onlyRelease 2.12.1 · 10 Jun 2026

Engineering decision: Prototype HFSM2 as a state-behavior engine inside a RISCue active object. Do not mistake it for an RTOS scheduler, event queue, or proof of deterministic timing.

01 · RECOMMENDATION

Decision in 60 seconds

Where HFSM2 shines

Hierarchical and orthogonal regions, type-safe transitions, no heap allocation in the framework's statically configured core, and optional diagnostics. It is highly relevant to RISCue's proposed hierarchical state-machine layer. [1]

Where it stops

No event queue, RTOS scheduling guarantee, persistence of arbitrary host context, or automatic worst-case execution-time proof is provided merely by declaring a machine.

Recommended experiment: model a bounded, single-owner Idle → Active → Fault controller; run a scripted event corpus; measure sizeof(FSM::Instance), allocations, step latency, and compiler footprint under the actual RISCue toolchain.
02 · MENTAL MODEL

Why a hierarchy matters

Flat state machines multiply states when several modes share behavior. A hierarchical FSM groups related states under a parent: the Online parent can own common entry/exit work while Idle and Running handle their own behavior. Orthogonal regions express simultaneously active subregions—useful, but potentially subtle when mapping to a single-threaded actor.

  • MissionMode (root)
    • Offlinepeer
    • Onlinecomposite
      • Idleinitial substate
      • Runningother substate

HFSM2 uses templates to describe this topology in C++ source. It supports periodic update() and explicit event reactions via react(), with transitions addressed by types rather than fragile integer IDs. [1, 2]

04 · EVIDENCE QUALITY

What exists versus what we would build

VERIFIED ARTIFACTS

The maintainer publishes an actual traffic-light program, a CMake project, and a separate Unreal Engine integration plugin (documenting UE 5.2). Microsoft's vcpkg publishes the hfsm2 port, version 2.12.1 as inspected. These are inspectable artifacts—not independently verified production deployments. [2, 5, 6, 8]

PROPOSED APPLICATIONS

RISCue: dispatch one actor's events into a bounded HFSM2 instance. VeloSim: replay recorded events to compare state traces. SharpHDL / TinyTMR: use a state-machine test fixture to drive fault scenarios. None is claimed as existing integration or actual flight usage.

Adoption honesty: Public examples, plugins, stars, and package availability do not establish safety certification, production flight heritage, field reliability, or any particular commercial customer. Treat those as unanswered qualification questions.
05 · C++20 WALKTHROUGH

A small, genuinely hierarchical machine

This is an independently adapted example using the API patterns in the upstream traffic-light implementation. Its first top-level region is Online with nested Idle and Active; its peer is Offline. The machine starts in Idle. One update requests Active; a later explicit change selects Offline.

#include <cassert>
#include <hfsm2/machine.hpp>

struct Context {
    unsigned starts = 0;
};

using Config = hfsm2::Config::ContextT<Context&>;
using M = hfsm2::MachineT<Config>;

// The online region owns two nested states.
using FSM = M::PeerRoot<
    M::Composite<struct Online, struct Idle, struct Active>,
    struct Offline
>;

struct Online : FSM::State {};

struct Idle : FSM::State {
    void update(FullControl& control) {
        control.changeTo<Active>();
    }
};

struct Active : FSM::State {
    void enter(Control& control) {
        ++control.context().starts;
    }
};

struct Offline : FSM::State {};

int main() {
    Context context{};
    FSM::Instance machine{context};

    assert(machine.isActive<Idle>());
    machine.update();
    assert(machine.isActive<Active>());
    assert(context.starts == 1);

    machine.changeTo<Offline>();
    machine.update();
    assert(machine.isActive<Offline>());
}
Compile check: This sample was checked against the maintainer's current template and method usage but not compiled in this run because the HFSM2 development headers were not available to the local build environment. Treat the accompanying vcpkg/Ninja commands as the reproducible verification route, not a reported passing build.

Design discipline: never place arbitrary I/O into entry/exit callbacks without accounting for worst-case duration and failure semantics. Transition guards, event ordering, and shutdown behavior deserve tests as much as the happy path.

06 · BUILD & INTEGRATION

Bring it into a CMake/Ninja target

The vcpkg port reports release 2.12.1 (last updated 11 June 2026). Use a controlled vcpkg baseline and lock/pin the exact dependency revision for reproducible work; a floating branch is not a build manifest. [5, 7]

vcpkg add port hfsm2

For a manifest-based project, include "hfsm2" in dependencies; configure CMake using the vcpkg toolchain file. The upstream CMake target and the vcpkg usage file agree on the imported name. [4, 7]

cmake_minimum_required(VERSION 3.21)
project(hfsm2_probe LANGUAGES CXX)

find_package(hfsm2 CONFIG REQUIRED)
add_executable(hfsm2_probe main.cpp)
target_compile_features(hfsm2_probe PRIVATE cxx_std_20)
target_link_libraries(hfsm2_probe PRIVATE hfsm2::hfsm2)
cmake -S . -B build -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=/path/to/vcpkg/scripts/buildsystems/vcpkg.cmake
cmake --build build
./build/hfsm2_probe

On Windows, run the produced executable using its platform-appropriate path. The library is header-only; the examples and upstream test harness have separate dependencies that need not ship in the target firmware. [4]

08 · REAL-TIME DISCIPLINE

“No heap” is not the same as “deterministic”

What is supported

HFSM2's maintainer describes a fully statically defined framework with no dynamic allocations in its core. Its compile-time types can make memory provision explicit. [1]

What needs proof

Application callbacks may allocate, block, throw, or depend on external clocks. C++ construction, I/O, and log sinks have their own behavior. A fixed machine layout alone does not certify bounded CPU time.

For RISCue, use one serialized owner per machine: dequeue one event in a known order, call the chosen reaction/update API, record state and transition trace, and continue. An RTOS priority change or an unrelated producer can otherwise change the observed event sequence. Do not assume that an HFSM2 instance is safe for concurrent unsynchronized access.

Disable or fix the seed and inputs to any utility-theory random decisions when comparing replay traces; declare feature switches consistently across all translation units; and measure worst-case transition chains, guard invocations, and stack growth in the actual embedded configuration.

Tradeoffs, not a silver bullet

10 · TEST PLAN

A measurable proof-of-value for RISCue

  1. Functional matrix: cover every transition, invalid event, guard and hierarchical entry/exit ordering; assert exact active states.
  2. Memory: inspect sizeof(FSM::Instance), alignment, linker map, new/delete hooks, and stack high-water marks.
  3. Timing: measure per-event latency and worst-case transition sequences on the target, in Release builds with representative instrumentation.
  4. Replay: feed a fixed event corpus twice with identical initial context and compare state/transition traces byte-for-byte.
  5. Traceability: assign each state, event and guard a requirement identifier; link those IDs to tests rather than assuming library reflection supplies requirements coverage.
  6. Cross-toolchain: GCC, Clang, and the actual RTOS target toolchain with controlled flags (including exceptions and RTTI policy).
  7. Negative cases: unexpected event while Fault, duplicate reset, callback failure, full event queue, power transition during work, and malformed serialized state if used.

Practical acceptance gate: no undesired dynamic allocation, measured footprint within budget, replay equivalence, guard coverage, and successful target builds. No values have been measured in this edition.
