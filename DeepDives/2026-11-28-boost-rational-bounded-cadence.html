01 / The engineering contract

Periodic work is rarely an integer multiple of the kernel tick. A 375 Hz task on a 1 kHz clock should produce exactly 375 releases every 1,000 ticks, not drift because its nominal 2.667 ms period was rounded to 3 ms. Exact fractions are a useful configuration representation. They are not a substitute for a bounded scheduler.

Boost.Rational is a header-only C++ library for normalized fractions over a chosen integer type. With ordinary machine integers its representation requires no dynamic storage for the two integers. The integer backend determines range, arithmetic cost and potential allocation. The public interface exposes numerator and denominator, comparison and arithmetic. We use the installed Boost 1.83.0 release here, not a claim about the newest release.

Decision: Use rational numbers for configuration and host-side reasoning. Compile them into a small phase accumulator for the actual RTOS hot path. Do not perform arbitrary rational arithmetic in an ISR.

02 / API and numeric hazards

Construction reduces a fraction to relatively prime integers and makes its denominator positive. For instance, 6/16 becomes 3/8 and 0/7 becomes 0/1. Normalization is useful for canonical configuration, hashing and trace records. The two-argument constructor rejects zero denominators with boost::bad_rational in exception-enabled builds. The Boost exception hook needs an explicit policy in builds without exceptions.

using Rate = boost::rational<std::int64_t>;
Rate r(6, 16);  // numerator() == 3, denominator() == 8
// Exact while every required integer operation stays in range.

Neither normalization nor cross-cancellation converts a machine integer into checked arithmetic. Addition, multiplication, sign handling and division can exceed the backend's representable range; signed overflow is undefined in C++. Intermediate operations matter, even if the ideal final fraction would fit. The most-negative signed integer is another boundary to qualify. A checked or arbitrary-precision backend introduces its own error semantics and cost; arbitrary precision may allocate. Do not assume a checked backend preserves the rational invariant after a throwing component assignment.

Inspect the versioned implementation and tests, not just the mathematical API. The installed header normalizes by a GCD, handles zero separately, and checks certain invalid denominators; that is not a general overflow check.

03 / From fraction to a bounded release

Let n/d be events per tick, with 0 ≤ n ≤ d ≤ 1,000,000. Store the reduced fraction and a phase p initially zero. On each logical tick add n; if p ≥ d, subtract d and emit one release. Since p < d before the addition, the temporary sum is at most 1,999,999. At most one release is possible per call.

Induction: after k calls the cumulative release count is floor(kn/d) and the phase is kn mod d. The base case is zero. Adding n either leaves the remainder below d or advances the quotient by one and subtracts d. Thus each prefix differs from the ideal count by less than one release. Inter-release gaps for nonzero rates are floor(d/n) or ceil(d/n) ticks. Release timing is quantized, not jitter-free; dispatch latency and deadlines are separate properties.

This example schedules on the third, sixth and eighth tick. It does not account for dropped hardware ticks, mailbox congestion, or changes of rate during operation. The configuration interface resets phase on success; a rejected configuration leaves all state unchanged. Calls must be serialized by design.

04 / Complete C++20 demonstration

Save the following as demo.cpp. The program uses actual Boost headers. The test uses return codes rather than assertions, so Release builds still check every prefix. The local abort hook is a demonstration of fatal invariant handling, not a flight fault-management policy. In a larger application define the hook once in a platform translation unit; route faults through the qualified platform policy.

#include <boost/rational.hpp>
#include <cstdint>
#include <cstdio>
#include <boost/throw_exception.hpp>
#include <cstdlib>
#ifdef BOOST_NO_EXCEPTIONS
namespace boost {
void throw_exception(std::exception const&) { std::abort(); }
void throw_exception(std::exception const&, source_location const&) { std::abort(); }
}
#endif
class Cadence {
    std::uint64_t n_=0, d_=1, phase_=0;
public:
    bool configure(std::int64_t n, std::int64_t d) {
        if (n<0 || d<=0 || n>d || d>1'000'000) return false;
        boost::rational<std::int64_t> rate(n,d);
        n_=static_cast<std::uint64_t>(rate.numerator());
        d_=static_cast<std::uint64_t>(rate.denominator());
        phase_=0;
        return true;
    }
    bool tick() noexcept {
        phase_+=n_;
        if (phase_<d_) return false;
        phase_-=d_;
        return true;
    }
    std::uint64_t phase() const noexcept { return phase_; }
    std::uint64_t denominator() const noexcept { return d_; }
};
int main() {
    Cadence c;
    if (!c.configure(6,16) || c.denominator()!=8) return 1;
    unsigned count=0;
    for (unsigned k=1; k<=100000; ++k) {
        count+=c.tick();
        if (count!=k*3/8 || c.phase()!=k*3%8) return 2;
    }
    if (count!=37500 || c.tick() || c.phase()!=3) return 3;
    if (c.configure(1,0) || c.configure(-1,8) || c.configure(9,8)
        || c.configure(1,1000001) || c.phase()!=3) return 4;
    if (c.tick() || !c.tick() || c.phase()!=1) return 5;
    if (!c.configure(0,7) || c.tick() || c.denominator()!=1) return 6;
    if (!c.configure(7,7) || !c.tick() || c.phase()!=0) return 7;
    if (!c.configure(999999,1000000) || c.tick() || !c.tick()) return 8;
    std::printf("PASS: 100000 prefix checks; count=%u; sizeof(Cadence)=%zu\n",count,sizeof c);
}

The rate domain deliberately excludes negative values, zero denominator, rates above one event per tick, and excessive denominators. In this small domain, GCD inputs and normalization results are bounded positive magnitudes (or zero numerator); ordinary signed 64-bit integers have ample headroom. The tick function does not invoke Boost or division at all. No heap use is requested by the example's cadence code; that is a source-level observation, not an instrumented proof of system-wide allocation freedom. The host test uses stdio only for reporting.

05 / CMake, Ninja and dependency control

Use an already installed, version-pinned Boost distribution. The exact package version is three-component 1.83.0. The first configure attempt using 1.83 EXACT failed because the installed package did not consider it an exact match; the corrected configuration below passed. The example needs headers, not a separate Rational binary.

cmake_minimum_required(VERSION 3.24)
project(cadence LANGUAGES CXX)
find_package(Boost 1.83.0 EXACT CONFIG REQUIRED)
add_executable(cadence demo.cpp)
target_link_libraries(cadence PRIVATE Boost::headers)
target_compile_features(cadence PRIVATE cxx_std_20)
set_target_properties(cadence PROPERTIES CXX_EXTENSIONS OFF)
if(CMAKE_CXX_COMPILER_ID MATCHES "GNU|Clang")
  target_compile_options(cadence PRIVATE -Wall -Wextra -Werror -fno-exceptions -fno-rtti)
endif()
enable_testing()
add_test(NAME cadence COMMAND cadence)
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
ctest --test-dir build --output-on-failure
./build/cadence
# Separate UBSan test on a GCC host:
g++ -std=c++20 -Wall -Wextra -Werror -fno-exceptions -fno-rtti \
  -fsanitize=undefined -fno-sanitize-recover=all demo.cpp -o ubsan
./ubsan

For reproducible builds record the Boost archive digest, transitive header dependencies, compiler, flags, target ABI, toolchain file and configuration macros in the build manifest. Pin a reviewed Boost archive or vendor a reviewed dependency closure; copying only rational.hpp is insufficient. Use separate CMake presets for host sanitizers and target cross-compilation. Do not assume a Linux package is the target toolchain's package.

07 / Actual adoption versus candidate integration

Verified source-level use: The installed Boost.Geometry 1.83 header boost/geometry/policies/robustness/segment_ratio.hpp constructs boost::rational<Type> in comparison helpers for segment ratios. The local source was inspected directly; the corresponding upstream file is a reproducibility pointer. This is genuine library integration, not proof of a particular production deployment or hardware qualification.

Suggested RISCue application: a configuration-time rate compiler for active-object timer releases, with the phase accumulator owned by the timer service. Preserve the ordering of simultaneous releases by a stable logical priority and identifier. Model admission failure separately: a release decision is not proof that a message was delivered. Preemptive access to the same cadence object needs explicit synchronization.

Suggested VeloSim application: use the integer phase model for rationally related simulated clocks at a defined logical tick resolution. Persist reduced n and d, phase, tick index, schema version and tie-breaking policy for replay. Exact scheduling of sub-tick edge order or multiple events per tick requires a different model, such as a rational-time event calendar with checked comparisons. No existing adoption in RISCue or VeloSim has been verified.

08 / .NET 10 Native AOT interoperability

Share the wire contract, not the C++ object layout. Encode n, d and phase as explicit-width integers with specified byte order and validate p < d, n ≤ d, d ≤ 1,000,000 and canonical reduction. The C# runtime model can use the same bounded addition/conditional subtraction on ulong. No reflection, boxing, dynamic dispatch or BigInteger is required for this restricted operation.

// Illustrative C# kernel, not compiled in this run.
// Caller validates and exclusively owns canonical state.
static bool Tick(ulong n, ulong d, ref ulong phase)
{
    phase = checked(phase + n);
    if (phase < d) return false;
    phase -= d;
    return true;
}

Golden vectors should include 0/1, 1/1, 3/8, 999999/1000000, rejected values and a saved nonzero phase. Use explicit endian encoders such as BinaryPrimitives rather than marshalling struct bytes. Check Native AOT builds and allocation counters separately; this is a proposed interoperability approach, not a tested .NET implementation.

09 / Alternatives and tradeoffs

Which abstraction belongs where?
ApproachStrengthLimitation
Boost.RationalRuntime fraction normalization and general exact arithmetic within backend boundsOverflow risks, GCD and variable arithmetic cost
std::ratioCompile-time exact ratios, natural with chronoNot runtime-configurable; finite intmax_t representation
std::gcd + two integersSmall dependency footprint for this narrow use caseMust implement and review domain checks and canonical representation
Fixed-point accumulatorCheap bounded executionApproximation unless denominator is exactly representable in the chosen scale
Integer rational phaseExact average rate, constant operation count per tickQuantization, rate ≤ one per tick; no general rational arithmetic

If a cadence compiler is the only use, a checked pair with std::gcd is likely preferable to adding Boost. Boost.Rational becomes more attractive when configuration must also combine or compare runtime fractions, or when a host oracle benefits from a well-established API. Even then, derive numeric bounds for each operation or select a reviewed backend with explicit errors. Never benchmark a general fraction operation against a phase step as if they implement identical semantics.
