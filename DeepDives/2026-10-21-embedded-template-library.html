Bounded by design.

1. A container that cannot quietly grow

Imagine an active object with room for eight pending events. The ninth event must produce a deliberate outcome: reject it, signal overload, or apply a documented recovery policy. A container that silently obtains more memory would obscure that contract.

The Embedded Template Library (ETL) supplies containers and utilities for this kind of environment. Its fixed-capacity containers make maximum size part of the type. They offer familiar operations while keeping storage bounded. The project also covers algorithms, callbacks, messaging, and state-machine facilities. Its design accommodates older embedded toolchains as well as modern C++. [Repository overview]

Why this morning’s pick: ETL makes a resource limit visible in ordinary application code. That is closely aligned with your requirement that embedded execution own all of its storage, including during boot.

For a C++20 project, the most interesting question is selective reuse: which small primitives reduce maintenance without weakening your explicit lifetime, scheduling, and verification contracts?

2. How bounded storage works

An instance such as etl::queue<Event, 8> owns capacity for eight elements. Moving from eight slots to sixteen is a source-level resource decision. ETL’s container documentation describes a compile-time maximum and storage strategies that avoid heap allocation. The container’s own placement still matters: a local instance consumes stack space; an instance inside a statically stored object contributes to that object’s storage. [Container design]

Node-based structures can use fixed pools rather than a general-purpose heap. ETL documents constant-time allocation and release for etl::pool. There is an important lifetime distinction: allocate obtains a slot without constructing the object; create also constructs it. Corresponding release and destruction operations have similarly different responsibilities. Placement construction uses already provided memory. [Pool API]

This does not make arbitrary element types allocation-free. A payload’s constructor, copy operation, or destructor can still perform work outside the container’s control. A fixed queue of owning strings, for example, needs a payload audit. For your use case, small value events with explicit ownership are an easier starting point.

Capacity bounds also differ from execution-time bounds. Comparing keys, moving elements, running destructors, or entering a lock can dominate an operation. Treat complexity claims as inputs to target measurement rather than a complete worst-case timing argument.

4. Connections to your projects

StateForge resource contracts. A fixed-capacity event container gives a clear place to attach a maximum-depth requirement, overflow acceptance test, and memory-size record. Your traceability chain could connect the capacity requirement to the wrapper type and tests for empty, full, wraparound, and FIFO behavior. ETL itself does not supply that project-specific evidence.

RISCue OSAL boundaries. An application-level ETL container should not become a second scheduler or silently replace RISCue’s blocking queues. A plain queue supplies storage and operations; blocking, wakeup ordering, ISR rules, and priority inheritance belong to the appropriate kernel or adapter contract. This is an architectural recommendation for your work.

Deterministic simulation. Bounded storage can make overflow reproducible, but scheduling order and virtual time must still come from the simulator. A useful experiment would replay the same event stream into a small wrapper and a simple reference model, comparing every accept/reject and dequeue result.

Your C# tooling. A .NET Native AOT report tool could ingest compile-generated size and test records to track event-capacity budgets. ETL runs in native C++; this proposed tooling connection needs no managed runtime on the embedded target.

5. Practical example: an eight-event mailbox

This original example uses a simple value payload and a static mailbox. It checks capacity before each modifying operation and returns an explicit status. The checks and operations assume a single execution context; sharing this wrapper across threads or interrupts would introduce races.

#include <etl/queue.h>
#include <cstdint>
#include <type_traits>

struct Event {
    std::uint32_t tick;
    std::uint16_t signal;
};
static_assert(std::is_trivially_copyable_v<Event>);

class Mailbox {
public:
    bool post(Event event) {
        if (events_.full()) return false; // Explicit backpressure.
        events_.push(event);
        return true;
    }

    bool take(Event& event) {
        if (events_.empty()) return false;
        event = events_.front();
        events_.pop();
        return true;
    }

private:
    etl::queue<Event, 8> events_;
};

// Static storage; construction still occurs before main.
static Mailbox mailbox;

int main() {
    for (std::uint16_t n = 0; n < 8; ++n)
        if (!mailbox.post(Event{100u, n})) return 1;

    if (mailbox.post(Event{100u, 99u})) return 2;

    Event event{};
    for (std::uint16_t n = 0; n < 8; ++n)
        if (!mailbox.take(event) || event.signal != n) return 3;

    return mailbox.take(event) ? 4 : 0;
}

The program is intended to return zero after checking successful insertion, rejection of a ninth event, FIFO order, and rejection of an empty read. The queue API documents push as returning void, so the wrapper creates the boolean contract. Its documented full-queue checking depends on configuration, including ETL_CHECK_PUSH_POP; unchecked misuse can be undefined behavior. [Queue operations and preconditions]

For ISR or thread communication, choose a suitable synchronization design. ETL’s concurrent queues have different APIs and protection requirements; its ISR variant requires platform locking and memory barriers, while its atomic variant depends on atomic support. Confirm the chosen atomic operations’ target properties before claiming lock-free behavior. [Concurrency contracts]

Verification status: This sample was reviewed against the published API; it was not compiled or executed during this report. No dependencies were installed. It is a starting point for an isolated evaluation, not a verified StateForge implementation.

6. CMake, Ninja, licensing, and configuration

The repository documents a CMake target named etl::etl, with source-tree, installed-package, and FetchContent integration options. For a reproducible evaluation, use a reviewed revision and record its exact identity. The sketch below assumes the dependency is already available locally. [Official CMake integration]

cmake_minimum_required(VERSION 3.25)
project(etl_mailbox LANGUAGES CXX)
# Assumes a reviewed, pinned ETL checkout already exists here.
add_subdirectory(third_party/etl EXCLUDE_FROM_ALL)
add_executable(mailbox main.cpp)
target_compile_features(mailbox PRIVATE cxx_std_20)
target_link_libraries(mailbox PRIVATE etl::etl)
enable_testing()
add_test(NAME mailbox.capacity_and_fifo COMMAND mailbox)

# PowerShell commands:
# cmake -S . -B build -G Ninja
# cmake --build build --parallel
# ctest --test-dir build --output-on-failure

ETL is primarily header-based, so selected templates compile into the consuming native target. Ninja tracks header dependencies and rebuilds affected translation units when inputs change. An unchanged build does not need an always-running helper compiler step. The command above permits parallel build work; the achievable parallelism depends on how many independent compilation jobs the project has.

Keep the ETL profile consistent across translation units. Error policy, STL usage, and platform configuration should be deliberate build inputs. The repository documents discovery of etl_profile.h through include paths and notes that some optional interfaces need platform-specific functions. [Profile and platform notes]

ETL uses the MIT license. Its license permits commercial use, modification, and distribution subject to retaining the required copyright and permission notice; it includes warranty and liability disclaimers. Preserve the actual license text from the pinned dependency in your notices inventory. This is distinct from the licensing questions around your other functional references. [License text]

A productive first experiment would isolate one mailbox type, run full/empty and repeated wraparound cases, then add model-based randomized sequences with recorded seeds. Run sanitizers on the host and separately measure target memory and stack use. Include shutdown and failed-post paths in allocation checks.

My assessment: ETL deserves a small, measured evaluation for application containers and object pools. Your existing framework still needs its own scheduling semantics, requirement coverage, and target evidence. Selective use is easier to justify than adopting overlapping messaging or state-machine subsystems wholesale.
