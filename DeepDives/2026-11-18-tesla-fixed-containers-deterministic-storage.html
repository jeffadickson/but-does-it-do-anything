The engineering decision in one minute

A useful addition to the bounded-memory toolbox

Consider it for fixed-size event queues, trace windows, command batches, and typed lookup tables. You gain STL-shaped APIs with capacity embedded in the type. But fixed storage is not synonymous with drop-free operation, thread safety, stable ABI, or proven timing bounds.

01 / Why fixed capacity matters

Dynamic allocation raises questions a bounded RTOS would rather answer at design time: Can allocation fail? Is allocator latency bounded? Can fragmentation occur? Will a new code path allocate? What is the worst-case memory provision?

std::vector solves a different problem well: it grows. std::array owns exactly N elements, but does not directly represent a changing number of constructed elements. A fixed-capacity vector occupies the middle ground: variable logical size, fixed maximum storage.

Critical distinction: a heap-free container does not imply a heap-free application. If element construction, copying, moving, comparisons, hashing, or destruction allocate, an operation may still allocate. Deterministic memory does not establish a worst-case execution-time (WCET) proof.

For RISCue active objects or deterministic simulation, the container can encode a memory bound. The scheduler, event ownership, producer/consumer synchronization and overload contract still require independent design.

03 / The two overflow stories

Ordinary queue: preserve data or fail

FixedQueue<T,N> adapts FixedDeque<T,N>. Ordinary fixed sequences check invalid growth and element access. The default SequenceContainerAbortChecking invokes std::abort() on length errors, out-of-range access, empty access and invalid arguments. Upstream also documents full-container insertion as an invalid precondition; do not rely on deliberately triggering a checker to handle normal load.

For critical messages, make full capacity an explicit result before calling push(). This makes backpressure observable, testable and traceable to requirements. The library provides is_full() helpers.

Circular queue: keep newest samples

FixedCircularQueue<T,N> wraps FixedCircularDeque. Source inspection confirms that tail insertion on a full deque removes the front item first. A capacity-three trace pushed with 10,20,30,40 retains 20,30,40. That is sensible for some rolling diagnostics and hazardous for a command inbox.

TypeAt capacityAppropriate applicationDangerous assumption
FixedQueue<T,N>Checking failure unless caller prevents insertionLossless work queue with explicit full result“It simply returns false on overflow”
FixedCircularQueue<T,N>Oldest item is evicted, newest retainedRolling trace history“All submitted events survive”

Design review gate: specify capacity, admission policy, overflow instrumentation, recovery, and thread/ISR ownership. These adapters are not advertised as lock-free multi-producer/multi-consumer queues or RTOS synchronization primitives.

04 / Worked example: active-object inbox and trace tail

The key is to keep messages that must not disappear separate from diagnostics that may discard history. This code is an illustrative API exercise, not a claim of actual RISCue integration.

The wrapper returns Admission::Full, differentiates lossless and overwrite-only buffers, and avoids container-level growth allocation. Its correctness assumes a single-threaded access protocol: checking fullness and pushing is not an atomic transaction across concurrent producers.

Interrupt and concurrency boundary: if an ISR and a task access the same queue, choose a separately qualified SPSC/MPMC primitive or protect the complete operation using documented platform synchronization. Fixed capacity alone does not confer interrupt safety.

05 / Memory, object model and constexpr

The reviewed FixedVectorBase source holds logical size metadata and std::array-backed optional in-place element storage. Appending within capacity constructs objects in owned slots instead of reallocating. The project deliberately preserves suitable type traits and supports constant evaluation of many operations.

The README's self-referential, no stored pointers claim is especially useful for embedded placement and in-memory snapshots, but it must not be overextended.

PropertyUseful interpretationQualification needed
Heap-free containerStorage bound is intrinsic to the instantiated container.Payload operations may allocate; audit full call graph.
Type trait retentionAppropriate instantiations retain traits such as trivial copyability.Check exact type and toolchain with static_assert.
No persistent pointersContainer implementation is designed around self-contained storage.Payload types may contain pointers; temporary iterators may hold addresses.
Direct memory imageCould help with controlled same-ABI in-memory copying.Not a portable cross-machine wire format: padding, alignment, endian and version apply.
Constant evaluationCan validate some values/transformations at compile time.Not evidence of runtime timing bounds.

Expect sizeof(FixedQueue<T,N>) to include representation overhead, not necessarily N * sizeof(T) exactly. Measure sizeof, alignof and task stack high-water marks on your actual target. A fixed buffer placed on a small RTOS task stack can simply move a memory failure from heap to stack.

06 / CMake + Ninja integration

The upstream README documents the imported target fixed_containers::fixed_containers. Its CMake source requires C++20, creates an interface library and links magic_enum::magic_enum. Its own tests additionally depend on GoogleTest and Google Benchmark when enabled. A vcpkg port is available: use a pinned vcpkg baseline for reproducibility.

The example includes a simple executable main() and one CTest smoke check. Its standalone test assertions are shown separately for later integration into a real test target. These commands are documented instructions, not an executed build log.

  1. Pin the upstream commit or vcpkg baseline; never silently fetch changing main in qualification CI.
  2. Keep upstream testing dependencies out of production builds. Set BUILD_TESTS=OFF when appropriate for subproject inclusion.
  3. Compile with your deployed exception, RTTI, warning and optimization policies; inspect map and binary size artifacts.
  4. Capture compile_commands.json and the toolchain version for repeatable source-level analysis.

Compiler evidence: upstream's README lists Clang 13, GCC 11 and MSVC 14.29 as tested. That is its documented compatibility baseline, not a fresh cross-toolchain qualification for modern versions or any particular microcontroller/RTOS target.

08 / Tradeoffs and alternatives

AlternativeWhen it winsWhat fixed-containers adds
std::arrayExactly N active values and minimal complexityLogical-size mutation and queue-style interfaces
Boost.Container static_vectorAlready using Boost; only bounded contiguous storage is neededBroader container family, including associative and enum variants
ETLOlder compiler/language targets, established firmware integrationModern C++20 and structural/constexpr design goals
Boost.Lockfree SPSC queueQualified independent producer and consumer contextsOrdinary fixed queue is a bounded adapter, not a lock-free primitive
Hand-built ringDMA alignment, custom ISR conditions or exact bit layoutMore general APIs and familiar algorithms

Before adopting, answer three concrete questions: what happens on overflow, how many bytes does the instantiated type consume, and who can access it concurrently? A library choice without those answers is premature.
