Memory you can count on.

A real-time task should not discover at the worst possible moment that it needs more heap. Meet foonathan/memory: allocator building blocks that can turn a fixed byte budget into reusable event slots—and make exhaustion an explicit design decision.

Assessment · proposed for your projects

Worth prototyping, not adopting blindly

Hypothesis: a dedicated fixed-block memory pool per active-object class could bound memory consumption for RISCue event records while allowing reuse after deallocation. Its try_allocate_node() path is especially interesting: when the pool's free list is empty, it returns nullptr rather than growing the pool.

Critical distinction: a fixed backing store is not a proof that the whole system never allocates, never blocks, or meets its deadline. The calling code, diagnostics, synchronization, compiler settings, and all other components must also be audited.

The hidden heap problem

Consider an event-driven flight-style task processing 64 messages per cycle. Each record needs a predictable amount of storage. Ordinary dynamic allocation may be perfectly suitable in desktop tools, but it complicates the safety argument when an allocation can fail, block, contend with another task, or take data-dependent time.

The design goal is not necessarily “never use an allocator.” It is allocate from a known budget, predict what happens when it fills, and keep the result testable. That includes memory required by bookkeeping, alignment and debugging guards—not just N × sizeof(Event).

Useful mental model: imagine a parking lot with exactly 24 marked spaces. A car can park in a free space and leave it for reuse. A 25th car gets an explicit “full” response; the lot does not secretly construct another level.

How foonathan/memory works

The library distinguishes a RawAllocator that hands out appropriately aligned memory from a BlockAllocator that obtains larger backing blocks. The memory_pool divides blocks into equal-sized nodes and maintains a free list. A static_block_allocator can obtain those blocks from caller-owned static_allocator_storage<Size> instead of the heap.

Backing storagecaller-owned bytes

Two allocation paths matter: allocate_node() is permitted to request an additional backing block when the free list is empty. try_allocate_node() will not request a new block and returns nullptr when none is available. For a hard bound, pair a fixed backing allocator with the non-growing path and a deliberate failure policy. See the upstream header contract.

Subtle but important: static_allocator is monotonic: its deallocation operation does nothing. The pool recycles individual event nodes; the static_block_allocator supplies fixed backing blocks. Do not confuse those lifetimes.

For immutable lookup tables, the earlier Frozen edition offers a different solution: create constant data rather than allocate at runtime. Choose the simplest tool that solves the actual allocation problem.

Upstream-informed example · review only, not compiled against the library

A bounded event pool in C++20

This adaptation uses names and behavior checked against the v0.7-4 public headers. Its fixed storage is declared before the pool so it outlives the pool; the pool gets one 4096-byte block and try_allocate_node() never grows it. Each Event is constructed into the returned raw storage and explicitly destroyed before node recycling.

#include <cstdint>
#include <cstdio>
#include <new>
#include <foonathan/memory/memory_pool.hpp>
#include <foonathan/memory/static_allocator.hpp>

namespace fm = foonathan::memory;

struct Event {
    std::uint32_t id;
    std::uint32_t argument;
};

int main() {
    fm::static_allocator_storage<4096> backing{};
    using Pool =
        fm::memory_pool<fm::node_pool,
                        fm::static_block_allocator>;

    // One 4096-byte backing block; no heap fallback.
    Pool pool(sizeof(Event), 4096, backing);

    // This path never expands the free list.
    void* slot = pool.try_allocate_node();
    if (slot == nullptr) {
        std::puts("event-pool exhausted");
        return 1;
    }

    Event* event = ::new (slot) Event{42u, 7u};
    std::printf("Event %u: %u\n",
                event->id, event->argument);

    event->~Event();
    pool.deallocate_node(slot);
}
Object lifetime is not optional. A raw node is not automatically an Event. Placement construction and destruction are required for non-trivial objects. In a real event API, hide this pairing in a carefully reviewed owner type and test every early-return path.

Capacity is not 4096 / sizeof(Event). Free-list metadata, alignment and optional debug fences consume space. Use the upstream memory_pool::min_block_size(node_size, count) helper and measure actual capacity_left() under each build configuration. The example demonstrates API flow, not a certified count of event slots.

Three experiments worth running

Fill the parking lot

Choose Fixed, press Try 25. Expected: 24 occupied spaces, one rejected request. This is the policy you can reason about when event bursts exceed the allocated budget.

Reuse one slot

Activate any occupied amber slot, then press Allocate one. Expected: the freed slot is reused and the capacity remains 24. An individual node can be recycled without enlarging the backing store.

Contrast hidden growth

Reset, choose Growing, then press Try 25. Expected: capacity rises from 24 to 25. An unbounded growth policy may be useful for tools, but it violates a fixed memory budget.

Stretch challenge: what if a producer is faster than a consumer?

Define a queue bound, arrival burst limit and overflow action (reject, overwrite, backpressure, or recover safely). Record dropped-event counts. Merely having a memory pool does not prove queue correctness or scheduling fairness.

Verified adoption, not just a plausible use case

Documented third-party usage

eProsima Fast DDS

Fast DDS explicitly documents foonathan_memory as an external dependency, explains why it was selected, and publishes the actual APIs it uses, including memory_pool, node_pool, container node-size helpers and allocator wrappers. Its separate foonathan_memory_vendor repository builds and installs the dependency. These are primary-source indications of actual adoption—not a claim that RISCue uses it today.

Read the Fast DDS dependency quality declaration, actual API inventory and vendor package.

Boundary: Fast DDS's use does not prove memory boundedness, hard real-time suitability or flight certification. Its published declaration makes more modest, context-specific quality claims.

Reproducible CMake / Ninja trial

Pin the reviewed release rather than silently tracking main. As of November 1, 2026, GitHub reports v0.7-4 (published May 2, 2025) as the latest release.

mkdir -p external
git clone --depth 1 --branch v0.7-4 \
  https://github.com/foonathan/memory.git external/memory

Create CMakeLists.txt alongside the main.cpp above:

cmake_minimum_required(VERSION 3.20)
project(bounded_event_pool LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(FOONATHAN_MEMORY_BUILD_EXAMPLES OFF CACHE BOOL "" FORCE)
set(FOONATHAN_MEMORY_BUILD_TESTS OFF CACHE BOOL "" FORCE)
add_subdirectory(external/memory)

add_executable(bounded_event_pool main.cpp)
target_link_libraries(bounded_event_pool
  PRIVATE foonathan_memory)
cmake -S . -B build -G Ninja \
  -DCMAKE_BUILD_TYPE=Release
cmake --build build
./build/bounded_event_pool

Windows PowerShell: use the same CMake/Ninja commands after installing a compatible C++ toolchain; run .\build\bounded_event_pool.exe. The library is not purely header-only: CMake builds and links its target. The project's own installation guide describes add_subdirectory(), foonathan_memory and find_package(). For cross-builds, supply your target toolchain file before configuring.

Tradeoffs and failure modes

RiskEngineering response
Wrong node size or alignmentUse sizeof, alignof, upstream node-size helpers for STL containers, and debug builds; do not guess container node bytes.
ExhaustionExplicit nullptr handling; specify whether to reject, drop, backpressure or transition to safe mode. Never silently overwrite.
Thread contentionPool instances are not automatically thread-safe. The upstream v0.7 release notes call out thread_safe_allocator when synchronization is required.
Stack consumptionA local 4 KiB backing array consumes task stack; move backing storage to a carefully owned static region for RTOS integration.
Unexpected growthUse fixed backing storage and try_allocate_node(); audit constructors and every alternate allocation path.
No-exceptions targetsReview error handlers, configuration macros, exhaust paths and toolchain flags. Never assume the default throw/abort behavior is acceptable.
Debug-versus-release differenceFence, fill and assertion options change overhead. Characterize both and reserve conservative capacity.
CertifiabilityOpen source and downstream use are not substitute evidence for your target, safety case, code analysis or test campaign.

A fixed-node pool is not appropriate for every allocation shape. Large variable-sized arrays may be a poor fit; separate size classes or a simple arena may work better. A ring buffer remains an excellent baseline for event queues with FIFO lifetime.

Exit criteria for a serious proof-of-value

  1. Allocation audit: instrument global operator new, malloc and any platform allocator; warm up once, then exercise a million event operations. Expected steady-state external allocations: zero.
  2. Exhaustion: fill every pool, request one more event, and verify the specified outcome with no memory corruption or hidden fallback.
  3. Latency: time allocation/deallocation high-water percentiles and worst observed latency under realistic preemption, not only an average benchmark.
  4. Ownership: ASan/UBSan on a hosted build; static analysis and target-specific checks for double-return, use-after-free, lifetime and ISR misuse.
  5. Determinism: replay the exact same inputs and allocation/free order; compare traces, failures and high-water counters.
  6. Footprint: inspect .bss, task stack, debug fence overhead, linked binary size and static storage occupancy across GCC, Clang and your flight compiler.
  7. Requirements: trace each overflow, maximum burst, runtime heap ban and synchronization rule to automated tests and code.
