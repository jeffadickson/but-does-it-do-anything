THE SHORT VERSION

An active object is an owner, not just another thread.

QP/C++ marries a private event queue and run-to-completion processing to a hierarchical state machine. Instead of letting many tasks manipulate the same state through locks, an active object accepts messages and changes its own state one event at a time. Its queue, scheduling priority, and memory resources can be deliberately bounded. [1] [3]

QHsmReusable nested state semantics; can operate without QF scheduling.
QActiveState machine plus queued, asynchronous event processing.
QV / QKCooperative or preemptive run-to-completion scheduling options.
Why this is different from the October 23 Boost.SML deep diveBoost.SML emphasizes compile-time state-machine construction. QP/C++ supplies a fuller event-driven architecture: AO lifecycles, bounded queues, timed events, and kernels/RTOS ports. It is more prescriptive and has substantially different licensing.

How the moving pieces fit

There are two largely independent concerns: behavior and execution. The QHsm base class implements behavior as states and transitions; QActive hosts that behavior inside a concurrently scheduled actor-like object. QP describes each AO as processing one event to completion before accepting its next event. [2] [4]

Determinism is a budget, not a magic property

With a fixed event queue and correctly sized fixed-block event pools, memory consumption is bounded. Scheduling can be analyzed when event-handler execution times, priorities, arrival bursts, interrupt latencies and queue overflow policies are measured. The framework does not automatically prove worst-case execution times or make shared peripherals race-free. Its documentation contrasts fixed-block event pools with general-purpose heaps. [5]

Hierarchy removes repeated transitions

A shared operational superstate can handle FAULT_SIG once for both disarmed and armed children. A transition to fault exits the current child. After reset, the initial substate is re-entered. The example below makes those semantics explicit. [2]

A practical C++ example: a faultable puck gate

Start with a passive HSM, not threads. It implements a tiny safety gate: disarmed → armed → fault, with a common operational parent catching faults. A simulated shot only increments the counter while armed; reset returns to disarmed. This is a hypothetical training controller, not an approved safety interlock or deployed hockey product.

The declarations, Q_STATE_DECL/Q_STATE_DEF wrappers, QP::QEvt constructor, and QHsm::init/dispatch calls were compared against upstream QP/C++ 8.1.x headers and reference documentation. The code needs a configured QP/C++ port and linked framework; it is not freestanding C++. [2] [11]

C++20 consumer · QP/C++ 8.1.x modelIntegration-dependent
// QP/C++ 8.1.x: passive HSM, no scheduler or heap needed by this model.
// Compile/link only in a configured QP/C++ project with a matching port.
#include "qpcpp.hpp"
#include <cstdint>

// QP reserves signal numbers 0..3 for lifecycle actions.
enum GateSignal : QP::QSignal {
    ARM_SIG = QP::Q_USER_SIG,
    FIRE_SIG,
    FAULT_SIG,
    RESET_SIG
};

class PuckGate final : public QP::QHsm {
public:
    PuckGate() noexcept : QHsm(Q_STATE_CAST(&PuckGate::initial)) {}
    [[nodiscard]] std::uint32_t shots() const noexcept { return shots_; }

private:
    std::uint32_t shots_{0U};
    Q_STATE_DECL(initial);
    Q_STATE_DECL(operational); // composite parent
    Q_STATE_DECL(disarmed);    // child of operational
    Q_STATE_DECL(armed);       // child of operational
    Q_STATE_DECL(fault);       // sibling of operational
};

Q_STATE_DEF(PuckGate, initial) {
    Q_UNUSED_PAR(e);
    return tran(&operational);
}
Q_STATE_DEF(PuckGate, operational) {
    switch (e->sig) {
        case Q_INIT_SIG: return tran(&disarmed);
        case FAULT_SIG:  return tran(&fault); // works from either child
        default:         return super(&QP::QHsm::top);
    }
}
Q_STATE_DEF(PuckGate, disarmed) {
    switch (e->sig) {
        case ARM_SIG: return tran(&armed);
        default:      return super(&operational);
    }
}
Q_STATE_DEF(PuckGate, armed) {
    switch (e->sig) {
        case FIRE_SIG: ++shots_; return Q_HANDLED();
        default:       return super(&operational);
    }
}
Q_STATE_DEF(PuckGate, fault) {
    switch (e->sig) {
        case RESET_SIG: return tran(&operational); // re-enters disarmed
        default:        return super(&QP::QHsm::top);
    }
}

int main() {
    PuckGate gate;
    gate.init(0U); // top-level initial transition; no RTOS required
    QP::QEvt const arm{ARM_SIG};
    QP::QEvt const fire{FIRE_SIG};
    QP::QEvt const fault{FAULT_SIG};
    QP::QEvt const reset{RESET_SIG};
    gate.dispatch(&fire, 0U);  // disarmed: ignored
    gate.dispatch(&arm, 0U);   // armed
    gate.dispatch(&fire, 0U);  // shots = 1
    gate.dispatch(&fault, 0U); // fault, parent catches FAULT_SIG
    gate.dispatch(&fire, 0U);  // ignored while faulted
    gate.dispatch(&reset, 0U); // reset -> operational -> disarmed
    return gate.shots() == 1U ? 0 : 1;
}
Expected model testReturn code 0 means only the single shot made while armed was counted. The unarmed/faulted FIRE events must be ignored. This is a logic-level model test, not certification, timing proof or a complete QF application.

From passive model to an active object

QP's QActive adds a private event queue and scheduling. The following shows the essential architectural change; it intentionally omits full state handlers, startup callbacks, BSP and event producer so nobody mistakes it for a runnable firmware image. The QEvtPtr queue type is from the current upstream headers, which differ from some older API examples. [3] [11]

QActive startup shapeIllustrative / partial
// Transition to an ACTIVE object after verifying the passive HSM.
// This is an integration sketch, not a complete BSP/main program.
class PuckGateAO final : public QP::QActive {
public:
    PuckGateAO() : QActive(Q_STATE_CAST(&PuckGateAO::initial)) {}
private:
    Q_STATE_DECL(initial);
    Q_STATE_DECL(disarmed);
    Q_STATE_DECL(armed);
};
// In application startup, with an appropriate QV/QK/RTOS port:
static PuckGateAO gate;
static QP::QEvtPtr gateQueue[8]; // bounded queue: capacity is explicit
QP::QF::init();
gate.start(1U, gateQueue, Q_DIM(gateQueue), nullptr, 0U);
// Define state handlers, BSP callbacks and scheduler startup as documented.
// Never assume full queues are impossible: design a POST/POST_X policy.

For strictly allocation-free operation, keep handlers free of new, avoid unbounded operations, define fixed queue and stack budgets, and use immutable static events or explicitly provisioned fixed-block pools. A pool is bounded allocation, not literally “never allocates”—important when writing requirements.

Suggested requirements to baseline

RISCUE-AO-001 AO-owned mutable state shall not be accessed directly by another AO. RISCUE-AO-002 Every queue shall have a compile-time capacity and documented overflow policy. RISCUE-AO-003 Every event shall have a bounded run-to-completion budget on the target. RISCUE-AO-004 Fault event handling shall be traceable to both state-transition tests and timing tests. These identifiers are proposed and are not claims about your existing specification.

QP's own public requirements manual provides traceable IDs such as SRS_QP_REQ_000, _060 and _070. That is a real example of requirements-to-design links, distinct from asserting that your repository already uses their system. [6]

CMake, Ninja, ports and an evaluation plan

QP/C++ is a compiled library, not a single C++20 header. The maintained repository includes CMake integration documentation and platform ports. Its stated language baseline is C++17, so a C++20 compile is plausible but must be checked with your target flags, link mode, exception/RTTI policy, and static analyzers. [1] [8]

Smallest useful validation experiment

  1. Pin a QP/C++ release and record both the source commit and the documentation version; the public docs reviewed here report 8.1.5 while current source contains 8.1.6 identifiers.
  2. Build an unmodified host sample with Ninja and record code/RAM sizes; only then add the passive PuckGate model.
  3. Exercise all 4×4 state/event combinations, plus burst events at queue capacity and capacity+1. Record the selected POST versus POST_X failure policy.
  4. Try a two-AO setup, instrument worst-case dispatch times, and model priority inversion, interrupt traffic, and starvation.
  5. Evaluate RISCue integration with a tiny board support layer only after the host behavior and requirements are green.

Tradeoffs you should not skip

AdvantageCost / caveat
Single-owner state and run-to-completion behavior simplify many concurrency reviews.Shared devices, DMA buffers, ISRs and global singletons still require explicit ownership and synchronization contracts.
Hierarchical states avoid duplicated event logic.Nested transitions, entry/exit ordering and history require tests; the real cost includes debugging generated/manual state code.
Queue and event-pool storage can be fixed and preallocated.Capacity exhaustion must be specified; event pool exhaustion, queue overflow and priority starvation are design faults, not framework impossibilities.
QV cooperative kernel has a simple execution model; QK offers preemptive RTC.Long handlers damage latency; preemptive scheduling increases timing complexity. QXK appears as a commercial Extras feature in current upstream distribution notes.
Published architecture/requirements docs aid verification reviews.Safety certification artifacts and complete trace/test tooling are not all included in the public GPL distribution.
Native C++ framework aligns with embedded toolchains.QP/C++ is not an automatic .NET Native AOT component or a zero-effort plug-in to RISCue.

Licensing and integration constraints

QP/C++ is dual licensed: GPL-3.0-or-later for GPL-compliant open-source distribution, or a separate Quantum Leaps commercial license for closed-source distribution. This is not MIT, BSD, or Apache-2.0, and it matters for any code you ship with RISCue or customer applications. Follow the publisher's conditions and obtain legal advice for distribution questions. [9] [11]

The publisher states that its commercial Extras include QS tracing, QXK dual-mode kernel, expanded static-analysis configuration and a trace-based QUTest coverage suite; do not assume every feature illustrated in older tutorials is present in the public code. The safety-oriented SafeQP and certification kits are commercial offerings, not inherited merely by embedding QP/C++. [1]

Practical decision gatePrototype the passive HSM and open-source QV/QK path in a suitable development setting. Before integrating into a redistributable proprietary product—or presenting full tracing/certification as available—review exact licenses, current packaging, availability, support and commercial terms.
