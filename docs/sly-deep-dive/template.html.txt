<section id="problem"><div class="number">01 / The concrete problem</div><h2>It starts as a few words in a string.</h2>
<p class="intro">An application accepts a formula, a command, a filter, or a small configuration language. The first implementation splits on spaces or punctuation. That can be exactly the right amount of engineering.</p>
<div class="columns"><div class="box"><h3>The first version</h3><pre><code>gain 2.5
offset 0.1</code></pre><p>Two words, no nesting, no quoting, no ambiguity. A short validation routine may be all you need.</p></div><div class="box"><h3>The change request</h3><pre><code>gain (base + trim) * 2.5
label "rack 2 / channel A"</code></pre><p>Now spaces can belong inside a value. Parentheses nest. Operators have precedence. Error locations matter.</p></div></div>
<p>The awkward part is no longer finding separators. It is recognizing <em>structure</em>. Splitting <code>(1+2)*3</code> on plus signs loses the fact that the addition is a group. Treating <code>1+2*3</code> as a left-to-right operation sequence gives the wrong arithmetic structure.</p>
<p>A parser earns its place when the input has a language contract worth making explicit: commands should be composable, invalid input should be explainable, and changes should be testable without executing the application.</p>
<div class="note"><strong>More parsers, fewer accidental languages.</strong>That does not mean inventing a DSL for every setting. Reuse JSON, TOML, an existing query language, or a domain parser when it fits. Reach for a grammar when your input really has syntax that those formats do not express well.</div>
</section>
<section id="mechanics"><div class="number">02 / The machinery</div><h2>A lexer finds words.<br>A grammar finds relationships.</h2>
<div class="pipeline" aria-label="Text becomes tokens, then syntax, then validated meaning, then application behavior"><div>Text<small>original characters</small></div><div>Tokens<small>numbers, names, signs</small></div><div>Syntax tree<small>groups & operators</small></div><div>Validation<small>names, units, rules</small></div><div>Application<small>typed operations</small></div></div>
<p>For <code>1+2*3</code>, the lexer identifies five tokens. The parser groups them so that multiplication sits below addition in the tree. The tree records a relationship; evaluation is another operation.</p>
<p>Sly is a NuGet library. You describe lexical rules with attributes on an enum and grammar productions with attributes on C# methods. <code>ParserBuilder</code> reads that metadata and constructs the recognizer. Your methods are the typed actions called when a production matches.</p>
<div class="tablewrap"><table><thead><tr><th>You supply</th><th>Sly supplies</th><th>You still own</th></tr></thead><tbody><tr><td>Token patterns, symbols and modes</td><td>The lexer implementation</td><td>Which characters are legal in each context</td></tr><tr><td>BNF/EBNF production attributes</td><td>Grammar construction and recognition</td><td>Ambiguity, acceptance boundaries and coverage</td></tr><tr><td>Typed production methods</td><td>Dispatch into those methods</td><td>Syntax nodes and application semantics</td></tr><tr><td>Operator attributes</td><td>Generated expression rules</td><td>Precedence, associativity and their tests</td></tr></tbody></table></div>
<p>This is different from writing a recursive-descent parser by hand. It is also different from a Roslyn source generator: the ordinary Sly <code>ParserBuilder</code> path builds a parser from attributes in your .NET process. ANTLR’s normal tool instead emits source from a separate grammar before compilation.</p>
<p>The distinction matters operationally. A compact .NET application can use Sly without installing a Java generator. It still needs a defined grammar, runtime initialization, dependency management and qualification for its intended inputs.</p>
</section>
<section id="grammar"><div class="number">03 / The annotated implementation</div><h2>The interesting code is the language.</h2>
<p>A small expression grammar can stay close to the C# that consumes it. Here are representative pieces from the downloadable laboratory.</p>
<div class="codehead"><span>01 · Token rules</span><button data-copy="tokens-code">Copy</button></div>
<pre id="tokens-code"><code><span class="kw">internal enum</span> ExprToken
{
    <span class="at">[Lexeme(@"[ \t\r\n]+", true)]</span> Space = 1,
    <span class="at">[Lexeme(@"(?:[0-9]+(?:\.[0-9]*)?|\.[0-9]+)(?:[eE][+-]?[0-9]+)?[A-Za-z]*")]</span> Number,
    <span class="at">[Lexeme(@"[A-Za-z_@$][A-Za-z_0-9.$]*")]</span> Name,
    <span class="at">[Lexeme(@"\+")]</span> Plus,
    <span class="at">[Lexeme(@"\*")]</span> Times
    <span class="comment">// The complete source also declares grouping, calls and other operators.</span>
}</code></pre>
<p>The first rule skips whitespace. The number rule recognizes spelling, including engineering-style suffixes; it does not establish that a suffix is meaningful or that a value has the right unit. Those are semantic decisions.</p>
<div class="codehead"><span>02 · Operator rules and an AST action</span><button data-copy="operators-code">Copy</button></div>
<pre id="operators-code"><code><span class="at">[Operation((int)ExprToken.Plus,  Affix.InFix, Associativity.Left, 10)]</span>
<span class="at">[Operation((int)ExprToken.Times, Affix.InFix, Associativity.Left, 20)]</span>
<span class="kw">public</span> Node Binary(Node left, Token&lt;ExprToken&gt; op, Node right)
    =&gt; <span class="kw">new</span>(op.Value, left.Start, right.End, [left, right]);</code></pre>
<p>Higher precedence makes multiplication bind more tightly in this definition. The method creates a node with two children and a physical source range. It does not multiply anything.</p>
<div class="codehead"><span>03 · Grouping is a production</span><button data-copy="group-code">Copy</button></div>
<pre id="group-code"><code><span class="at">[Operand]</span>
<span class="at">[Production("group : Open ExprGrammar_expressions Close")]</span>
<span class="kw">public</span> Node Group(Token&lt;ExprToken&gt; first, Node value, Token&lt;ExprToken&gt; last)
    =&gt; <span class="kw">new</span>(<span class="st">"group"</span>, first.Position.Index, last.Position.Index + 1, [value]);</code></pre>
<p><code>ExprGrammar_expressions</code> is Sly’s generated expression-rule name for this class. The production says which token/nonterminal sequence matches. Its method says what syntax object to construct. A missing closing parenthesis is a grammar rejection before any evaluator or simulator is involved.</p>
<details><summary>What is a “production,” exactly?</summary><p>A production is one grammar rule: a name on the left and an allowed sequence on the right. In <code>group : Open expression Close</code>, a group consists of an opening token, an expression and a closing token. EBNF adds concise repetition and optionality: <code>item+</code>, <code>item*</code> and <code>item?</code>. Concise does not mean ambiguity disappears.</p></details>
</section>
<section id="meaning"><div class="number">04 / The architectural boundary</div><h2>Parsing should not turn things on.</h2>
<p>A command may be syntactically valid while referring to a missing instrument. A circuit may parse while using an unsupported model. An expression may be well formed while referencing an unknown variable.</p>
<p>Keep these outcomes separate. A useful frontend produces located syntax. A binder resolves names. A validator checks the domain contract. Only a later application operation performs I/O, changes state, or asks a numerical solver to work.</p>
<div class="columns"><div class="box"><h3>Syntax asks</h3><p>Is the differential pair closed? Are there two nodes? Does an expression have an operand after <code>+</code>? Is the control block terminated?</p></div><div class="box"><h3>Semantics asks</h3><p>Does the model exist? Does that port type match it? Are the units compatible? Is this command authorized? Can this analysis actually run?</p></div></div>
<p>The laboratory’s control test feeds a shell-looking command to the parser and checks that no marker file is created. Recognition retains command text; it does not execute it. That is evidence about this implementation path, not a general security sandbox or a guarantee about arbitrary semantic actions.</p>
<div class="note"><strong>The reusable pattern</strong>A UI, command palette, CLI and automation endpoint can share the same typed application operations. A text parser is an adapter into that system. It should not become a second, less-tested implementation of the application.</div>
</section>
<section id="contexts"><div class="number">05 / Where the interesting work begins</div><h2>The same character can change its job.</h2>
<pre><code>a1 in-node out/name gain
B1 out 0 V={v(in)-0.3}</code></pre>
<p>In the first line, a hyphen or slash can belong to a node name. In the expression, those characters are operators. One globally permissive identifier regex can swallow subtraction; one globally arithmetic lexer can break legitimate node spellings.</p>
<p>Sly has built-in lexer modes. The generic-mode probe uses attributes such as these:</p>
<div class="codehead"><span>Enter and leave an expression context</span><button data-copy="modes-code">Copy</button></div>
<pre id="modes-code"><code><span class="at">[Mode("default")][Sugar("{")][Push("expression")]</span> Begin,
<span class="at">[Mode("expression")][Sugar("}")][Pop]</span> End,
<span class="at">[Mode("expression")][Sugar("-")]</span> Minus</code></pre>
<p>The executed probe tokenizes <code>in-node {v(g)-1} out-node</code>. Both hyphenated names remain intact outside the braces; the minus becomes an operator inside. This corrects an easy misconception: modes are not an ANTLR-only capability.</p>
<div class="note warning"><strong>Important scope boundary</strong>The experiment has separate regex-based fragment grammars and a generic-lexer mode probe. It has not integrated them into one complete deck lexer. Showing that each mechanism works is not proof that the combined frontend is finished.</div>
<h3>Source offsets are the durable anchor</h3>
<p>A continuation can join a logical statement across physical lines and comments. The original characters should remain available for diagnostics, editing and reproducibility. Prefer absolute offsets into the original text over reconstructing source from normalized tokens.</p>
<pre><code>a1 [first
* comment
+ second] model</code></pre>
<p>In the measured Sly regex probe, <code>second</code> keeps the correct absolute UTF-16 index, 24 in the CRLF test string. Its reported zero-based line is 1, while the physical line is 2. The skipped multiline lexeme’s line accounting needs an adapter or a different lexical definition. Our ANTLR wrapper also uses a physical-position map for its own newline conventions.</p>
<p>That is useful engineering evidence. It is not a verdict that either library “cannot do locations.” It identifies where the integration boundary must do more work.</p>
</section>
<section id="boundaries"><div class="number">06 / A grammar earns its shape</div><h2>The last name was not another port.</h2>
<p>An XSPICE-shaped fragment ends in a model reference. Consider <code>a1 in out gain</code>: two named ports followed by the model <code>gain</code>. The straightforward first rule looked like this:</p>
<pre><code>card : Name port+ Name</code></pre>
<p>In the initial Sly implementation, the repeated port production consumed the final name. The test run had 14 passes and six failures. The current ANTLR grammar handles that shape with its recognition machinery; the candidate needed a more explicit boundary.</p>
<pre><code>card : Name port tail
tail : Name tail?
tail : Number tail
tail : compound tail</code></pre>
<p>The first port is required. For a named tail element, another tail makes this name a port; the final named element becomes the model reference. The C# action constructs the corresponding nodes. The library still recognizes the structure—there is no handwritten token-walking parser.</p>
<p>This named-model fragment is intentionally limited. The numeric-model-reference challenge exposes a missing production. A complete port grammar also needs typed vectors and other forms that are already covered by the simulator’s ANTLR frontend.</p>
<h3>A terminator is not always a prefix</h3>
<pre><code>.control
.endc_extra
.endc</code></pre>
<p>The generic control probe uses a sugar token for <code>.endc</code>. It rejects the example above, while the ANTLR baseline keeps the longer command name as a control record and recognizes the real terminator. The candidate needs a better token boundary rule.</p>
<p>These cases explain why parser work can be substantial even with a good library. The package removes the recognition engine you would otherwise write. You still have to define the language’s boundaries and test their consequences.</p>
</section>

<section id="testing"><div class="number">09 / Testing the claims</div><h2>A green result is the beginning of an explanation.</h2>
<p>The tests check malformed delimiters, missing operands, extra differential nodes, source offsets, precedence, lexical modes and inert control text. FsCheck adds 128 generated differential pairs with replay seed <code>551,20261031</code> and 128 malformed-string cases with <code>552,20261031</code>. Malformed strings are bounded to 128 UTF-16 characters.</p>
<p>These are finite, reproducible property checks. They are not an exhaustive input search, a coverage-guided fuzz campaign, an adversarial-depth qualification or evidence that every SPICE dialect is supported.</p>
<div class="tablewrap"><table><thead><tr><th>Original study measurement</th><th>Line coverage</th><th>Branch coverage</th><th>Scope</th></tr></thead><tbody><tr><td>Unit collector: whole experiment assembly</td><td>36.22%</td><td>28.26%</td><td>Includes unexecuted CLI and report-fixture catalogue</td></tr><tr><td>Unit collector: candidate API class</td><td>100%</td><td>90%</td><td>Only <code>Trial</code>, not the complete assembly or language</td></tr><tr><td>Separate CLI collector</td><td>91.04%</td><td>74.29%</td><td>Comparison executable run, not the same unit-test scope</td></tr></tbody></table></div>
<p>A low aggregate can expose a scope mismatch: unit tests do not run the reporting CLI. A high API-class number still says little about whether the grammar recognizes every intended sentence. Attribute strings and third-party recognition behavior need their own acceptance evidence.</p>
<h3>Mutation testing found a real weakness in the tests</h3>
<p>The first focused Stryker.NET run on <code>Trial.cs</code> killed 12 mutants, with three survivors and four uncovered. Stronger lexical-diagnostic and failed-result assertions improved the final result to <strong>15 killed, two survivors, two uncovered and three ignored</strong>.</p>
<p>The remaining survivors alter an error-list separator and a defensive failure-result null guard. The observed inputs do not distinguish them; that is not a general proof of equivalence. The two uncovered mutants concern construction failure of fixed valid grammars.</p>
<details><summary>What was excluded from the mutation score?</summary><p>The tool reported 79 compile-error mutants in the excluded CLI source and 148 ignored mutants in the excluded fixture/grammar files. These are not kills. The campaign did not mutate the third-party parser machine or grammar productions. The evidence preserves those distinctions instead of reporting a flattering combined score.</p></details>
<p>The downloadable lab’s parser and test source are the same implementation files, with a smaller dependency graph and a dedicated CLI. Its fresh test run also passed all 30 tests. The historical coverage and mutation figures above still describe the original study, not an invented measurement of the browser or a new full mutation campaign on this page.</p>

<section id="choice"><div class="number">10 / Does the complexity earn its place?</div><h2>Choose the maintenance boundary you want.</h2>
<div class="tablewrap"><table><thead><tr><th>Approach</th><th>Grammar lives in</th><th>Attractive when</th><th>Cost to keep visible</th></tr></thead><tbody><tr><td><strong>Sly</strong></td><td>C# enums, production and operator attributes</td><td>A compact .NET DSL benefits from a typed, annotated definition</td><td>Grammar factoring, context integration, diagnostics and runtime construction</td></tr><tr><td><strong>ANTLR</strong></td><td>Separate grammar files; generated target-language source</td><td>A substantial language, existing grammar or cross-language ecosystem fits the tool</td><td>Generator setup, grammar/target integration and version qualification</td></tr><tr><td><strong>Parlot</strong></td><td>C# parser composition; generation facilities also exist</td><td>The team likes composable C# parsing APIs</td><td>Executable grammar composition and the selected generation/runtime path</td></tr><tr><td><strong>Superpower</strong></td><td>C# tokenizers and parser combinators</td><td>Explicit tokenization and diagnostic-oriented composition fit the application</td><td>More of the language definition is assembled in C# code</td></tr></tbody></table></div>
<p>This table describes approaches. It is not a speed benchmark, completeness ranking or proof that one package is universally easier to maintain. We executed the bounded Sly study; Parlot and Superpower are primary-source comparisons here.</p>
<h3>Why we kept ANTLR</h3>
<p>The simulator already has a working generated frontend, resource policies, source mapping, regression evidence and a complete declared-sample gate. Sly showed that a C# package is credible, not that replacing the current parser would buy enough benefit to justify requalification.</p>
<p>Java is needed for our pinned ANTLR generator, not for the generated C# parser at runtime. <a href="https://github.com/antlr-ng/antlr-ng">antlr-ng</a> also provides a TypeScript-based generator with C# output. Changing generators would still need compatibility evidence; removing Java alone is not a behavioral qualification.</p>
<div class="columns"><div class="box"><h3>Sly is worth trying when…</h3><p>You have a genuinely small language, a .NET team, clear examples and a desire to keep grammar rules close to typed syntax actions. Start with the hardest ambiguous and malformed inputs.</p></div><div class="box"><h3>Skip the custom language when…</h3><p>A standard format or complete existing parser meets the need. Do not create a new grammar simply because its annotations look elegant. Reuse should be tested against real inputs first.</p></div></div>
<p>The durable lesson is broader than a package choice: make textual boundaries explicit, preserve syntax independently of execution, and keep the evidence strong enough that a future engineer can change the language without guessing.</p>
</section>
